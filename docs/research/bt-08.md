# Re-audit: what the present interfaces actually permit, what they fail to guarantee, and what the additive API should become

You are right to challenge the causal chain. My previous wording was too absolute.

The corrected conclusion is:

> The present `go-pabt` interfaces do **not prevent** BT Expansion, OBTEA, heuristic search, indexing, closed-set search, conflict analysis, or formal verification from being implemented. A sufficiently disciplined concrete `Condition`, `Action`, and `State` implementation can encode much of the required machinery, and side tables or stricter extension interfaces can supply the rest.
>
> What the interfaces do **not** provide is a planner-inspectable, enforceable semantic contract from which those algorithms’ guarantees and optimizations can be derived for arbitrary conforming implementations.

That distinction is fundamental:

| Level                        | Question                                                                                              |
| ---------------------------- | ----------------------------------------------------------------------------------------------------- |
| Computational expressiveness | Could application code somehow encode the information?                                                |
| Semantic inspectability      | Can a generic planner inspect and manipulate that information?                                        |
| Contract enforcement         | Can the planner reject implementations that violate the required model?                               |
| Theorem applicability        | Can it establish that a paper’s assumptions hold and therefore carry the theorem into this execution? |

`Condition.Match(any) bool` is computationally very expressive. It is weak at the other three levels.

Two other corrections are also necessary:

1. `State.Actions` already has a meaningful PA-BT completeness contract: its documentation requires **all viable actions** for the failed condition. It is not an incomplete contract for its intended finite, synchronous use. It is simply not a sufficiently expressive *general grounding protocol* for lazy, continuous, approximate, budgeted, or learned candidate sources. ([GitHub][1])
2. Immutability, snapshots, compiled programs, and per-instance state are not all mathematical necessities. Some are theorem requirements, some are ways of implementing those requirements, and some are performance architecture choices. I separate them below.

I also accept the module constraint:

> All new rich-definition, compiler, runtime, planner-annotation, and verification facilities belong additively in the existing `github.com/joeycumines/go-behaviortree` module, with no major-version change and no alteration to the existing `Node func() (Tick, []Node)` ABI. `github.com/joeycumines/go-pabt` remains intact.

The attached analysis’s strongest architectural proposal—an optional rich definition compiled into a shared program and exposed as an ordinary existing `Node`—is the correct pivot. I do not adopt every API choice in it, particularly its already-fixed execution and abort protocol, but its compatibility architecture is sound.

# 1. Why one opaque `Match` operation is not a complete planning semantics

The present abstractions are:

```go
type Condition interface {
    Variable
    Match(value any) bool
}

type Effect interface {
    Variable
    Value() any
}
```

The implementation uses `Match` in at least three logically distinct settings:

```text
Runtime evaluation
    condition.Match(state.Variable(condition.Key()))

Effect support
    condition.Match(effect.Value())

Conflict testing
    !condition.Match(effect.Value())
```

The source explicitly acknowledges that the same `Match` method may receive either an actual state value or an effect value, and even notes that stateful conditions may need to distinguish the two. `Effect.Value` is documented only as the expected new value and explicitly says it is not guaranteed. ([GitHub][1])

These three operations coincide only under a restricted mathematical model.

Let:

* (x_k) be one state variable;
* (C_k : V_k \rightarrow {\text{false},\text{true}}) be a pure unary predicate;
* (E_k := v) be an exact, unconditional, deterministic assignment;
* the effect have no other relevant writes.

Then:

```text
Evaluate C in state s:
    Ck(s[k])

Does E establish C?
    Ck(v)

Does E conflict with C?
    ¬Ck(v)
```

Under exactly those assumptions, reusing `Match` is coherent.

The Go interface, however, does not state that `Match` is:

* pure;
* deterministic;
* total;
* dependent only on its argument;
* stable over the planning operation;
* an extensional predicate, where equal inputs always have equal meanings;
* appropriate for synthetic effect values;
* free of time, random, global-state, I/O, or closure dependencies.

This is not an accusation that existing implementations do those things. It is a statement about what a generic implementation may soundly infer from the interface.

Consider:

```go
type RangeCondition struct {
    Limit func() int
}

func (c RangeCondition) Match(value any) bool {
    return value.(int) < c.Limit()
}
```

The condition is evaluable. It does not define a stable symbolic constraint unless the semantics of `Limit` are also modeled.

Or:

```go
func (c ReachableCondition) Match(value any) bool {
    return value.(Cell) == c.Target &&
        globalOccupancy.PathExists(actor.Position, c.Target)
}
```

Passing an effect’s synthetic cell value into this matcher does not establish that the action entails reachability.

The issue is therefore not “callbacks are incapable of planning.” The issue is:

> A callback is an implementation of a decision procedure, not necessarily a declarative representation of the proposition being decided.

A richer planning layer needs to distinguish at least:

```go
Evaluate(snapshot, condition) Truth
Entails(transition, condition) Relation
Conflicts(transition, condition) Relation
Regress(condition, action) Condition
```

Those may share optimized implementations for simple finite-domain conditions. They must not be assumed identical by the general API.

# 2. Complete BT Expansion: what is actually required

## 2.1 The theorem’s model

BT Expansion’s soundness and completeness result is not a theorem about arbitrary behavior-tree nodes or arbitrary Boolean callbacks. It is proved through a finite state-space formulation combined with STRIPS-style planning. States and conditions are sets of literals; actions have explicit preconditions, add effects, and delete effects; and the algorithm expands a condition through the action transition model. The paper presents this formalization specifically to obtain soundness and completeness that are unavailable from an unstructured classical BT representation alone. ([AAAI Publications][2])

In that model, an action is broadly:

[
a =
\left\langle
pre(a), add(a), del(a)
\right\rangle
]

and successful execution changes a state according to:

[
s' =
\left(s \cup add(a)\right)\setminus del(a)
]

The proof depends on more than being able to ask whether one value “matches” a condition. It depends on being able to define and reason over:

* a finite symbolic state space;
* a finite or exhaustively enumerable action set;
* exact applicability;
* exact successor or predecessor conditions;
* preservation and deletion of required literals;
* whether a symbolic condition has already been expanded;
* whether every solvable predecessor can eventually be explored.

## 2.2 What `go-pabt` already supplies

The current interface is not wholly alien to that model:

* A comparable `Key` can identify a symbolic variable or fluent.
* `Effects` can represent finite-domain assignments.
* Boolean variables can encode positive and negative literals.
* `Conditions()` provides an OR of conjunctions.
* The goal is also an OR of conjunctions.
* `State.Actions(failed)` can act as an exact support index, returning every action that may establish the failed condition.
* The contract requires all relevant effects to be listed. ([GitHub][1])

A disciplined concrete condition type could therefore be:

```go
type LiteralCondition struct {
    Atom  AtomID
    Value bool
}

func (c LiteralCondition) Key() any {
    return c.Atom
}

func (c LiteralCondition) Match(value any) bool {
    return value == c.Value
}
```

A disciplined effect type could encode an exact assignment. A separate BT Expansion engine could use those concrete types and satisfy the paper’s assumptions.

## 2.3 What is not in the base contract

The base API does not establish that:

* the state space is finite;
* action enumeration is finite;
* the returned actions constitute the complete transition model needed by the theorem rather than merely the application’s current guesses;
* effects are exact rather than “expected”;
* all outcomes are deterministic;
* condition identity and equality are available;
* condition sets can be regressed canonically;
* an effect’s assignment is equivalent to a STRIPS add/delete transition;
* `Match` is a pure unary relation;
* execution implements the declared action transition.

Thus, the corrected conclusion is:

> **BT Expansion can be implemented over stricter concrete implementations or an additive symbolic view. The current interfaces do not themselves certify that its completeness theorem applies.**

The missing element is not raw expressive power. It is an inspectable model plus enforceable assumptions.

# 3. OBTEA: the exact gaps are costs, transition algebra, and condition identity

OBTEA makes the necessary semantics particularly explicit.

Its planning problem contains:

* a finite state set (S);
* a finite action set (A);
* transition rules (P);
* an initial state (s_0);
* a goal;
* a nonnegative action-cost function (D(a)).

Actions use `pre`, `add`, and `del` sets. Algorithm 1 maintains:

* (C_U): explored but unexpanded conditions;
* (C_E): expanded conditions;
* (D(c)): the currently best cost for a condition;
* a minimum-cost selection operation;
* predecessor generation:

[
c_a =
pre(a)\cup\left(c\setminus add(a)\right)
]

* delete-effect tests;
* dominance tests:

[
D(c)+D(a)<D(c_a)
]

The paper then terminates when the minimum-cost expanded condition holds in the initial state. These are not incidental implementation details; they are the uniform-cost-search mechanism supporting its optimality claim. ([IJCAI][3])

## 3.1 What maps well already

The current `go-pabt` goal representation is structurally close to DNF:

```go
goal []Conditions[T]
```

Each `Conditions[T]` is a conjunction, and the outer slice is a disjunction. `Action.Conditions()` similarly supports alternative conjunctions. That part is not a deficiency. ([GitHub][1])

`State.Actions(failed)` could also replace OBTEA’s literal “for every (a\in A)” loop with an exact reverse support index:

```text
actions whose modeled effects may support c
```

That is potentially more efficient than scanning all actions. It remains equivalent only if it is complete for the required support relation.

## 3.2 What is absent

The base `Action` interface has no:

```text
action cost
stable action identity
explicit add set
explicit delete set
outcome set
condition-set regression
```

The base `Condition` interface has no:

```text
semantic equality
hash
canonical identity
literal representation
```

The interface value itself cannot safely serve as a universal map key: an interface is comparable only when its dynamic value is comparable, and semantic equivalence is not the same as Go identity anyway.

The current implementation’s predecessor construction is PA-BT PPA expansion, not OBTEA’s cost-labelled search over canonical condition sets. This is entirely appropriate for the algorithm it implements. It does not provide OBTEA’s uniform-cost machinery. ([GitHub][4])

## 3.3 Correct conclusion

> **OBTEA is implementable with a richer action/condition type, a cost side table, and an exact support provider. The current generic API does not expose enough common semantics for a reusable OBTEA engine to derive its optimality proof across arbitrary implementations.**

In particular, “action ordering” is not enough. The engine must know that costs are nonnegative, that all relevant predecessors are present, and that two condition sets judged equal really denote the same search state.

# 4. Admissible heuristic search: my prior claim was materially overstated

An admissible heuristic is a lower bound on the true remaining cost. In ordinary A* notation:

[
f(n)=g(n)+h(n)
]

and admissibility requires:

[
h(n)\leq h^*(n)
]

for every relevant search node (n), where (h^*(n)) is the actual least cost to a goal. A* also requires a search graph or transition system and edge costs. ([U of Auckland Computer Science][5])

Nothing about `Condition.Match` inherently prevents that.

A user could define an entirely separate search graph:

```go
type SearchState struct {
    Facts BitSet
}

func Heuristic(SearchState) Cost
func Successors(SearchState) []Transition
```

and use `go-pabt` only when converting the resulting policy into an executable BT.

Alternatively, a concrete `State[T]` could keep a side model containing costs and a heuristic.

The accurate criticism is narrower:

* `go-pabt.Action` exposes no cost.
* `Condition` exposes no stable search-state identity.
* no API distinguishes an admissible lower bound from an arbitrary estimate;
* no API expresses the assumptions under which a heuristic is a lower bound;
* the planner cannot validate that a learned estimate is admissible.

HBTP illustrates the distinction well: learned or LLM-generated guidance can reorder or prune search, but inaccurate or incomplete reasoning requires fallback expansion if reliability is to be retained. The paper explicitly treats the learned path as heuristic guidance around a symbolic planner, not as self-authenticating proof of optimality. ([arXiv][6])

The corrected conclusion is:

> **The present API neither enables nor disables admissible heuristic search as such. It simply does not standardize the weighted search graph or the lower-bound contract required to make admissibility an interoperable property.**

# 5. Effect indexing: the current API already permits it

My previous wording was wrong here.

`State.Actions(failed)` is already an abstraction boundary through which an implementation can perform arbitrary indexing:

```go
map[VariableKey][]Action
map[PredicateID][]Schema
map[AtomID][]GroundAction
intervalIndex
databaseQuery
```

The planner need not know how.

Moreover, `Key()` is explicitly required to return a comparable variable identifier. The current PA-BT implementation itself maps action effects by key, and `State.Actions` can perform a coarse key-to-actions lookup before returning candidates. ([GitHub][1])

## 5.1 What is actually unavailable

The generic library cannot automatically derive richer indexes from an arbitrary `Match` callback.

Suppose the condition is:

```text
temperature < 10
```

and actions assign:

```text
temperature := 5
temperature := 7
temperature := 20
```

The library can:

1. index all effects by the `temperature` key;
2. scan that bucket and call `Match` for each effect.

It cannot generically know that the condition denotes an interval and construct a range index unless that structure is represented declaratively.

Similarly, first-order lifted planning needs to reason about an action schema such as:

```text
Move(?actor, ?from, ?to)
```

and find substitutions satisfying its precondition in the current state. Lifted successor-generation research treats the state as a database and an action precondition as a conjunctive query, allowing applicable grounded actions to be produced without first materializing the entire ground action set. Grounded planners such as Fast Downward also compile structured preconditions into successor-generator decision structures instead of naively testing every operator. ([AAAI Publications][7])

`State.Actions` can hide such an implementation internally. What it cannot do is expose its schemas, substitutions, query plan, or index to another generic planner.

The accurate conclusion is:

> **The API supports application-owned effect indexing, especially by variable key. It does not expose enough structure for reusable automatic semantic indexing, lifted successor generation, or index sharing across planning algorithms.**

That is an extensibility limitation, not a prohibition.

# 6. Canonical closed sets: canonicalization is optional; correct equivalence is not

I previously bundled two separate ideas:

* **closed-set semantics**: recognizing that a search condition or state has already been processed;
* **canonical representation**: one efficient method for implementing that recognition.

BT Expansion and OBTEA maintain sets of expanded symbolic conditions. OBTEA also maintains best-known costs for condition sets and discards dominated revisits. Algorithm 1 explicitly tests membership in (C_E) and compares (D(c_a)). ([IJCAI][3])

A canonical bitset or interned identifier is not mathematically mandatory. Other valid representations include:

```text
structural equality
BDD identity
sorted literal slices
hash + equality
union-find representative
database key
```

What is mandatory for a graph-search interpretation is that equivalence be correct for the algorithm’s state abstraction.

The current interface supplies only:

```go
Key() any
Match(value any) bool
```

`Key` identifies a state variable, not a complete condition. Two conditions may have the same key but different semantics:

```text
battery >= 30
battery >= 80
battery in [20, 50]
```

Conversely, two separate callback instances may denote the same predicate but have no common semantic identifier.

For arbitrary executable predicates, extensional equality cannot generally be inferred by inspecting the Go value.

Again, this does not make closed sets impossible. A concrete type can add:

```go
type CanonicalCondition interface {
    pabt.Condition

    Canonical() ConditionID
}
```

or a new engine can constrain `T` more strongly.

The corrected conclusion is:

> **The current base interface lacks a generic condition-equivalence contract. Algorithms needing closed-set semantics must impose one through a stricter type, adapter, or side model. “Canonical condition sets” are a recommended efficient implementation, not a universal prerequisite.**

PA-BT itself need not be changed merely because other algorithms use closed sets.

# 7. Conflict resolution: valid for a narrow assignment model, not a universal relation

The current conflict test is effectively:

```go
if earlierAction has an effect for condition.Key() &&
   !condition.Match(effect.Value()) {
    conflict
}
```

The source describes this as checking a new action’s conditions against effects of actions executed before it, then moving the conflicting subtree leftward. ([GitHub][4])

This is a principled test under these assumptions:

1. Every condition depends on exactly one variable identified by `Key`.
2. Every relevant write to that variable is declared.
3. An effect is an exact, unconditional, deterministic assignment.
4. `Match` is a pure predicate over that variable’s value.
5. Actions do not concurrently modify the condition’s dependencies.
6. The declared effect models the post-action state that execution actually produces.

Then, for a condition (C_k) and assignment (x_k:=v):

[
C_k(v)=\text{false}
]

is exactly the statement that executing the assignment makes the condition false.

The relation becomes incomplete or unsound outside that model.

## 7.1 Multi-variable conditions

```text
x < y
```

cannot generally be attached to one key without hiding a dependency.

An effect changing `y` may invalidate the condition even if the selected key is `x`.

## 7.2 Derived predicates

```text
Reachable(actor, goal)
```

may depend on:

* actor pose;
* occupancy;
* robot footprint;
* door state;
* dynamic obstacles;
* map revision.

An effect on any dependency may change reachability. A same-key test sees that only if every action redundantly declares an effect on a synthetic `reachable` variable.

## 7.3 Conditional effects

```text
when doorUnlocked:
    doorOpen := true
```

A plain expected value does not expose the condition under which the write occurs.

## 7.4 Nondeterministic outcomes

```text
OpenDoor:
    outcome 1: doorOpen
    outcome 2: jammed
```

There is no single `Effect.Value` against which universal preservation can be tested.

## 7.5 Numeric or set-valued transitions

An action may have:

```text
battery' ∈ [battery-10, battery-5]
```

rather than a single assignment.

## 7.6 Model–execution mismatch

The current effect documentation says `Value()` is expected and “doesn’t guarantee it.” Consequently, even a symbolically non-conflicting ordering is not an execution guarantee unless action implementation and effect model are consistent. ([GitHub][1])

The corrected assessment is:

> **The existing conflict resolver is coherent for PA-BT’s intended unary-variable, exact-effect interpretation. A broader planning API needs explicit read/write dependencies, transition outcomes, entailment, and interference relations.**

It should not replace the present PA-BT implementation. It should exist in the optional richer model consumed by other algorithms.

# 8. Formal verification: callbacks require an external abstraction

An arbitrary callback is not intrinsically unverifiable. It can be:

* manually abstracted;
* translated from a restricted DSL;
* replaced by a finite transition model;
* monitored at runtime;
* treated as a nondeterministic environment action;
* discharged as an explicit assumption.

What cannot generally be done is to extract a faithful formal model automatically from unrestricted Go behavior.

BehaVerify demonstrates exactly this boundary. Standardized composite-node semantics can be translated automatically, while custom leaves require additional user-provided modeling to be represented correctly. It then checks temporal properties over the resulting nuXmv model. ([arXiv][8])

The current closure-based `Node` introduces a similar issue:

```go
type Node func() (Tick, []Node)
```

The closure may contain hidden mutable state, perform I/O, or return structure dynamically. Existing `Metadata` helps expose a conceptual tree independently of physical closures, but it does not define the transition semantics of arbitrary leaves. ([GitHub][9])

The corrected conclusion is:

> **The existing API can participate in formal verification when users provide abstractions. It does not expose sufficient semantics for automatic faithful verification of arbitrary implementations.**

The rich layer therefore needs an optional capability such as:

```go
type FormalProvider interface {
    BT_Formal() FormalModel
}
```

An absent model should create an explicit opaque boundary, not an invented one.

# 9. Reassessing `State.Actions`: a good PA-BT contract, not a universal grounder

The present contract is:

```go
Actions(failed T) ([]Action[T], error)
```

and its documentation requires all viable actions for the failed constraint. ([GitHub][1])

This is a perfectly reasonable contract when:

* the relevant action set is finite;
* it is cheap enough to enumerate synchronously;
* each returned action can be represented by a lightweight handle;
* grounding is exact;
* no planner budget needs to interrupt enumeration;
* candidates do not require persistent sampling cursors;
* the world/model does not change during enumeration.

The slice does not necessarily imply one heap allocation per call. It could be backed by reused storage, a static array, or lightweight interface handles.

Its semantic constraint is:

> By the time `Actions` returns, the complete result for that call must be logically available to the planner.

It cannot interleave generation with planner consumption.

Below is the exact reason each additional capability becomes necessary in broader planning.

---

## 9.1 “There are more candidates”

### Needed by

Lazy candidate generation, task-and-motion planning, large grounded domains, and any planner that wants to begin evaluating candidates before the full set is produced.

### Specific mechanism

PDDLStream defines a stream’s procedural component as a conditional generator mapping input values to a finite or infinite sequence of output tuples. Section 3.1 formalizes a generator and a `next(g)` operation that obtains the next output. The planner need not enumerate the sequence before considering the first result. ([arXiv][10])

### Why the slice cannot express it

A returned slice means:

```text
these are the results of this invocation
```

There is no accompanying state saying:

```text
these are the first 32 results;
the exact source has further results
```

The provider could retain hidden state and return another batch on a later call, but `go-pabt` has no protocol telling the planner that another call is required, whether results may repeat, or whether a later call continues the same search.

### Honest conclusion

This capability is not needed by current finite PA-BT domains. It is required for a reusable lazy-grounding protocol.

---

## 9.2 “Enumeration is complete”

### Needed by

Any completeness or optimality argument that depends on having considered every relevant action or on a fair enumeration that will eventually consider every relevant action.

### Specific mechanism

BT Expansion’s completeness assumes the formal transition model is available for exploration. OBTEA evaluates every relevant predecessor before finalizing minimum-cost expansion. PDDLStream’s algorithms distinguish feasible-instance semi-completeness from simply trying a finite sample and stopping. ([AAAI Publications][2])

### Current behavior

For the current API, completion is implicit in the words “all viable actions.” That is a valid contract.

### The generalization problem

A source that returns:

```text
the 20 actions an LLM considered likely
```

has not fulfilled the current contract, even if those actions are useful.

A richer source needs to distinguish:

```text
Complete:
    no relevant candidates remain

Suspended:
    exact enumeration can resume with more budget

Incomplete:
    the source is advisory and makes no coverage claim
```

Without that distinction, a generic complete planner cannot tell whether “no solution found” means:

* the model is unsatisfiable;
* the source has been exhausted;
* the sampling budget ended;
* the learned source omitted a necessary action.

---

## 9.3 “Enumeration was suspended by budget”

### Needed by

Anytime planning, real-time game AI, bounded robotics planning, lazy TAMP, or cooperative scheduling where one grounder may not monopolize the thread.

### Specific mechanism

PDDLStream algorithms explicitly interleave finite symbolic planning problems with stream evaluation. Its Persistent algorithm balances time spent searching against time spent sampling rather than eagerly evaluating every external procedure. ([arXiv][10])

### Why the current signature is insufficient

An implementation has three unattractive choices:

1. block until enumeration is complete;
2. return a partial slice while violating “all viable actions”;
3. hide continuation state and hope the caller invokes it again.

A budget-aware cursor can instead report:

```go
n, CursorSuspended, nil
```

while preserving the claim that its eventual enumeration is exact.

---

## 9.4 “These are learned suggestions”

### Needed by

HBTP-style LLM guidance, learned action ranking, proposal networks, retrieval systems, and planner portfolios.

### Specific mechanism

HBTP uses LLM reasoning to identify heuristic paths, action predicates, and objects. Its authors explicitly address inaccurate or incomplete LLM reasoning by retaining symbolic planning, widening the pruned action space, and using feedback. Learned guidance is therefore not the same semantic object as an exhaustive action model. ([arXiv][6])

### Why the distinction matters

Suppose:

```go
Actions(failed) == learnedTop10
```

A PA-BT consumer will interpret those as **all viable actions**. If the necessary action is absent, an algorithm may report failure even though the modeled problem is solvable.

A richer API should separate:

```text
Exact source
    coverage claim

Advisor
    ordering or proposals only

Pruner
    removes candidates and must state what guarantee is lost

Heuristic
    estimates cost or usefulness
```

The planner can use learned proposals first while retaining an exact fallback.

---

## 9.5 “This candidate depends on a geometric certificate”

### Needed by

Task-and-motion planning, motion planning, inverse kinematics, collision checking, visibility, grasp generation, and other black-box geometric procedures.

### Specific mechanism

PDDLStream couples each procedural stream with declarative certified facts. Its example streams generate poses, grasps, inverse-kinematic configurations, and trajectories while certifying predicates such as kinematic feasibility, motion validity, containment, and collision freedom. The planner reasons about the certified facts without needing to understand the sampler’s implementation. ([arXiv][10])

For example:

```text
stream output:
    trajectory τ

certified:
    Motion(q1, τ, q2)
    CollisionFree(τ, scene)
```

### What an ordinary `Action` can do

A concrete action can privately capture `τ` in a closure. That is enough to execute it.

### What the planner cannot then do generically

It cannot inspect:

* what fact the trajectory certifies;
* which scene revision it was checked against;
* which action precondition relies on it;
* whether the certificate can be reused;
* why the candidate is valid;
* whether another planner can validate it.

The requirement is therefore not “the slice cannot hold a trajectory.” It can.

The requirement is:

> The candidate protocol must expose the relationship between generated data and the symbolic facts that data certifies.

---

## 9.6 Infinite or continuous binding domains

### Needed by

Robotic poses, grasps, configurations, trajectories, continuous controls, procedural level spaces, and some game steering or placement problems.

### Specific mechanism

PDDLStream was designed to avoid pre-enumerating a finite set of every possible pose, grasp, or configuration. Its conditional generators produce finite or infinite enumerable sequences of candidate values, inducing an infinitely large action-instance space. ([arXiv][10])

A continuous mathematical domain is not exhaustively enumerated. The planner instead uses a sampling strategy with a semi-completeness or probabilistic-completeness argument appropriate to the generator family.

### Why a slice is insufficient

An actually infinite complete slice cannot return.

A finite sampled slice is necessarily one of:

* a bounded approximation;
* a prefix of a fair generator;
* an advisory candidate set.

Those three meanings need different contracts.

---

## 9.7 Continuation after expensive sampling

### Needed by

Stateful inverse-kinematics solvers, randomized motion planners, trajectory optimizers, database queries, staged constraint solving, and any generator whose next result builds on previous work.

### Specific mechanism

PDDLStream models a generator with repeated `next(g)` operations and tracks its evaluation count. Stream instances retain their position in an output sequence. Algorithms repeatedly evaluate selected stream instances rather than reconstructing them from scratch. ([arXiv][10])

### Missing lifecycle in `Actions`

The provider can hide a generator in `State`, but the planner has no explicit way to:

* resume it;
* cancel it;
* identify it;
* associate it with a failed condition/model revision;
* know whether the next call is continuation or restart;
* release its resources.

This motivates a cursor rather than merely an iterator:

```go
type CandidateCursor interface {
    PLAN_Next(
        context.Context,
        []Candidate,
    ) (int, CursorState, error)

    Close() error
}
```

The destination slice is caller-owned, so the protocol does not require one allocation per batch.

---

## 9.8 Candidate cost and lower bounds

### Needed by

OBTEA, A*, branch-and-bound, best-first search, anytime search, Pareto search, and cost-sensitive TAMP.

### Specific mechanisms

OBTEA requires a nonnegative (D(a)) for every action and orders condition expansion by accumulated cost. A* admissibility requires a lower bound on remaining path cost. PDDLStream also supports external cost functions, such as trajectory distance, for cost-sensitive planning in stream-induced action spaces. ([IJCAI][3])

### Why this is not in `Actions`

The returned `Action` has no standard cost method.

A concrete action can carry cost privately, but no generic planner can obtain it without a further interface or side registry.

There are also two different values:

```text
exact candidate cost:
    known after generation

lower bound:
    available before expensive completion and safe for pruning
```

They must not be conflated. A learned score is not automatically a lower bound.

## 9.9 Provenance

### Needed by

Not by the elementary correctness proof of every planner, but by:

* auditability;
* debugging;
* assurance;
* deciding whether a candidate is exact, sampled, learned, or manually authored;
* reproducing a planning decision;
* attributing a failed model;
* security policy;
* certificate invalidation.

CABTO explicitly separates high-level model completeness from low-level policy consistency and uses planner and environment feedback to refine the grounding. Determining which source proposed a model or policy and what evidence tested it is operationally significant in that workflow. ([AAAI Publications][11])

### Honest qualification

Provenance is an assurance and systems-engineering requirement, not a universal search-theory prerequisite.

It can be carried privately by the concrete action today. A standardized rich protocol makes it interoperable.

---

## 9.10 Stale candidates after model or world revision

### Needed by

Online planning, games with moving entities, robotics with changing geometry, plan repair, cached motion plans, and asynchronous candidate generation.

### Specific mechanism

A collision-free trajectory is valid relative to:

```text
start configuration
goal configuration
robot geometry
obstacle geometry
collision model
```

PDDLStream’s certified facts are functions of the relevant stream inputs and static facts. Extending that mechanism to a changing online world implies that a certificate must be scoped to the model/world revision whose facts justified it. This revision requirement is an engineering inference from the stream-certificate semantics, not a theorem stated by PDDLStream itself. ([arXiv][10])

### Why the current protocol is silent

An action may capture a world snapshot internally, but the planner has no standard way to know:

```text
candidate generated at occupancy revision 41
current occupancy revision 46
certificate no longer reusable
```

A candidate should be able to carry dependency revisions or a validator.

---

## 9.11 Action-schema indexing rather than full grounding

### Needed by

Large first-order domains where constructing every grounded action causes prohibitive time or memory growth.

### Specific mechanism

Lifted successor generation treats an action schema’s precondition as a database query over the current state. Its result is the set of variable substitutions yielding applicable ground actions. The cited work specifically addresses hard-to-ground problems and reports that decision-tree-like grounded successor structures and lifted query techniques can substantially accelerate successor generation. ([AAAI Publications][7])

### What `State.Actions` can already do

The application may implement exactly that query internally and return grounded `Action` handles.

### What is not exposed

The generic planner sees only the result slice. It cannot:

* inspect the schema;
* share the query plan;
* delay individual bindings;
* retain schema-level heuristic information;
* reason about grounding completeness;
* combine grounding with another planner’s indexes.

Thus, this is an interoperability and reusable-infrastructure limitation, not an inability to implement lifted generation behind the interface.

# 10. A suitable richer candidate protocol

`go-pabt` should remain unchanged. A future planner-neutral layer in the existing `go-behaviortree` module can use something resembling:

```go
type CursorState uint8

const (
    CursorMore CursorState = iota + 1

    // Exact enumeration has ended.
    CursorComplete

    // Exact enumeration may resume with additional budget.
    CursorSuspended

    // The source has ended but makes no coverage claim.
    CursorIncomplete
)

type CandidateCursor interface {
    PLAN_Next(
        context.Context,
        []Candidate,
    ) (int, CursorState, error)

    Close() error
}

type Candidate struct {
    Action ActionRef

    Cost       Cost
    LowerBound Cost

    Evidence Evidence

    ModelRevision Revision
    WorldRevision Revision
}
```

This is not proposed as a replacement for every planner’s native internal representation. A finite classical planner should normally use dense action arrays and indexes directly.

The cursor is the interoperability boundary for:

* lazy grounding;
* continuous sampling;
* advisory proposals;
* external solvers;
* database-backed action generation.

A native planner should lower that boundary once and then use algorithm-specific arrays, bitsets, or query structures internally.

# 11. Reassessing the “non-negotiable invariants”

The earlier list incorrectly presented theorem requirements, implementation choices, and performance objectives as one category.

A better taxonomy follows.

---

## 11.1 Theorem-level semantic requirements

These are necessary when claiming the corresponding theorem.

### A coherent state or belief revision

BT Expansion and OBTEA evaluate conditions against one state (s). For example:

[
c\subseteq s
]

has a defined meaning only if the facts in (c) are evaluated against one coherent semantic state. ([IJCAI][3])

Consider two actual revisions:

```text
revision r0: x = 0, y = 0
revision r1: x = 1, y = 1
```

At both actual revisions:

```text
x == y
```

Suppose a planner reads:

```text
x at r0
y at r1
```

It constructs:

```text
x = 0, y = 1
```

That mixed tuple was never an actual state, and it makes `x == y` false.

A planner might therefore:

* expand a condition that was never false;
* reject an action that was always applicable;
* derive a predecessor that has no corresponding world state;
* violate the assumptions of its soundness argument.

The requirement is not specifically “copy the entire world into an immutable map.”

The actual requirement is:

> Every logical operation whose theorem is defined over one (s) must receive values from one declared state or belief revision.

Valid implementations include:

```text
immutable snapshot
read transaction
reader lock
MVCC revision
seqlock with retry
event-log position
estimator-produced belief revision
```

In robotics, raw sensors are naturally asynchronous. The coherent object may be a timestamped estimator or belief-state revision rather than simultaneous raw measurements.

A traditional reactive BT may intentionally read live state separately at each leaf. That is valid execution semantics. It simply is not identical to one classical atomic-state transition unless the proof model explicitly includes those interleavings.

### Stable model semantics within a claim’s scope

The action model may evolve. It need not be globally immutable.

However, a claim such as:

```text
optimal for model revision 17
```

is not automatically a claim about revision 18.

Search caches, closed sets, costs, certificates, and proofs must be:

* scoped to a model revision;
* incrementally repaired under a justified transformation; or
* invalidated when relevant model semantics change.

### Complete successor/support relation

A completeness theorem needs an exhaustive action relation or a fair generator that eventually enumerates every required action.

A learned proposal source may coexist with that relation. It cannot silently replace it while retaining the theorem.

### Correct search-state equivalence

Graph search needs a correct equivalence relation over its abstract states or conditions.

Canonical IDs are one implementation. Correct equality is the semantic requirement.

### Exact transition semantics

Sound symbolic regression and conflict analysis require a transition model whose semantics are known:

```text
deterministic assignment
add/delete transition
conditional transition
nondeterministic outcome relation
probabilistic transition
```

An opaque executor can still be used, but the guarantee is conditional on its consistency with the abstract transition.

---

## 11.2 Requirements for exact event-driven execution

These are not classical-planning theorem requirements. They are requirements for replacing polling with event scheduling without changing observable behavior.

Suppose a condition computes:

[
y=F(x,z)
]

The runtime caches (y_0=F(x_0,z_0)) and promises to reevaluate only when declared dependency (x) changes.

If (z) changes to (z_1), and:

[
F(x_0,z_1)\neq y_0
]

but no event is scheduled, the cached result is observably stale.

Therefore:

> Skipping a polling evaluation is semantics-preserving only when every change capable of altering the node’s result causes a wakeup, or a fallback cadence eventually reevaluates it.

This is why an arbitrary legacy closure cannot safely be made event-driven automatically. Its dependencies may include time, globals, external services, hidden fields, or dynamically selected data.

Unreal’s event-driven BT implementation makes the same architectural trade: blackboard observers and decorator aborts trigger reevaluation rather than traversing the whole tree every frame. That optimization relies on explicit observable changes. ([Epic Games Developers][12])

The rich runtime should therefore have three honest modes:

```go
const (
    ModeExact Mode = iota

    // Declared dependencies enable selective scheduling.
    // Opaque nodes remain polling-compatible.
    ModeIncremental

    // Additionally checks dynamic reads against declared
    // dependency supersets where instrumentation permits.
    ModeChecked
)
```

`ModeExact` is the compatibility baseline.

---

## 11.3 Strong architecture recommendations, not mathematical laws

### Immutable compiled `Program`

This is the most effective publication model for:

* safe concurrent sharing;
* cacheability;
* compact arrays;
* deterministic structure;
* zero-lock traversal;
* many agents sharing one definition.

In-place mutation under a global lock could also be correct. It is less attractive for the intended workloads.

### Per-instance execution state

This becomes necessary if one immutable program is shared among agents while each has independent:

* child cursor;
* running action;
* retry count;
* timer;
* activation state.

Mature game implementations use the same broad separation. Unreal shares behavior-tree node templates across agents for memory and CPU efficiency while storing agent-specific state separately or instancing only nodes that require it. ([Epic Games Developers][13])

This is not a rule imposed on ordinary legacy closures. An opaque legacy node may retain its own state. It simply cannot then be shared among agents unless its factory or contract makes that safe.

### Separate editable and executable forms

A linked or graph representation is excellent for:

* PA-BT subtree insertion;
* conflict relocation;
* planner edits;
* stable handles.

A flat program is excellent for:

* traversal;
* locality;
* per-instance state indexing;
* event dependency indexes.

Executing the editing representation directly can still be correct. Compiling it is a performance and lifecycle recommendation.

### Stable revision boundaries

A program should not be structurally modified while an instance is traversing it.

That can be implemented through:

* immutable replacement;
* copy-on-write;
* transactional patches;
* stop-the-world mutation;
* versioned graph snapshots.

Immutable replacement is the cleanest default.

---

## 11.4 Domain-dependent requirements

### Effect verification

In an authoritative in-process game simulation:

```go
world.Move(entity, destination)
return Success
```

may be the authoritative state transition. A separate observation verifier adds no truth.

In a robot or distributed service:

```text
controller reported completion
```

does not necessarily mean:

```text
declared symbolic effect holds
```

CABTO defines consistency precisely in this cross-layer sense: low-level control policies should produce state transitions matching their high-level action models. Its examples include actions whose controllers fail to establish declared effects or need an undeclared precondition. ([AAAI Publications][11])

Thus:

> Fresh effect verification is required when claiming model–executor consistency, not for every deterministic simulation.

### Unknown truth values

Three- or four-valued truth is required for belief-state and partial-observation modes. It is unnecessary for a closed-world deterministic game model whose state is authoritative.

### Cancellation

Cancellation is necessary for externally running or resource-owning actions that may be deselected. It is irrelevant to an instantaneous pure condition.

---

## 11.5 Performance objectives

These are release targets, not semantic invariants:

```text
zero steady-state allocations for native built-ins
no global lock on the tick path
one immutable Program shared by many Instances
dense child/state arrays
no interface dispatch for compiled native composites
bounded custom-interface dispatch
event-driven quiescence in O(1)
```

A correct opaque fallback may allocate. Compatibility takes priority over claiming universal zero allocation.

# 13. A defensible recursive definition interface

A strong candidate is:

```go
type Definition interface {
    // BT_ChildCount returns the finite direct-child count.
    BT_ChildCount() int

    // BT_Child returns the child at index.
    BT_Child(index int) Definition

    // BT_Bind creates one runtime behavior for one
    // structural occurrence in one Instance.
    //
    // A registered native lowerer may bypass this method.
    BT_Bind(*BindContext) (Behavior, error)

    mustEmbedUnimplementedDefinition()
}

type UnimplementedDefinition struct{}

func (UnimplementedDefinition) BT_ChildCount() int {
    return 0
}

func (UnimplementedDefinition) BT_Child(int) Definition {
    panic(ErrChildIndex)
}

func (UnimplementedDefinition) BT_Bind(
    *BindContext,
) (Behavior, error) {
    return nil, ErrUnsupported
}

func (UnimplementedDefinition) mustEmbedUnimplementedDefinition() {}
```

The exported interface-contract namespace is consistently `BT_`. The private embedding marker is the necessary exception.

The structural contract must say:

* child count is finite and nonnegative;
* count and order remain stable for the definition revision;
* repeated `BT_Child(i)` calls identify the same definition;
* child access is side-effect free;
* child access should be (O(1));
* nil children are invalid;
* a definition submitted for compilation is immutable;
* structural cycles require an explicit call/policy construct rather than accidental pointer cycles.

Dynamic behavior remains possible through explicit nodes such as:

```text
Slot
Call
PolicyDispatch
Planner
```

or by publishing a new definition revision.

Arbitrary dynamic legacy closures remain opaque `Node` islands.

# 14. `BT_ChildCount` and `BT_Child`: what is verifiably true

My earlier justification overclaimed exclusivity. Count/index is defensible, but not because iterators are incapable of the same tasks.

## 14.1 Exact claims

### Exact one-pass local capacity

Knowing a node’s child count lets a compiler reserve that node’s edge span without first materializing its children.

For a CSR-like representation:

```text
node.edgeStart
node.edgeCount
edges[]
```

the compiler can allocate or reserve exactly `edgeCount` entries for that node.

An iterator can achieve the same overall result by:

* appending to a global growable buffer;
* making a first counting pass and a second filling pass;
* buffering one node’s children.

Therefore count/index **simplifies** exact allocation. It does not make it uniquely possible.

### Replayability

`BT_Child(i)` is naturally replayable when its stability contract holds.

The standard `iter.Seq` convention says most iterators replay the sequence when called again, but explicitly permits single-use iterators that cannot be rewound. A compiler using `iter.Seq` would therefore need an additional “stable and replayable” contract. ([Go Packages][15])

This is a genuine semantic advantage for a compile-time tree definition.

### Random access

Count/index permits:

```text
validate child 4
lower selected children
partition child ranges
perform multi-pass analysis
```

without resuming or replaying an iterator from the start.

This advantage depends on `BT_Child(i)` actually being (O(1)). If an implementation obtains the (i)th child by walking a linked list, complete traversal becomes (O(n^2)).

### No mandatory yield closure

At a dynamically dispatched interface boundary, count/index does not require the caller to construct and pass a closure.

This can matter to current Go escape analysis. It is not a language guarantee that `iter.Seq` allocates.

### Deterministic structural occurrence ordering

A stable integer index gives each direct edge a natural identity:

```text
(parent occurrence, child index)
```

That helps assign reproducible occurrence IDs.

An ordered replayable iterator can do the same. Count/index merely makes the contract more explicit.

---

## 14.2 Claims that were overstated

Count/index is **not required** to:

* calculate tree depth;
* count total nodes or edges;
* validate structure;
* assign stable IDs;
* build a flat program;
* build CSR edges;
* traverse without allocation.

A replayable iterator or callback can do all of those.

Concrete, inlinable iterator functions may be allocation-free. The standard `iter.Seq` type is simply:

```go
type Seq[V any] func(yield func(V) bool)
```

and its callback model supports early termination naturally. ([Go Packages][15])

---

## 14.3 Detracting considerations

### Interface call per child

Count/index normally incurs one `BT_Child` interface call per child.

A callback interface may make one outer dynamic call and then invoke a statically known yield closure repeatedly.

Depending on compiler devirtualization and inlining, either can win.

### Lazy and virtual structure

`iter.Seq` naturally represents:

* lazily generated children;
* filtered views;
* virtual structures;
* streams;
* early termination.

For an immutable compiled BT definition, unrestricted laziness is often undesirable because compilation needs a finite stable artifact. For introspection, it is valuable.

### Expensive count

Some structures know how to enumerate children but cannot determine the count cheaply without enumeration.

Requiring (O(1)) count excludes them or forces caching.

### Compilation is not the hottest path

This interface is used during compilation or structural inspection, not native execution. A 50-nanosecond difference per child may be irrelevant if compilation is rare.

PA-BT or game hot-reload workloads may compile frequently, so it is still worth measuring.

---

## 14.4 Microbenchmark evidence

I reran a synthetic benchmark under:

```text
Go 1.23.2
linux/amd64
Intel Xeon Platinum 8370C
go test -bench=. -benchmem -benchtime=500ms -count=3
```

The benchmark forced genuinely dynamic interface dispatch by returning one of two concrete implementations from a `//go:noinline` function.

Median-like representative results:

| Traversal           | 8 children | Allocations | 64 children | Allocations |
| ------------------- | ---------: | ----------: | ----------: | ----------: |
| Dynamic count/index |   ~16.3 ns |           0 |     ~126 ns |           0 |
| Dynamic callback    |     ~66 ns |    2 / 24 B |     ~190 ns |    2 / 24 B |
| Dynamic `iter.Seq`  |    ~112 ns |    4 / 56 B |     ~261 ns |    4 / 56 B |

When the compiler could see the concrete receiver:

| Traversal            | 8 children | Allocations | 64 children | Allocations |
| -------------------- | ---------: | ----------: | ----------: | ----------: |
| Concrete count/index |      ~6 ns |           0 |      ~39 ns |           0 |
| Concrete callback    |      ~9 ns |           0 |     ~105 ns |           0 |
| Concrete `iter.Seq`  |    ~7.5 ns |           0 |     ~100 ns |           0 |
| Direct slice range   |      ~4 ns |           0 |      ~23 ns |           0 |

What this shows:

* `iter.Seq` is not intrinsically allocating.
* Dynamic-interface iterator closures can escape in the current compiler.
* Count/index currently gives a robust zero-allocation dynamic path.
* direct concrete arrays remain substantially faster than any generic boundary;
* compilation should ultimately lower to arrays rather than execute through any of these structural interfaces.

What it does **not** show:

* Go 1.27 will produce the same code;
* count/index is universally faster;
* real node definitions have the same cost profile;
* compilation time dominates runtime;
* a callback SPI is unacceptable.

## 14.5 Recommendation

Use count/index for the finite immutable compilation SPI:

```go
BT_ChildCount()
BT_Child(index)
```

Use `iter.Seq` for ergonomic inspection:

```go
func Children(d Definition) iter.Seq[Definition]
func Walk(d Definition) iter.Seq[Definition]
```

This recommendation rests primarily on:

* stable finite structure;
* replayability;
* random access;
* exact arity;
* current dynamic-dispatch behavior.

It does **not** rest on a claim that Go iterators inherently allocate or cannot build compact trees.

Native registered lowerers should bypass most generic structural overhead anyway.

# 15. Event-driven scheduling and linearization are separate optimizations

These were partially conflated in the inspirational analysis and in my previous response.

## Event-driven scheduling removes work

It changes:

```text
tick every condition every frame
```

into:

```text
reevaluate only observers affected by changed inputs,
plus explicitly periodic or next-frame behaviors
```

Unreal describes its behavior trees as event-driven specifically to avoid unnecessary per-frame work and uses observer aborts to react to blackboard changes. ([Epic Games Developers][12])

## Linearization makes remaining work cheaper

It changes:

```text
closure / pointer graph / linked children
```

into:

```text
dense node records
contiguous child edges
indexed per-instance state
bitsets
reverse dependency tables
```

Linearization improves:

* locality;
* memory footprint;
* state lookup;
* subtree interval operations;
* batching;
* serialization of structural data.

It does not itself reduce the number of logical conditions evaluated.

## Correct hybrid

```text
changed facts / timers / futures / external ticks
                    │
             dependency index
                    │
               ready queue
                    │
          compact Program arrays
                    │
         per-agent Instance state
```

An opaque legacy node receives compatibility ticks because its dependencies are unknown.

A native rich node may become quiescent until:

* a declared variable changes;
* a timer expires;
* a future completes;
* the next simulation frame arrives;
* an external event occurs.

# 16. The deactivation problem: semantic requirement, API still provisional

My prior phrase “`BT_Halt` is mandatory” fixed an API before the execution model was sufficiently analyzed.

The actual semantic problem is real.

Suppose a reactive fallback is:

```text
Fallback
├── EmergencyCondition
│   └── EmergencyAction
└── Navigate
```

`Navigate` returns `Running`.

On the next decision:

```text
EmergencyCondition becomes true
```

The runtime selects `EmergencyAction` and no longer ticks `Navigate`.

If navigation represents an external process, merely ceasing to poll it does not necessarily:

* cancel the navigation command;
* release resources;
* invalidate its callback;
* reset local activation state;
* prevent a late completion from mutating the world.

The current `go-pabt` documentation similarly warns that a running action’s eventual status or error is not guaranteed to be consumed. ([GitHub][1])

BehaviorTree.CPP uses an explicit `halt()` convention for asynchronous actions and expects such actions to stop promptly when halted. Unreal has an explicit abort lifecycle for in-progress tasks. ([behaviortree.dev][16])

## 16.1 What should be normative now

The semantic contract should state:

> When an occurrence that was active and returned `Running` ceases to be selected, the runtime must transition that activation into a deactivated state. Any cancelable external work must receive a cancellation/deactivation signal, and completions belonging to the previous activation must not affect a later activation.

## 16.2 What should remain unsettled

The signal may ultimately be represented as:

### Optional callback

```go
type Aborter interface {
    BT_Abort(AbortContext) error
}
```

### Activation-context cancellation

```go
ctx.Done()
```

where every activation receives a distinct context.

### Streaming state-machine signal

```go
Signal{
    Kind: SignalAbort,
    Activation: id,
}
```

### Runtime destruction of disposable behavior state

Appropriate only when no external work or resource needs cancellation.

The forthcoming streaming/linearized execution analysis should determine which mechanism is primary.

`BT_Halt` should therefore not yet be frozen into the required `Behavior` interface.

# 17. Abort, shutdown, and close must remain distinct

You are correct that a proposed `BT_Close(context.Context)` would misuse established Go lifecycle vocabulary.

## Activation abort

Scope:

```text
one activation of one behavior occurrence
```

Properties:

* may happen repeatedly over the object’s lifetime;
* does not destroy the behavior;
* may allow later reactivation;
* should invalidate stale completion;
* often initiates cancellation but should not block indefinitely.

Possible future name:

```go
BT_Abort
```

## Graceful runtime shutdown

Scope:

```text
entire Instance, scheduler, or execution service
```

Conventional shape:

```go
type Shutdowner interface {
    Shutdown(context.Context) error
}
```

Meaning:

* stop accepting or starting new work;
* request active work to finish or cancel;
* wait for quiescence;
* return the context error if the deadline expires;
* generally make the runtime non-reusable.

That follows the established `http.Server.Shutdown` pattern: stop new activity, wait for active work, and respect context expiry. ([Go Packages][17])

## Resource close

Standard shape:

```go
io.Closer
```

Meaning:

```go
Close() error
```

The standard interface intentionally says little beyond closure, and behavior after the first call is undefined unless the implementation documents it. ([Go Packages][18])

A likely `Instance` surface is:

```go
func (i *Instance) Shutdown(context.Context) error
func (i *Instance) Close() error
```

An optional custom behavior may itself implement `io.Closer` where it owns resources.

Neither operation substitutes for per-activation abort.

# 19. Go 1.27 generic methods: precise role

Go 1.27 is still unreleased as of July 12, 2026. Its draft release notes say concrete methods may declare their own type parameters, while interface methods may not declare type parameters and generic methods cannot implement interface methods. ([Go][19])

Therefore these are suitable:

```go
func (c *Compiler) Register[T Definition](
    lower func(*Lowering, T) error,
) error
```

```go
func (d Data) Get[T any](
    key Key[T],
) (T, bool)
```

```go
func (b *Builder) Add[C any](
    typ Type[C],
    config C,
    children ...Ref,
) (Ref, error)
```

These are not legal:

```go
type Definition interface {
    BT_Get[T any](Key[T]) (T, bool)
}
```

Nor can a generic concrete method satisfy a non-generic interface method through some generalized matching rule.

The compatibility interfaces must therefore remain non-generic.

Typed operations should live on concrete:

* `Compiler`;
* `Builder`;
* `Data`;
* `Registry`;
* `Views`;
* `Overlay`.

This is also architecturally desirable: generics provide typed authoring and registration, while compiled hot paths use dense IDs and arrays rather than repeatedly invoking generic maps.

Possible standard keys or optional capabilities include:

```go
type StableProvider interface {
    BT_ID() StableID
}

type WakeProvider interface {
    BT_Wake() WakeSpec
}

type SymbolicProvider interface {
    BT_Symbolic() SymbolicModel
}

type FormalProvider interface {
    BT_Formal() FormalModel
}

type CodecProvider interface {
    BT_Codec() Codec
}
```

Most future growth should occur through optional capability interfaces rather than adding methods to `Definition`.

Forward-compatible embedding protects source compatibility, but semantically meaningful defaults are dangerous. A new required method must not silently invent behavior.

# 21. Native lowering plus universal fallback

The compiler should have two paths.

## Native path

A registered lowerer recognizes a concrete type:

```go
compiler.Register(
    func(l *Lowering, n *Sequence) error {
        return l.Sequence(
            n.Memory,
            n.BT_ChildCount(),
        )
    },
)
```

It emits:

```text
opcode
flags
child span
payload index
state-slot description
metadata index
```

The hot runtime uses no node interface for that operation.

## Fallback path

For an unregistered definition:

```go
behavior, err := definition.BT_Bind(ctx)
```

The compiled program stores an opaque custom-behavior slot.

This yields the required trade-off:

| Property                             | Native definition      | Opaque definition        |
| ------------------------------------ | ---------------------- | ------------------------ |
| Generic interoperability             | Yes                    | Yes                      |
| Built-in interface dispatch per tick | No                     | Yes                      |
| Zero-allocation potential            | Strong                 | Implementation-dependent |
| Formal model                         | Standard or supplied   | Optional                 |
| Event scheduling                     | Compiled wake contract | Polling unless declared  |
| Serialization                        | Registered codec       | Not automatic            |
| Custom concrete methods              | Preserved              | Preserved                |

The closure design remains useful as the fallback implementation mechanism.

It ceases to be the sole structural and runtime representation.

# 22. Exact legacy compatibility

## Rich instance used by existing code

```go
legacyNode := instance.Node()
```

Physically, this can be one existing `Node` whose tick drives the compiled instance.

Conceptually, it exposes the rich tree through existing metadata:

```go
legacyNode = legacyNode.WithStructure(logicalStructure)
```

Existing:

* managers;
* tickers;
* decorators;
* walkers;
* one-shot-man integrations;
* PA-BT parents;

continue to see an ordinary `Node`. The current metadata API expressly supports conceptual structure differing from physical closure structure. ([GitHub][14])

## Legacy node used by the rich runtime

A legacy node is wrapped as an opaque definition.

The safe default is:

```go
func Opaque(
    factory func() Node,
    config OpaqueConfig,
) Definition
```

A factory is preferable to one shared `Node` because a closure may contain per-agent state.

By default:

```text
structure      opaque unless metadata supplied
execution      exact polling
dependencies   unknown
cancellation   unsupported unless adapter supplied
serialization  unsupported
formal model   opaque
sharing        not assumed
```

A user can opt into stronger capabilities by declaring:

* static structure;
* purity;
* wake dependencies;
* cancel function;
* formal abstraction;
* shareability.

The runtime must never silently stop ticking an arbitrary legacy closure merely because an optimization assumes it has no undeclared dependencies.

# 23. Planner-mode support should be optional semantics, not core BT methods

The recursive BT interface should not contain fields for every planner family.

Instead, planner modes consume richer views or attachments.

| Planner/execution mode     | Additional semantics required                                                                |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| Existing PA-BT             | None beyond the current `Node`; optional metadata                                            |
| BT Expansion               | finite symbolic states, exact action transition, complete action support, condition equality |
| OBTEA                      | BT Expansion model plus nonnegative costs and cost-labelled condition search                 |
| A*/GBFS                    | explicit search states, successors, costs, heuristic contract                                |
| UHBTP/HBTP                 | exact fallback plus heuristic/advisory ranking                                               |
| TAMP/PDDLStream            | resumable streams, certified facts, binding identity, revision dependencies                  |
| Belief BT                  | belief state, observation actions, outcome model, unknown truth                              |
| FOND                       | explicit nondeterministic outcomes and policy-state dispatch                                 |
| Temporal planning          | durations, invariants, temporal constraints, clock                                           |
| Causal parallelization     | read/write/resource sets and partial-order constraints                                       |
| Formal verification        | transition abstractions and finite analysis profile                                          |
| Game incremental execution | complete wake dependencies or polling fallback                                               |
| Multi-agent planning       | agent identity, intention/resource model, communication semantics                            |

The core runtime need only know how to execute a compiled operation or invoke an opaque behavior.

Planner-specific engines should access typed semantic views during planning and compilation. They should not make ordinary game BT nodes pay for unused symbolic fields.

# 24. What should remain unchanged in `go-pabt`

No redesign is required for the existing module.

Its API is compact and appropriate for its published algorithm:

```go
State.Variable
State.Actions
Condition.Match
Action.Conditions
Action.Effects
Action.Node
Plan.Node
Plan.Running
```

Its editable linked structure supports the algorithm’s subtree insertion and conflict relocation. Its assumptions should be documented clearly, but its compatibility should be preserved. ([GitHub][1])

The rich runtime can integrate it in two ways:

### Exact subtree

```text
go-pabt Plan.Node()
        ↓
opaque legacy Definition
        ↓
compiled Instance
```

### Conceptual inspection

Expose the planner’s logical structure through `Metadata`, should `go-pabt` later choose to attach it without changing execution behavior.

Other planner engines—BT Expansion, OBTEA, belief planners, temporal planners—can use the new rich semantic layer without being forced into `go-pabt.State`.

That is additive coexistence, not replacement.

# 25. Revised decision table

| Earlier claim                                     | Corrected conclusion                                                                                                                                     |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Match` prevents BT Expansion                     | It does not prevent a constrained implementation; it does not certify the exact finite transition semantics required by the theorem                      |
| `Match` prevents OBTEA                            | It does not prevent an extension; base API lacks cost, transition algebra, and condition-set identity                                                    |
| `Match` prevents admissible heuristics            | Incorrect; heuristic search can be entirely external. Base API simply has no standardized cost/lower-bound contract                                      |
| `Match` prevents effect indexing                  | Incorrect; `State.Actions` can implement arbitrary indexing. Base API prevents generic automatic semantic indexing beyond key buckets                    |
| `Match` prevents canonical closed sets            | Too strong; concrete types can supply identity. Base API provides no generic semantic equality                                                           |
| Conflict resolution is unprincipled               | Too strong; it is principled under a unary exact-assignment model and insufficient outside it                                                            |
| Formal verification is prevented                  | Incorrect; manual abstraction is possible. Automatic faithful extraction is not supported                                                                |
| `State.Actions` lacks completeness                | Incorrect for PA-BT: “all viable actions” is an implicit synchronous completeness contract                                                               |
| `State.Actions` is a universal grounder           | Incorrect: it cannot represent lazy, infinite, advisory, budgeted, or certified enumeration without hidden conventions                                   |
| Immutable world snapshot is universally mandatory | Incorrect; coherent semantic revision is required for classical-state claims. Snapshotting is one implementation                                         |
| Immutable program is mathematically mandatory     | Incorrect; it is a strong sharing, concurrency, and performance architecture                                                                             |
| `BT_Halt` must be the API                         | Premature; deactivation is semantically required for running external work, but callback versus context cancellation versus streamed signal remains open |
| Long cleanup belongs in `BT_Close(ctx)`           | Incorrect; use activation abort, graceful `Shutdown(ctx)`, and `io.Closer` as distinct concepts                                                          |
| Multiple new modules are required                 | Rejected; all new rich facilities belong additively in the existing `go-behaviortree` module                                                             |

# 26. Defensible current recommendation

The design that now survives the re-audit is:

1. Preserve the existing `Node` and `Tick` ABI unchanged.
2. Preserve `go-pabt` unchanged.
3. Add an optional recursively structured `Definition` interface with `BT_`-namespaced methods and forward-compatible embedding.
4. Treat the definition as a finite, immutable compilation input, not the hot execution object.
5. Use `BT_ChildCount` and `BT_Child` as the compilation SPI, while retaining `iter.Seq` for inspection.
6. Document that count/index is a trade-off—not an intrinsic superiority theorem.
7. Compile recognized definitions into a shared dense `Program`.
8. Store mutable state in a per-agent `Instance`.
9. Expose each instance as one ordinary existing `Node`.
10. Wrap arbitrary legacy nodes as exact, opaque polling islands.
11. Enable event-driven skipping only where a complete wake/dependency contract exists.
12. Keep exact polling as the compatibility baseline.
13. Represent planner semantics through optional typed data and capabilities, not through the recursive core interface.
14. Use Go 1.27 generic methods on concrete registries, builders, and data containers—not interfaces.
15. Separate per-activation abort from instance `Shutdown(context.Context)` and `Close()`.
16. Leave the exact activation/deactivation method unresolved until the streaming and allocation-linearization model has been worked through.
17. Require richer planner engines to state the assumptions under which they claim completeness, optimality, grounding coverage, or verification.
18. Do not infer those claims merely from an algorithm’s name or from the presence of callback methods.

The most important corrected principle is:

> **Opaque Go behavior is maximally implementation-flexible but minimally self-describing. The additive API should preserve that flexibility while allowing nodes that choose to provide declarative structure, dependencies, planner models, and formal abstractions to be compiled and reasoned about much more powerfully.**

That gives the legacy API exact continuity, PA-BT complete continuity, game-scale event scheduling, dense compiled execution, and a technically honest path to complete, optimal, belief-aware, temporal, task-and-motion, multi-agent, and formally verified planning.
