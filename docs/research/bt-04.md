# Deep technical autopsy of the actual pick-and-place example

## Scope and an important correction

The full example materially changes one point from my earlier analysis:

> **The complete script does synchronize held-item state.**

`syncToBlackboard()` publishes `heldItemExists` and `heldItemId`, in addition to actor position and geometric facts. The documentation excerpt omits this machinery because it is a partial presentation; it should therefore be labelled as non-self-contained, but the corresponding defect does **not** exist in the full script. ([GitHub][1])

The full program nevertheless exposes more consequential issues than the excerpt did. In particular, it shows that this is not merely a PA-BT example. It is a compact hybrid of:

1. symbolic backward planning through PA-BT;
2. grid-based motion planning through A*;
3. a bespoke reachability and obstacle-selection oracle;
4. a rudimentary movable-obstacle manipulation planner;
5. a concurrent JavaScript/Go execution and observation system;
6. a terminal UI whose dimensions currently leak into world semantics.

The most valuable reframing is therefore:

> **This is an embryonic task-and-motion planner for Navigation Among Movable Obstacles, with a PA-BT execution layer—not merely a behavior-tree tutorial.**

That interpretation identifies much higher-value improvements than local API polishing.

I inspected the current script and relevant planner/runtime sources and performed a deterministic source-level replay of the default map and pathfinding code. I did not execute the `osm` binary, so the operation counts below are algorithmic replay results rather than wall-clock benchmarks.

---

# 1. What the example actually implements

The initial world contains:

* an actor at approximately `(5, 11)`;
* a target cube at `(45, 11)`;
* a 3×3 goal region centered at `(8, 18)`;
* a one-cell-thick 5×5 perimeter of sixteen movable blockers around that goal;
* a walled room containing the target, with a gap in its left wall;
* one additional movable obstacle;
* a fixed `80×24` spatial index;
* a nominal play-area width of `55`;
* mutable terminal `width` and `height` fields. ([GitHub][1])

At the symbolic layer, the final goal is:

```text
cubeDeliveredAtGoal == true
```

The broad intended causal chain is:

```text
Deliver target
    requires holding target
    requires being near goal

Pick target
    requires empty hand
    requires path to goal clear
    requires being near target

Clear goal path
    requires picking a selected blockade cube
    requires depositing that cube elsewhere

Move near object/goal
    requires its path-blocker state to be clear
```

The script dynamically generates grounded movement, blocker-pick, and blocker-deposit actions from failed condition keys such as:

```text
atEntity_107
atGoal_1
pathBlocker_goal_1
heldItemId
```

Static actions implement target picking, target delivery, and generic placement. ([GitHub][2])

Geometrically, the script computes one flood fill from the actor whenever `gridDirty` is true. It classifies a destination as:

* `-1`: a cell in its 3×3 neighbourhood is reachable;
* `-2`: unreachable with no frontier;
* a positive object ID: the frontier obstacle nearest the destination by Manhattan distance. ([GitHub][1])

For movement, the action runs a bounded A* search to the exact destination on every invocation, pops one grid step, moves the actor one cell, marks the geometry dirty, and returns `Running`. ([GitHub][2])

This architecture is clever enough to solve the deliberately constructed default map. Its fragility appears when one asks whether its symbolic facts are true, whether its obstacle choice is causally justified, whether execution is transactionally observed, and whether it can generalize to maps not designed around its heuristic.

# 2. A source-level replay of the default solution

The initial flood fill visits the free component containing the actor. Its nearest frontier obstacle to the goal is blocker `107`, located at `(6, 18)`. There are four equally close ring cells, but the flood-fill queue and direction order encounter `107` first.

The resulting nominal strategy is:

```text
Move near blocker 107
Pick blocker 107
Deposit blocker 107 to the left of the actor
Move to the target
Pick the target
Move through the opened ring
Deliver the target
```

I reproduced the script’s custom heap behavior, direction ordering, search bounds, interaction threshold, map construction, and “one path step per new A* search” behavior. The resulting search work is:

| Movement leg              | Movement steps | A* invocations | Expanded A* nodes |
| ------------------------- | -------------: | -------------: | ----------------: |
| Actor → blocker `107`     |              6 |              6 |                48 |
| Blocker location → target |             45 |             45 |             1,543 |
| Target → goal             |             48 |             48 |             9,793 |
| **Total**                 |         **99** |         **99** |        **11,384** |

If the program computes one path per unchanged-occupancy movement leg and consumes that path until the occupancy revision changes, the corresponding work is approximately:

| Movement leg              | A* invocations | Expanded nodes |
| ------------------------- | -------------: | -------------: |
| Actor → blocker `107`     |              1 |             13 |
| Blocker location → target |              1 |            128 |
| Target → goal             |              1 |            409 |
| **Total**                 |          **3** |        **550** |

For the default map, this is:

[
\frac{99}{3}=33\times
]

fewer A* invocations and:

[
\frac{11{,}384}{550}\approx20.7\times
]

fewer A* node expansions.

These figures are not speculative big-O claims; they are a replay of the current source algorithm on the current default geometry. They are not wall-clock speedups because bridge, BT, rendering, allocation, and scheduler costs were not measured. The source nevertheless makes the cause unambiguous: every movement step discards a still-valid route and solves almost the same search problem again. ([GitHub][2])

The initial flood fill itself visits approximately 1,065 reachable cells. It records 178 frontier entries representing only 92 unique blocked cells because blocked frontier cells are deliberately not added to a frontier-seen set. Since every actor movement marks `gridDirty`, normal scheduling causes roughly one whole-map reachability pass per movement step: more than 100,000 visited cells and about 400,000 neighbour examinations over the default solution, before counting subsequent derived-condition iteration. ([GitHub][1])

This is the first immediate, measurable material benefit:

> **Route persistence plus correct cache invalidation can remove approximately 95% of geometric search work in the default scenario without changing the planning algorithm at all.**

# 3. Highest-value defect: presentation dimensions alter world physics

The world currently has at least four competing coordinate extents:

```text
ENV_WIDTH     = 80
ENV_HEIGHT    = 24
spaceWidth    = 55
state.width   = current terminal width
state.height  = current terminal height
```

`FlatSpatialIndex` is permanently allocated as `80×24`, but a `WindowSize` event overwrites `state.width` and `state.height`. The flood fill forms visited keys as:

```javascript
y * state.width + x
```

and bounds its vertical exploration using `state.height`. A* uses `spaceWidth` for keys but still uses mutable `state.height` for vertical bounds. The UI resize handler does not mark geometry dirty. ([GitHub][1])

This creates several concrete failure modes.

## 3.1 Key aliasing in a narrow terminal

Suppose the terminal width becomes `40`. Then:

```text
key(41, y) = 40y + 41
key(1, y+1) = 40y + 41
```

Two distinct world cells have the same visited key.

Because the logical x-range extends above 40, flood-fill reachability can:

* suppress exploration of a cell as “already visited”;
* falsely connect or disconnect regions;
* choose a different blocker;
* produce resize-dependent plans.

This is not cosmetic. Terminal width changes the graph on which reachability is computed.

## 3.2 Phantom free space in a tall terminal

If terminal height grows above 24, the movement and reachability functions allow y-coordinates beyond the physical spatial index. `FlatSpatialIndex.get()` returns `undefined` outside its fixed bounds, which the pathfinding code interprets as empty space.

The agent can therefore plan through or even move into rows that:

* have no occupancy representation;
* were not part of the initialized world;
* cannot contain indexed obstacles;
* exist solely because the terminal is tall.

## 3.3 Artificially unreachable goals in a short terminal

The goal is centered at y=18. A sufficiently short terminal makes that position outside the movement bounds, regardless of the actual world model. Resizing the display can turn a solvable planning problem into an unsolvable one.

## 3.4 Delayed semantic change

`WindowSize` updates the dimensions but does not set `gridDirty`. Existing path-blocker facts continue reflecting the old coordinate system until some later movement or spatial change invalidates the cache. The planner can therefore operate temporarily with a mixture of:

```text
new UI dimensions
old reachability facts
fixed spatial-grid dimensions
```

## 3.5 There is also a horizontal off-by-model inconsistency

The room is constructed through x=55, while `spaceWidth` is 55 and navigation rejects x values at or above `spaceWidth - 1`, namely x≥54. The right wall at x=55 therefore sits outside the effective navigation domain. The actor is bounded by an implicit edge at x=54 rather than by the modeled wall.

## Required fix

Separate immutable world geometry from presentation state:

```typescript
interface LogicalWorldBounds {
  readonly width: 80;
  readonly height: 24;
  readonly navigableMinX: 1;
  readonly navigableMaxX: 53;
  readonly navigableMinY: 1;
  readonly navigableMaxY: 22;
}

interface Viewport {
  terminalWidth: number;
  terminalHeight: number;
  horizontalOffset: number;
}
```

Every world-coordinate key must use the logical grid width:

```typescript
function cellIndex(cell: Cell, bounds: LogicalWorldBounds): number {
  return cell.y * bounds.width + cell.x;
}
```

Rendering alone should consume the viewport.

## Material benefit

This change delivers much more than cleaner code:

* identical planning under all terminal sizes;
* reproducible simulations and tests;
* correct headless operation;
* stable cache keys;
* deterministic incident replay;
* elimination of phantom or aliased map cells;
* a prerequisite for comparing planner algorithms fairly.

A high-value invariant should be tested:

```text
For any two viewport sizes V1 and V2:
    planTrace(world, V1) == planTrace(world, V2)
```

This is a low-effort, very-high-value correction.

# 4. The blackboard is thread-safe but not a coherent observation

The full example synchronizes the right variables, but does so through a sequence of independent calls:

```javascript
syncValue(state, 'actorX', actor.x);
syncValue(state, 'actorY', actor.y);
syncValue(state, 'heldItemExists', actor.heldItem !== null);
syncValue(state, 'heldItemId', ...);
...
syncValue(state, 'pathBlocker_goal_1', blocker);
```

Each blackboard operation has its own mutex. That prevents memory races on one map operation, but does not make a group of facts atomic. `Snapshot()` is only a shallow copy and is not being used as the planner’s immutable tick input. ([GitHub][1])

A planner tick can observe combinations that never existed in the simulated world. For example, a pick action writes:

```text
heldItemId = 107
heldItemExists = true
```

in separate operations. Between them, the blackboard can contain:

```text
heldItemId = 107
heldItemExists = false
```

Conversely, the general synchronization path writes existence before ID, creating the opposite transient inconsistency.

A deposit action writes:

```text
heldItemExists = false
heldItemId = -1
pathBlocker_goal_1 = -1
```

sequentially. A plan tick can therefore observe an empty hand but the old blocker fact, or a clear path while still seeing the object as held.

This problem becomes more serious because the UI update loop and the behavior-tree ticker are separate clocks:

```text
UI/update synchronization: roughly 16 ms command cycle
PA-BT ticker:              100 ms
```

The ticker reads Go blackboard state while JavaScript publishes fields individually. ([GitHub][2])

## Required fix: immutable versioned world snapshots

Replace mutable per-key publication with an atomic commit:

```typescript
interface WorldSnapshot {
  readonly revision: bigint;
  readonly observedAt: number;

  readonly actorPose: ReadonlyMap<ActorId, Cell>;
  readonly holding: ReadonlyMap<ActorId, ObjectId | null>;
  readonly objectLocation: ReadonlyMap<ObjectId, ObjectLocation>;

  readonly occupancyRevision: bigint;
  readonly topologyRevision: bigint;

  readonly observations: ReadonlyMap<FactId, ObservationMetadata>;
}
```

Synchronization becomes:

```typescript
const frame = world.beginFrame();

frame.setActorPose(actorId, actor.position);
frame.setHolding(actorId, actor.heldItem?.id ?? null);
frame.setObjectLocations(objects);
frame.setOccupancy(occupancy);

world.commit(frame); // one publication, one revision
```

Every planner tick receives exactly one snapshot reference and retains it throughout evaluation:

```typescript
const snapshot = world.currentSnapshot();
plan.tick(snapshot);
```

Derived conditions are computed against that revision:

```typescript
reachable(destination, snapshot.occupancyRevision)
near(actor, object, snapshot.revision)
```

## Material benefit

Atomic snapshots provide:

* elimination of torn symbolic states;
* deterministic replay;
* reliable effect verification;
* unambiguous cache invalidation;
* meaningful planner traces;
* easier concurrency reasoning;
* safe migration from simulation to asynchronous sensors or services.

This is foundational. Cost-optimal planning over an incoherent state is still incoherent planning.

# 5. Pause currently pauses the UI loop, not the autonomous agent

The pause flag causes the UI `Tick` handler to return before synchronization and tick-count increment. It does **not** stop the independently created PA-BT ticker. Action leaves check `gameMode`, but they do not check `state.paused`. ([GitHub][2])

Consequently, while the display says:

```text
*** PAUSED ***
```

the autonomous planner can continue to:

* move the actor;
* pick objects;
* place objects;
* deliver the target;
* mutate the spatial grid.

At the same time, `syncToBlackboard()` is no longer being called by the paused UI cycle. The planner can continue acting against stale geometric observations.

This interacts especially badly with the speculative path-clear write discussed below. A deposit can assert:

```text
pathBlocker_goal_1 = -1
```

and, while paused, no geometric refresh need correct it.

## Required fix

There should be one authoritative simulation clock, or pause must explicitly suspend all relevant schedulers:

```typescript
interface SimulationClock {
  pause(): void;
  resume(): void;
  isPaused(): boolean;
}
```

At minimum:

```typescript
if (state.paused) {
  return bt.running; // without any mutation
}
```

must guard every executor, and the PA-BT ticker should itself stop or block.

Required temporal invariant:

[
G(\text{paused}\rightarrow X(\text{worldRevision}
=================================================

\text{worldRevision}_{current}))
]

In words: while paused, the next state must not contain a world mutation.

## Material benefit

This fixes:

* invisible autonomous progress;
* nondeterministic debugging;
* stale-sensor execution;
* test flakiness;
* user-control violations.

It is another inexpensive, high-impact correction.

# 6. The “truthful effects” contract is violated by path clearing

The script’s header says that actions must report success only after the physical state changed and describes effects as truthful. ([GitHub][2])

The blocker-deposit action does physically place the blocker, but then it directly writes:

```javascript
syncValue(
  state,
  'pathBlocker_' + destinationKey,
  -1
);
```

before recomputing reachability.

Its placement procedure merely:

1. derives a vector from the actor toward the destination;
2. prefers one of the cells in the opposite direction;
3. selects the first unoccupied adjacent cell;
4. places the object there;
5. declares the destination path clear. ([GitHub][2])

“Placed away from the target” does not logically imply:

```text
a traversable route now exists
```

It happens to work for the default one-cell ring because moving the left ring cell outward opens a one-cell entrance. It fails for ordinary variants such as:

* a two-cell-thick ring;
* two blockers in series;
* a blocker moved into another necessary corridor;
* a static wall behind the selected movable blocker;
* a narrow passage where the deposited object blocks the actor’s return;
* another object occupying the only viable approach direction;
* a target requiring a different interaction radius or robot footprint.

The code does mark geometry dirty through the spatial-grid update, so a later synchronization may correct the assertion. But between action completion and that recomputation, the planner-visible state can contain a fact the geometry has never certified.

## Correct semantic split

A placement action may truthfully guarantee:

```text
Holding(actor) := None
Location(blocker) := Cell(x, y)
```

It cannot guarantee `PathClear(destination)` unless a geometric procedure proves that relation.

Thus:

```typescript
interface PlaceEffects {
  guaranteed: {
    holding: null;
    objectLocation: Cell;
  };

  // Not a logical effect:
  predictedConsequences?: {
    destinationLikelyReachable: number;
  };
}
```

`PathClear` should be a derived, revision-bound certificate:

```typescript
interface ReachabilityCertificate {
  start: Cell;
  destinationRegion: Region;
  occupancyRevision: bigint;
  trajectory: readonly Cell[];
  clearance: number;
}
```

The action should not succeed at the planner level until a fresh snapshot verifies its guaranteed effects and, where necessary, a geometry stream certifies the next precondition.

## Correct execution protocol

```text
Place command dispatched
        ↓
controller completes
        ↓
new occupancy snapshot committed
        ↓
placement effect verified
        ↓
reachability recomputed/certified
        ↓
action or macro completes
```

A suitable state machine is:

```text
Created
  → Dispatched
  → Running
  → ControllerCompleted
  → AwaitingObservation
  → Verified
  → Success
```

With typed failure states:

```text
Rejected
TimedOut
Cancelled
ControllerFailed
VerificationFailed
ModelViolation
ObservationError
```

The central invariant is:

[
\text{PlanSuccess}
\Rightarrow
\text{GoalSatisfiedInFreshCommittedSnapshot}
]

## Material benefit

Verified effects eliminate:

* phantom plan success;
* execution on guessed geometry;
* repeat loops caused by wrong action models;
* misleading planner traces;
* unsafe transfer of the example’s semantics to real robots, games, services, or distributed workflows.

This is one of the highest-value strategic improvements because it converts “the node returned Success” from a control-flow event into defensible evidence about the world.

# 7. The current obstacle selector is not actually a path-clearing planner

The flood-fill procedure computes the actor’s current connected free-space component. If the destination is outside that component, it returns the frontier obstacle with minimum Manhattan distance to the destination. ([GitHub][1])

That answers:

> Which observed boundary obstacle is geometrically closest to the destination?

It does **not** answer:

> Which movable obstacle or set of obstacles should be manipulated to create a feasible low-cost route?

Those are very different questions.

## 7.1 It may select a static wall

Every cube with ID≥100 receives blocker-related facts, including wall objects with IDs starting at 1000. The generator then creates a pick action for the returned object. The pick action subsequently rejects static objects. ([GitHub][1])

In a map where the frontier wall nearest the destination is static but a movable “door” farther from the destination would open a route, the planner repeatedly identifies the static wall and never represents the viable alternative.

## 7.2 It represents only one blocker

A positive `pathBlocker` value contains one object ID. It cannot express:

```text
either move A or B
move both A and B
move A, then choose between C and D
no movable-obstacle solution exists
```

A two-layer blockade cannot be reasoned about as a condition set. At best, the system may discover the second layer after moving the first, but because deposit prematurely declares the path clear, the symbolic reasoning between those actions is unsound.

## 7.3 “Closest to destination” is not causal relevance

A frontier obstacle can be close to the destination but unrelated to every feasible path from the actor. It can belong to:

* a cul-de-sac;
* the wrong side of a disconnected enclosure;
* a static boundary;
* a component the actor cannot manipulate from its current side.

## 7.4 Frontier duplicates add bias and work

Blocked cells are intentionally not added to `visited`, so the same obstacle can be inserted from several adjacent reachable cells. The default initial flood produces 178 frontier records for 92 unique occupied frontier cells.

This does not change the minimum distance itself, but it:

* increases work and memory;
* makes ordering more dependent on traversal details;
* complicates candidate diversity;
* obscures how many distinct obstacle choices exist.

A separate `frontierSeen` set is an easy local fix, but the deeper problem is the objective being optimized.

# 8. Directly applicable research: NAMO, MCR and MCD

The example is a discrete instance of **Navigation Among Movable Obstacles**. NAMO explicitly models a robot that may reconfigure its environment by moving obstacles to open navigable space. The foundational work distinguishes fixed and movable obstacles and constructs plans interleaving navigation, grasping, and obstacle movement. It also shows why exploiting navigation structure is preferable to naively searching the full joint configuration space. ([Georgia Tech Repository][3])

The **Minimum Constraint Removal** formulation asks for the smallest set of constraints or obstacles whose removal admits a path. It was explicitly motivated, among other uses, by identifying which movable obstacles a robot must manipulate. ([Intelligent Motion Laboratory][4])

The **Minimum Constraint Displacement** formulation goes further: rather than treating every moved obstacle equally, it minimizes how far constraints must be displaced, jointly with path-related costs. ([Robotics Proceedings][5])

These are not merely analogous papers. Their objective functions can be transplanted directly into this grid domain.

## 8.1 A discrete minimum-removal search

Label every blocked cell by its object ID. Search over:

```text
(cell, removalSet)
```

Entering a free cell has cost:

```text
(0 additional manipulations, 1 travel step)
```

Crossing a movable obstacle’s cell adds its label to `removalSet`. A static obstacle is forbidden.

A lexicographic objective is suitable:

[
J =
\left(
|\mathcal{R}|,
\sum_{o\in\mathcal{R}} d_o,
L,
\rho
\right)
]

where:

* (\mathcal{R}) is the set of objects to move;
* (d_o) is predicted displacement or manipulation effort;
* (L) is robot travel length;
* (\rho) is risk or uncertainty.

Lexicographic ordering can prioritize:

1. minimum number of pick/place cycles;
2. minimum total obstacle displacement;
3. minimum robot travel;
4. minimum risk.

For a small 55×24 grid and sixteen movable ring objects, an exact or strongly bounded search is practical.

A dominance rule controls state growth:

```text
At the same cell:

(removalSet A, cost A) dominates (removalSet B, cost B)

when:
    A ⊆ B
and cost(A) ≤ cost(B)
```

The output should be:

```typescript
interface CorridorPlan {
  blockerSet: ReadonlySet<ObjectId>;
  nominalRoute: readonly Cell[];
  staticBlockers: ReadonlySet<ObjectId>;
  lowerBound: CostVector;
}
```

## 8.2 Placement must be part of the same reasoning problem

Removing a blocker is not enough; it must be deposited somewhere that preserves the required corridor.

Generate candidate placement cells and reject any that fail:

```text
Free(candidate)
ReachableManipulationPose(candidate)
Stable(candidate)
DoesNotBlockRequiredCorridor(candidate)
DoesNotTrapActor(candidate)
DoesNotBlockFutureTargetRoute(candidate)
```

For this grid example, candidate placements can be exhaustively tested in a local radius. For a physical robot, they become geometry and kinematics samplers.

## Material benefits

A real MCR/NAMO treatment would provide:

* correct handling of multiple blockers;
* explicit rejection of static obstacles;
* lower manipulation count;
* lower cycle time;
* lower energy usage;
* lower actuator and gripper wear;
* fewer opportunities for manipulation failure;
* less obstacle displacement;
* prevention of re-blocking;
* explanations such as “objects 107 and 113 jointly disconnect the goal”;
* principled unsolvability reports.

This has substantially more material worth than making the current “nearest frontier” heuristic marginally faster.

# 9. The right abstraction is task-and-motion planning with certified streams

The original PA-BT formulation already describes `MoveTo` as requiring a collision-free trajectory, not merely a Boolean guess that a path has no blocker. Pick and place are similarly parameterized by grounded objects and poses. ([ar5iv][6])

The actual script has all the ingredients of a task-and-motion planner:

```text
Task layer:
    Deliver
    Pick
    Place
    Clear path

Motion/geometric layer:
    findPathManual
    computeReachabilityMap
    getFreeAdjacentCell
    object and wall geometry
```

What it lacks is a formal interface between the two.

PDDLStream is directly relevant because it lets symbolic planning use black-box geometric procedures that generate values and certify declarative facts. It was designed for relationships such as collision, kinematics, object pose, and trajectory validity that are inappropriate to enumerate entirely in advance. ([arXiv][7])

## A directly applicable stream interface

```typescript
stream planPath(
  start: Cell,
  destination: Region,
  occupancyRevision: bigint
): Iterable<{
  trajectory: Trajectory;
  certifies: ValidTrajectory;
}>;

stream findRemovalSet(
  start: Cell,
  destination: Region,
  occupancyRevision: bigint
): Iterable<{
  blockers: ReadonlySet<ObjectId>;
  corridor: Corridor;
  certifies: CorridorPossibleAfterRemoving;
}>;

stream samplePlacement(
  object: ObjectId,
  requiredCorridor: Corridor,
  occupancyRevision: bigint
): Iterable<{
  pose: Cell;
  certifies: [
    Free,
    Stable,
    ReachablePlacement,
    PreservesCorridor
  ];
}>;
```

The corresponding action model becomes:

```typescript
Navigate(actor, destination, trajectory)
pre:
  ActorPose(actor) == trajectory.start
  ValidTrajectory(trajectory, occupancyRevision)
eff:
  ActorPose(actor) := trajectory.end

Pick(actor, object)
pre:
  Holding(actor) == None
  Movable(object)
  Near(actor, object)
eff:
  Holding(actor) := object
  Location(object) := HeldBy(actor)

Place(actor, object, pose)
pre:
  Holding(actor) == object
  ReachablePlacement(actor, object, pose)
  Stable(object, pose)
eff:
  Holding(actor) := None
  Location(object) := Cell(pose)
```

`PathClear` is then not an action effect. It follows from a certified trajectory or corridor under a particular occupancy revision.

## Material benefit

This separation creates:

* reusable symbolic actions independent of map size;
* replaceable A*, D*, sampling-based, or physical motion planners;
* explicit validity of geometric facts;
* lazy evaluation of expensive geometry;
* safe cache invalidation by occupancy revision;
* clean integration of robot footprint, clearance, kinematics, and collision checking;
* a migration path from terminal simulation to a real task-and-motion stack.

This is probably the single most strategically valuable reframing of the example.

# 10. The motion planner repeatedly solves an unchanged problem

`createMoveToAction()` does the following on every active invocation:

```text
compute exact A* route
take first step
discard the route
mark geometry dirty
return Running
```

The next invocation repeats the entire search from the adjacent cell. ([GitHub][2])

## Immediate correction: persist the route

```typescript
interface NavigateExecution {
  destination: Destination;
  occupancyRevision: bigint;
  trajectory: readonly Cell[];
  cursor: number;
}
```

Execution becomes:

```typescript
if (!execution ||
    execution.destination !== destination ||
    execution.occupancyRevision !== snapshot.occupancyRevision) {
  execution = computeTrajectory(snapshot, destination);
}

if (!nextCellIsStillValid(execution, snapshot)) {
  execution = computeTrajectory(snapshot, destination);
}

moveToward(execution.trajectory[execution.cursor++]);
return Running;
```

Actor motion should increment a `poseRevision`, not an `occupancyRevision`.

## The current dirty flag conflates two kinds of change

Every actor step sets `gridDirty`, even though static connectivity normally depends on occupied cells, not on which free cell the actor currently occupies.

Separate:

```text
poseRevision
occupancyRevision
topologyRevision
```

A new actor pose may require evaluating whether the current destination is still near, but it does not require rebuilding the entire free-space topology.

For an undirected grid with unchanged occupancy, all points in the actor’s current connected component remain mutually reachable. A single connected-component labeling can support many reachability queries.

## When D* Lite becomes worthwhile

D* Lite is designed to reuse search information across related path-planning problems as the robot moves and discovers cost changes, rather than solving each problem from scratch. ([AAAI][8])

For this particular default example:

* occupancy changes only when objects are picked or placed;
* the map is small;
* one persisted A* path per occupancy revision is probably the best first implementation.

D* Lite or Lifelong Planning A* becomes valuable when:

* obstacles move frequently;
* only small parts of the occupancy map change;
* navigation maps become large;
* rapid local replanning matters.

## Search-budget semantics also need repair

The current A* search has a 500-node budget. If the goal is not reached but some expanded node is heuristically closer, it returns a path to that partial node. The caller does not distinguish a complete route from budget-limited progress. ([GitHub][1])

Use:

```typescript
type PathResult =
  | {
      kind: "complete";
      trajectory: Trajectory;
      cost: number;
    }
  | {
      kind: "partial";
      trajectory: Trajectory;
      lowerBound: number;
      continuation: SearchState;
    }
  | {
      kind: "unreachable";
      certificate?: CutCertificate;
    }
  | {
      kind: "budget-exceeded";
      continuation: SearchState;
    };
```

Otherwise a local heuristic improvement can be mistaken for evidence that continued execution will reach the goal.

## Material benefit

Route persistence and revision separation deliver:

* approximately 33× fewer A* invocations in the supplied map;
* approximately 20.7× fewer node expansions in the source-level replay;
* much less full-map reachability work;
* smoother motion;
* lower bridge traffic;
* predictable action latency;
* scalability to larger grids.

This is the clearest immediate performance win.

# 11. Primary effects, derived facts and hidden interference

The action model currently mixes direct state variables and derived facts.

For example:

### Navigate

Declared effect:

```text
atEntity_1 = true
```

Actual primary change:

```text
ActorPose := new position
```

Derived changes potentially include:

```text
atEntity_N
atGoal_N
pathBlocker_entity_N
pathBlocker_goal_N
```

for many N.

### Pick

Declared effects:

```text
heldItemId = object
heldItemExists = true
```

Actual primary changes:

```text
Holding := object
Location(object) := Held
Occupancy := Occupancy \ object
```

Derived changes include:

```text
atEntity_object
every reachability/path-blocker fact affected by occupancy
```

### Deliver

Declared effect:

```text
cubeDeliveredAtGoal = true
```

Actual changes include:

```text
Holding := None
Location(target) := goal cell
Occupancy := Occupancy ∪ target
```

The core planner contract states that all relevant action effects should be mapped and that actions should not have unmodeled side effects. The current example plainly relies on relevant consequences that are not represented in each action’s effect set. ([GitHub][9])

This weakens conflict resolution. PA-BT detects interference by comparing action effects with conditions. If movement only declares one chosen `at...` Boolean, the planner cannot see that it invalidates other location conditions. If pick/place do not declare occupancy changes or their dependency closure, the planner cannot reason generally about their effects on reachability.

The special precondition on `Pick_Target`:

```text
pathBlocker_goal_1 == -1
```

is explicitly described in the script as necessary to prevent a planning livelock. That is useful domain knowledge, but it is also evidence that a local patch is compensating for missing causal and resource structure. ([GitHub][2])

## Correct model

Represent only canonical primary variables as writable:

```typescript
ActorPose(actor)
Holding(actor)
ObjectLocation(object)
OccupancyRevision
```

Register dependencies:

```text
Near(actor, object)
    depends on ActorPose(actor), ObjectLocation(object)

AtGoal(actor, goal)
    depends on ActorPose(actor)

Reachable(actor, destination)
    depends on ActorPose component, occupancy, destination

ValidTrajectory(...)
    depends on occupancy revision and endpoints
```

Action conflict analysis should use:

```typescript
readSet
writeSet
resourceClaims
invariants
derivedDependencyClosure
```

For example:

```typescript
Navigate:
  reads:  Occupancy, ActorPose
  writes: ActorPose
  resource: Base

Pick:
  reads:  ActorPose, ObjectLocation, Holding
  writes: ObjectLocation, Holding, Occupancy
  resource: Gripper

Place:
  reads:  ActorPose, Holding, Occupancy
  writes: ObjectLocation, Holding, Occupancy
  resource: Gripper
```

## Material benefit

This removes the need to manually enumerate and maintain many dependent Boolean effects. It enables:

* correct conflict detection;
* automatic invalidation;
* resource-aware scheduling;
* safe parallelism;
* fewer domain-specific livelock patches;
* much smaller and more coherent action models.

# 12. The world state permits illegal combinations

Several values encode the same fact independently:

```text
heldItemExists
heldItemId
actor.heldItem
cube.deleted
cube location
spatial-grid occupancy
```

This permits contradictory states such as:

```text
heldItemExists = false
heldItemId = 107
actor.heldItem = null
cube 107 deleted = true
```

The overloaded `deleted` flag is especially problematic. It can mean:

* physically held;
* removed from occupancy;
* nonexistent;
* temporarily hidden;
* already delivered, depending on context.

The path-blocker value also overloads status and witness:

```text
-1  = clear
-2  = unreachable
>0  = one alleged blocker ID
```

That cannot distinguish:

* unknown;
* stale;
* sensor error;
* statically unreachable;
* blocked by several objects;
* blocked by one movable object;
* blocked by one static object;
* geometrically reachable but action-infeasible.

## Replace redundant fields with finite-domain variables

```typescript
type ObjectLocation =
  | { kind: "cell"; cell: Cell }
  | { kind: "held"; actor: ActorId }
  | { kind: "delivered"; goal: GoalId }
  | { kind: "removed" };

type Reachability =
  | {
      kind: "reachable";
      certificate: ReachabilityCertificate;
    }
  | {
      kind: "blocked";
      movableCandidates: ReadonlySet<ObjectId>;
      staticConstraints: ReadonlySet<ObjectId>;
      cut?: CutCertificate;
    }
  | {
      kind: "unreachable";
      reason: string;
    }
  | {
      kind: "unknown";
      reason: string;
    }
  | {
      kind: "error";
      error: Error;
    };
```

Then:

```text
Holding(actor) = object
```

is derived from:

```text
Location(object) = HeldBy(actor)
```

or vice versa, but not separately mutable in two places.

## Material benefit

This prevents entire classes of bugs structurally rather than detecting them after the fact. It also makes serialization, replay, validation and planning substantially easier.

# 13. Object identity should not encode object type

The script uses numeric conventions:

```text
1       target
100+    movable blockade
803     additional movable obstacle
1000+   static wall
```

and conditions are encoded as strings:

```text
atEntity_107
pathBlocker_entity_107
pathBlocker_goal_1
```

The action generator performs prefix tests, string replacement and `parseInt`. ([GitHub][2])

This gives no type-level protection against:

* attempting to pick a wall;
* malformed keys;
* naming collisions;
* referring to missing objects;
* mixing goal and entity identifiers;
* accidental assumptions about ID ranges.

Use typed predicates:

```typescript
at(actorId, objectId)
near(actorId, objectId)
pathClear(actorId, destination)
holding(actorId)
movable(objectId)
```

or first-order terms:

```typescript
{
  predicate: "near",
  args: [actorId, objectId]
}
```

Then grounding becomes unification over declared domains rather than string parsing.

## Material benefit

Typed terms enable:

* action indexing by predicate;
* static model validation;
* safe schema refactoring;
* clearer traces;
* reusable parameterized actions;
* formal search algorithms;
* completeness checks over explicit object domains.

This is a prerequisite for obtaining meaningful guarantees from BT Expansion, OBTEA or a reference planner.

# 14. `match` conflates observation, entailment and conflict reasoning

The planner decides that an action is relevant when:

1. an effect has the same normalized key as a failed condition;
2. the failed condition’s `Match` function returns true when passed the effect value. ([GitHub][10])

The same matcher is therefore used for:

```text
Does the observed world value satisfy the condition?
```

and:

```text
Would the action's declared effect entail the condition?
```

Conflict reasoning needs a third operation:

```text
Would this effect contradict or preserve another condition?
```

An arbitrary JavaScript callback is not necessarily a sound implementation of all three. It might depend on:

* mutable closure state;
* another blackboard value;
* current time;
* randomness;
* an external service;
* side effects;
* whether it was called with an observation or synthetic effect.

The underlying core comments even acknowledge that stateful conditions may need to distinguish state values from effect values. ([GitHub][9])

## Correct interface

```typescript
interface SymbolicConstraint {
  readonly id: ConstraintId;
  readonly variable: VariableId;

  evaluate(snapshot: WorldSnapshot): ConditionResult;

  isEntailedBy(effect: SymbolicEffect): boolean;

  conflictsWith(effect: SymbolicEffect): boolean;

  canonicalForm(): CanonicalConstraint;
}
```

Opaque JavaScript guards can remain available:

```typescript
interface RuntimeGuard {
  evaluate(snapshot: WorldSnapshot): ConditionResult;
}
```

but they should not be used to claim soundness, completeness or optimality unless accompanied by a conservative symbolic abstraction.

## Material benefit

This single separation enables:

* reliable action indexing;
* canonical condition-set hashing;
* cycle detection;
* conflict checking;
* reference-planner comparison;
* complete and optimal search modes;
* safer custom user code.

# 15. False, unknown and operational error are collapsed

A JavaScript condition returns `false` if:

* its matcher is missing;
* its bridge is missing;
* the bridge is stopping;
* JavaScript invocation fails;
* the callback throws. ([GitHub][11])

Thus, to the planner:

```text
“The condition is observed false”
```

is equivalent to:

```text
“The JavaScript runtime failed”
“The observation subsystem is unavailable”
“The condition implementation is malformed”
```

A planner may then execute a corrective physical action in response to a software fault.

The blackboard separately returns `nil` for a missing key, which can also collide semantically with an explicit JavaScript `null`. ([GitHub][12])

## Required result type

```typescript
type ConditionResult =
  | {
      kind: "satisfied";
      evidence?: Evidence;
    }
  | {
      kind: "unsatisfied";
    }
  | {
      kind: "unknown";
      reason:
        | "missing"
        | "stale"
        | "occluded"
        | "insufficient-confidence";
    }
  | {
      kind: "error";
      error: Error;
    };
```

Default policy:

```text
satisfied   → continue
unsatisfied → plan a corrective action
unknown     → sense, wait, or fail conservatively
error       → stop and expose an operational fault
```

Belief Behavior Trees directly support the important conceptual extension from Boolean conditions to true, false and unknown, and include perception actions for reducing uncertainty. They also address nondeterministic action outcomes. ([Miccol][13])

## Material benefit

This prevents the system from treating sensor absence or code failure as a physical fact. It also creates a clear path to:

* stale-observation handling;
* sensing actions;
* confidence thresholds;
* partially observable domains;
* safe degraded operation.

A full probabilistic belief planner is not needed immediately. The four-valued result type alone is already high value.

# 16. Action success sometimes means “the target disappeared”

`MoveTo` returns `Success` if the destination cube is marked deleted, even though its advertised effect is:

```text
atEntity_<id> = true
```

`Pick_GoalBlockade` similarly returns `Success` if the cube is already deleted, even though its effects claim that the actor now holds that cube. ([GitHub][1])

Those are not successful executions of the declared action. They are stale or obsolete action instances.

The correct semantics are:

```text
If the postcondition is independently satisfied:
    the enclosing PPA fallback condition succeeds

If the target vanished:
    this action becomes Obsolete or Invalidated

If another actor achieved the intended effect:
    refresh observations and reevaluate the postcondition
```

Use an execution outcome such as:

```typescript
type ActionOutcome =
  | { kind: "completed" }
  | { kind: "failed"; reason: string }
  | { kind: "cancelled" }
  | { kind: "obsolete"; reason: string };
```

The planner should never infer an advertised effect from `obsolete`.

## Material benefit

This eliminates another form of phantom success and makes concurrent or externally perturbed environments tractable.

# 17. Asynchronous actions require identity, cancellation and stale-result rejection

The underlying planner explicitly warns that the eventual outcome of an asynchronous `Running` action is not guaranteed to be consumed. A reactive tree may stop ticking that branch because the world changes or another branch becomes preferable. ([GitHub][9])

The current example does not define:

* cancellation when a running movement branch is abandoned;
* whether a late completion is still authoritative;
* whether a command may be dispatched more than once;
* how action instances are identified;
* timeouts;
* cleanup;
* compensation.

A production-grade action instance should carry:

```typescript
interface ActionInstance {
  planId: string;
  treeRevision: bigint;
  actionInstanceId: string;
  actionSchemaId: string;
  bindingId: string;

  startWorldRevision: bigint;
  expectedOccupancyRevision: bigint;

  deadline: number;
  idempotencyKey: string;
  attempt: number;
}
```

Execution API:

```typescript
execute(context)
poll(context)
cancel(context)
cleanup(context)
compensate(context)
verify(before, after)
```

A callback is accepted only if its `actionInstanceId` is still active. Otherwise it is a stale completion.

## Material benefit

This is essential when leaves eventually control:

* animations;
* network requests;
* navigation stacks;
* industrial controllers;
* robot arms;
* long-running subprocesses;
* transactions with external side effects.

# 18. `winConditionMet` is an achievement latch, not a current-state fact

The final blackboard goal is synchronized from:

```javascript
state.winConditionMet
```

That flag becomes true on delivery and is not derived from current target position. ([GitHub][1])

If the target is subsequently picked up or moved out of the goal in manual mode, the planner still regards:

```text
cubeDeliveredAtGoal == true
```

as true.

There are two valid interpretations, but they must not be conflated.

## Achievement interpretation

```text
“The target has been delivered at least once.”
```

Then rename the field:

```text
missionCompleted
deliveryAchievementRecorded
```

and make its temporal semantics explicit.

## Current-state interpretation

```text
“The target is presently in the goal and not being held.”
```

Then derive it:

```typescript
isDelivered(snapshot) =
  Location(target).kind === "cell" &&
  isInGoalArea(Location(target).cell) &&
  Holding(actor) !== target;
```

## Material benefit

Explicit temporal semantics prevent stale goals and enable future mission specifications such as:

```text
deliver target
then return home
never remove target after delivery
```

Those are temporal goals, not simple final-state Booleans.

# 19. Action-generator precedence forces brittle application code

When the action generator returns any nonempty list, it becomes authoritative and the static registry is not scanned—even if every generated action is irrelevant to the failed condition. ([GitHub][10])

The example compensates by manually fetching registered actions such as:

```text
Deliver_Target
Pick_Target
Place_Held_Item
Place_Target_Temporary
Place_Obstacle
```

inside the generator and returning them alongside dynamic instances. ([GitHub][2])

This creates unnecessary coupling between:

* static registry names;
* generator implementation;
* internal precedence semantics;
* action completeness.

It also means an innocuous generator result can accidentally suppress the only valid static action.

## Required API

```typescript
state.setActionGenerator(generator, {
  mode: "augment",
  errorPolicy: "strict",
```

Supported modes:

```text

    static ∪ generated

override
    generated only

fallback
    use generated relevant actions,
```

```typescript
interface GenerationResult {

  complete: boolean;
  continuation?: string;
  modelRevision: bigint;
```

`complete` states whether the relevant grounding space was fully enumerated. That becomes important for any completeness claim.

Dynamic action identity should include every binding:

```text
DepositBlocker(object=107,destination=goal:1,pose=4,17)
```

not only:

```text
Deposit_GoalBlockade_107
```

## Material benefit

This removes brittle name lookups, protects plan reachability, and gives bounded or anytime grounding a formal contract.

# 20. The planner has no meaningful action-quality objective

Static action order is effectively registry/name order, while generated action order comes from application code. Under a memorizing fallback, that order determines which alternative is attempted first and may remain selected while running.

The original PA-BT work explicitly does not investigate optimal action choice, although it notes that action ordering could account for execution time and success probability. It also assumes valid grounding exists and that a conflict-free ordering can be found. ([ar5iv][6])

For this example, action value should include at least:

```text
robot travel distance
number of picks
number of placements
object displacement
predicted success probability
risk of reblocking
planning cost
```

A useful domain objective is:

[
J(\pi)=
\alpha L_{\text{robot}}
+\beta N_{\text{pick}}
+\gamma N_{\text{place}}
+\delta D_{\text{objects}}
+\epsilon R
]

where (R) is risk or expected recovery cost.

A simple candidate ranking could use:

[
J(a)
====

c(a)
+\lambda_t d(a)
-\lambda_p\log p_{\text{success}}(a)
+\lambda_r r(a)
+\lambda_s s(a)
]

but that remains heuristic unless embedded in a search algorithm with the corresponding optimality assumptions.

## Material benefit

Even in a game, this produces less erratic and more intelligible behavior. In robotics or workflow automation, it directly reduces:

* cycle time;
* energy;
* wear;
* manipulation failure exposure;
* operational cost.

# 21. Directly applicable complete and optimal BT planning

The current PA-BT mode should be retained; it is useful as a low-latency reactive refinement and execution substrate. But it should not be presented as complete or cost-optimal.

The original paper assumes valid grounded refinements exist, does not optimize action choice, and assumes a non-conflicting action order exists. ([ar5iv][6])

## 21.1 Complete mode: BT Expansion

BT Expansion uses a state-space formulation and provides soundness and completeness under its formal finite action-model assumptions. It was proposed partly because earlier BT synthesis methods can fail on solvable tasks. ([AAAI Publications][14])

A mode could be exposed as:

```typescript
plannerMode: "complete"
```

with assumptions:

```text
finite symbolic state model
deterministic exact transitions
complete grounding
well-formed goals
finite search
```

The default PA-BT mode remains:

```typescript
plannerMode: "reactive-lazy"
```

with an honest guarantee:

```text
low-latency best-effort online refinement;
not complete and not optimal
```

## 21.2 Cost-optimal mode: OBTEA-style search

OBTEA represents goals in DNF and actions using preconditions, add effects, delete effects and costs. It performs backward search over condition sets, selecting the unexplored set with minimum accumulated cost. For a current condition set (C) and action (a), its predecessor is broadly:

[
C_a =
pre(a)\cup(C\setminus add(a))
]

while actions deleting required literals are excluded. ([IJCAI][15])

For the example, this can minimize:

```text
travel steps + weighted pick/place cost + displacement
```

rather than accepting whichever blocker the flood frontier happens to return first.

Mode:

```typescript
plannerMode: "optimal"
```

with assumptions:

```text
nonnegative costs
exact action effects
complete grounding
canonical condition sets
model-execution agreement
```

## 21.3 Anytime mode

A practical system can use:

```typescript
plannerMode: "anytime"
```

with:

1. a quick heuristic search;
2. a safe executable prefix;
3. a retained complete search frontier;
4. continued improvement between action completions;
5. no permanent pruning solely from an inadmissible heuristic.

## Critical caveat

None of these guarantees survive arbitrary JavaScript matchers, guessed effects, incomplete grounding or incoherent observations.

> The theorem boundary follows the symbolic-model boundary.

| Complete BT Expansion mode                     | Solves all modeled finite solvable instances under assumptions     | Defensible completeness option                |                      High |
| OBTEA-style optimal mode                       | Minimizes declared task cost                                       | Lower cycle time/manipulation cost            |                      High |
| Unknown/error condition states                 | Prevents acting on software/sensing failure                        | Partial-observability support                 |                    Medium |
| Formal monitors/model checking                 | Enforces critical temporal invariants                              | Deployment assurance                          | High, after model cleanup |

The best return sequence is not “implement every research paper.” It is:

```text
correct world semantics
→ atomic observations
→ certified geometry
→ verified effects
→ route/cache improvements
→ typed symbolic model
→ better obstacle planning
→ complete/optimal modes
→ formal assurance
```

# 27. Concrete implementation roadmap

## Phase 0: correctness repairs

1. Introduce immutable `worldBounds`; never use terminal dimensions in planning.
2. Set `gridDirty` or, preferably, remove dimension-dependent geometry entirely.
3. Make pause suspend the PA-BT ticker and all action mutation.
4. Add a frontier-seen set.
5. Reject static objects before generating blocker-pick actions.
6. Stop treating deleted targets as successful movement/pick effects.
7. Rename or redefine `winConditionMet`.
8. Make generator mode additive by default.
9. Include all bindings in dynamic action identity.
10. Mark the documentation example as partial and non-standalone.

Acceptance properties:

```text
Viewport resize never changes plan or world state.
Pause never changes world revision.
No action reports Success when its guaranteed effect is false.
No static object is generated as a pickable blocker.
```

## Phase 1: performance and execution reliability

1. Persist navigation paths.
2. Add `poseRevision` and `occupancyRevision`.
3. Cache connected components or reachability by occupancy revision.
4. Return typed complete/partial/unreachable path results.
5. Introduce action instance IDs and cancellation.
6. Add timeouts and stale-completion rejection.
7. Record A* calls, expansions, flood cells and bridge invocations.

Acceptance target for the current default map:

```text
≤ 4 full A* searches
0 unverified path-clear writes
0 full topology recomputations caused solely by actor movement,
unless explicitly chosen by the implementation
```

## Phase 2: semantic model

1. Replace string facts with typed predicates.
2. Replace `heldItemExists` and `heldItemId` with one finite-domain holding variable.
3. Replace `deleted` with explicit object locations.
4. Represent static/movable capability explicitly.
5. Separate primary effects from derived facts.
6. Add dependency-based invalidation.
7. Add costs, resources and invariants.
8. Expose full DNF goals and alternative precondition groups.

## Phase 3: geometric planning

1. Implement discrete MCR search.
2. Return blocker sets rather than one ID.
3. Generate candidate placement poses.
4. Certify preserved corridors after placement.
5. Integrate a PDDLStream-like black-box certification API.
6. Use D* Lite or LPA* only if incremental occupancy changes justify it.

## Phase 4: planner modes

1. Retain current PA-BT as `reactive-lazy`.
2. Add cycle detection, canonical condition sets, budgets and no-goods.
3. Add BT Expansion as `complete`.
4. Add OBTEA-style cost search as `optimal`.
5. Add an anytime heuristic mode.
6. Publish each mode’s assumptions through `plan.guarantees()`.

## Phase 5: uncertainty and assurance

1. Add `Satisfied`, `Unsatisfied`, `Unknown`, `Error`.
2. Add freshness and confidence metadata.
3. Add sensing actions.
4. Export trees and action models for formal analysis.
5. Add runtime temporal monitors.
6. Differential-test complete and optimal modes against a reference finite-domain planner.

# 28. Required test programme

## Property-based world tests

```text
Object locations and occupancy agree.
At most one object occupies a cell.
A held object occupies no world cell.
A static object is never held.
Holding is mutually consistent with object location.
Viewport state cannot affect logical facts.
```

The current initialization already contains four duplicate wall-corner records whose spatial-index cells are overwritten by later registrations: 109 cube records correspond to 105 unique occupied cells. That is harmless visually but violates a clean one-object-per-cell world invariant and illustrates why initialization validation is worthwhile. ([GitHub][1])

## Planner semantic tests

```text
Plan Success implies goal true in a fresh snapshot.
Error never behaves like an ordinary false condition.
Unknown safety conditions never permit unsafe action.
Augment-mode generators never suppress relevant static actions.
Irrelevant generated actions cannot destroy solvability.
Equivalent snapshots and model versions produce identical plans.
```

## Differential planning tests

Generate finite random domains and compare:

```text
complete mode ↔ reference STRIPS solver solvability
optimal mode  ↔ reference uniform-cost solution cost
```

Forward-simulate every returned plan.

## Geometric disturbance tests

```text
one movable blocker
two blockers in series
two alternative blockers
nearest frontier is static
movable door farther from target
no legal placement
placement that reblocks route
occupancy changes during navigation
target moves during navigation
actor is externally teleported
```

## Concurrency tests

```text
pause during every action lifecycle state
resize during flood fill
late callback after cancellation
bridge shutdown during condition evaluation
snapshot commit during planner tick
rapid automatic/manual mode switching
```

## Documentation tests

Every code block should execute in CI or be explicitly marked as pseudocode/partial. The full example should assert its terminal postcondition rather than merely display a win banner.

# 29. How the reference documentation should be reframed

The documentation currently presents the example chiefly as a PA-BT illustration. That understates both its sophistication and its risks.

A better reference structure is:

## 29.1 “What PA-BT does”

Explain:

* PPA construction;
* backward refinement;
* reactive reevaluation;
* conflict relocation;
* what `Running` means;
* what PA-BT does **not** guarantee.

## 29.2 “What this example adds”

Explicitly identify four separate systems:

```text
PA-BT symbolic refinement
reachability/blocker analysis
A* motion planning
action execution and observation synchronization
```

## 29.3 “Model assumptions”

State:

```text
deterministic grid world
fully observable state
one actor
one held object
unit-cost movement
instantaneous pick/place
movable ring obstacles
no physical stability or kinematics
```

## 29.4 “Truthful effects and certified derived facts”

Remove advice that treats likely consequences as effects.

Use:

```text
guaranteed primary effect
derived certified fact
heuristic prediction
```

as three separate concepts.

## 29.5 “Guarantees”

Provide a matrix:

| Property                                     | Current PA-BT mode |
| -------------------------------------------- | ------------------ |
| Reactive reevaluation of existing conditions | Yes                |
| Runtime tree expansion                       | Yes                |
| Automatic recovery from every failure        | No                 |
| Complete grounding                           | Not guaranteed     |
| Complete planning                            | No                 |
| Cost optimality                              | No                 |
| Partial observability                        | No                 |
| Effect verification                          | No                 |
| Atomic world observations                    | No                 |
| Temporal safety guarantees                   | No                 |

## 29.6 “Research lineage”

The reference should connect the example to:

* original PA-BT for online reactive refinement;
* BT Expansion for completeness;
* OBTEA for cost-optimal backward BT planning;
* NAMO/MCR/MCD for obstacle manipulation;
* PDDLStream for certified task-and-motion integration;
* Belief Behavior Trees for unknown state and sensing;
* BTPG for benchmarking;
* BehaVerify/Fiacre for temporal verification.

This would make the page significantly more technically sophisticated without exaggerating the implementation’s present guarantees.

# Final technical judgment

The full example is better than the partial documentation suggests. It contains a real online planner, geometric state derivation, bounded A*, dynamic grounding, obstacle manipulation and reactive BT execution. It is a valuable prototype.

Its central weakness is not that it lacks enough heuristics. It is that the boundaries between the layers are informal:

```text
world state ↔ blackboard
blackboard fact ↔ symbolic condition
action status ↔ achieved effect
placement heuristic ↔ path-clear guarantee
geometry result ↔ planner certificate
UI dimensions ↔ world dimensions
```

The highest-value transformation is therefore:

> **Retain PA-BT as the reactive execution and incremental-refinement substrate, but put it over a typed, versioned and formally interpretable task-and-motion model whose geometric facts are certified and whose action effects are verified.**

In practical order:

1. decouple world geometry from the terminal;
2. make pause and concurrency semantics correct;
3. persist routes and split pose from occupancy revisions;
4. publish atomic world snapshots;
5. stop directly asserting derived reachability effects;
6. verify effects against fresh snapshots;
7. replace string/sentinel state with typed finite-domain variables;
8. replace nearest-frontier selection with MCR/NAMO reasoning;
9. expose certified geometric streams;
10. add explicit cost, complete and optimal planner modes;
11. add uncertainty and formal monitors once the model boundary is sound.

The immediate result would be a faster and more deterministic demo. The strategically important result would be something much more valuable:

> a reusable, auditable, cost-aware task-and-motion planning platform in which the PA-BT machinery supplies reactive execution, rather than being forced to compensate for unmodeled geometry and observation semantics.
