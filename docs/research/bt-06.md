# Planner-first redesign of `go-pabt` and `go-behaviortree`

## Executive conclusion

The proposed recursive, forward-compatible, `BT_`-namespaced interface is the right direction **only if it represents an immutable behavior-tree definition—not a directly stateful executable node**.

Replacing this:

```go
type Node func() (Tick, []Node)
```

with this:

```go
type Node interface {
    Tick() (Status, error)
    Children() ...
}
```

would improve discoverability but would not solve the fundamental architectural problems:

* definition and execution state would remain entangled;
* one tree could not be efficiently shared among many agents;
* planner mutation and runtime traversal would still compete for the same representation;
* action construction would remain coupled to planning search;
* running actions would still lack a rigorous preemption contract;
* policy graphs, temporal dispatchers, belief policies, and continuous planners would still be forced through a tree-shaped lowest common denominator;
* a general interface call would remain on every built-in node visit.

The strongest architecture is a staged one:

```text
typed domain model
        ↓
algorithm-specific dense planning view
        ↓
planner session and mutable search state
        ↓
immutable plan/policy artifact
        ↓
artifact-specific BT lowering
        ↓
immutable compiled BT Program
        ↓
per-agent mutable BT Instance
        ↓
verified action executor
```

The central representation split should be:

```text
Node       immutable, recursive, interoperable definition
Behavior   per-instance custom runtime behavior
Program    immutable, dense, compiled execution representation
Instance   mutable execution state for one Program
PlanGraph  mutable planner-side editing representation
Artifact   immutable semantic planner result
```

This is the only design that simultaneously gives:

* arbitrary user-defined nodes;
* efficient planner mutation;
* zero-allocation built-in execution;
* stable runtime identity;
* state transfer across replanning;
* sharing of one compiled tree among many agents;
* complete and optimal planner plugins;
* policy-graph, temporal, belief, hierarchical, continuous, and multi-agent integration;
* preservation of planner guarantees through execution;
* meaningful compatibility.

The closure design remains an excellent **convenience leaf/composite adapter**. It should cease to be the structural and execution substrate.

# 1. The current APIs optimize the wrong unification boundary

The present `go-pabt` surface is compact:

```go
type State[T Condition] interface {
    Variable(key any) (any, error)
    Actions(failed T) ([]Action[T], error)
}

type Action[T Condition] interface {
    Conditions() []Conditions[T]
    Effects() Effects
    Node() bt.Node
}

type Condition interface {
    Variable
    Match(value any) bool
}
```

`Action.Node()` is permitted to return a running asynchronous BT node, although the documentation explicitly warns that its eventual success, failure, or error may never be consumed. `Plan.Running()` is only the narrow fact that the preceding root tick returned `Running` as the result of an action-node tick. ([Go Packages][1])

Internally, the implementation uses:

* one planner node for each BT node;
* raw intrusive pointers for parent, first child, last child, previous sibling, and next sibling;
* `map[any]Effect` for action effects;
* `map[any]*precondition` for conjunctions;
* immediate invocation of `Action.Node()` while an action candidate is being incorporated;
* `Condition.Match(effect.Value())` for action relevance and conflict reasoning;
* a newly materialized `[]bt.Node` when an editable group is projected into an executable node. ([GitHub][2])

This design successfully minimizes the number of concepts in the package, but it unifies five things that should have different representations:

1. **The declarative action model**
2. **Grounding and candidate generation**
3. **Search state**
4. **The editable output policy**
5. **The executable BT and its running state**

That is the core issue. It is more important than any individual map allocation or interface call.

## 1.1 `Action.Node()` is the most consequential coupling

During candidate generation, the planner calls:

```go
act.Node()
```

before that action has necessarily been selected for execution.

That means a planning candidate is simultaneously:

* a symbolic transition;
* an action binding;
* a stateful executable object;
* a potentially closure-captured application object;
* a future asynchronous operation.

This obstructs:

* cost-only search without executable construction;
* millions of transient grounded candidates;
* sharing one action model among many search nodes;
* SAT, SMT, CP, or MILP encodings;
* delayed execution binding;
* remote execution;
* serialization;
* plan validation independent of execution;
* separate simulation and physical executors;
* policy graphs containing the same action at several states;
* parallel or multi-agent execution with independent action instances.

A planner should manipulate an `ActionRef` or model record. It should construct a BT action behavior only after an artifact commits that action for possible execution.

## 1.2 `Condition.Match` conflates three semantic relations

The current API uses the same operation for:

```text
Evaluate:
    Does the current observed value satisfy the condition?

Entail:
    Would an action effect establish the condition?

Conflict:
    Would an action effect contradict or preserve the condition?
```

The package documentation itself acknowledges that a stateful condition may need to distinguish actual state values from effect values. ([Go Packages][1])

Those operations are not interchangeable.

For an equality condition they may happen to coincide:

```text
condition: heldItem == cube7
effect:    heldItem := cube7
```

For richer conditions they do not:

```text
distance(target) < weaponRange
batteryLevel >= requiredEnergy(route)
pathExists(actor, destination)
probability(objectAt(x)) > 0.9
```

A JavaScript or Go callback can evaluate a world snapshot but usually cannot provide sound effect entailment, regression, conflict detection, or canonical identity.

That prevents the planner from honestly supporting:

* complete BT Expansion;
* OBTEA-style optimal planning;
* admissible heuristic search;
* effect indexing;
* canonical closed sets;
* principled conflict resolution;
* formal verification.

## 1.3 `State.Actions` is neither a scalable grounder nor a complete grounding contract

```go
Actions(failed T) ([]Action[T], error)
```

requires an eagerly materialized slice and cannot express:

* “there are more candidates”;
* “enumeration is complete”;
* “enumeration was suspended by budget”;
* “these are merely learned suggestions”;
* “this candidate depends on a geometric certificate”;
* infinite or continuous binding domains;
* continuation after an expensive sampling step;
* lower bounds on candidate cost;
* provenance;
* stale candidates after a model or world revision;
* action-schema indexing rather than full grounding.

This is particularly limiting for task-and-motion planning. PDDLStream demonstrates why continuous bindings and geometric relationships need lazy black-box streams whose outputs certify declarative facts, rather than an eager finite action slice. ([arXiv][3])

## 1.4 The editable tree is directly re-expanded as an executable tree

The intrusive linked representation is a reasonable editing structure. The problem is that every group’s closure traverses those links and constructs an executable child slice:

```go
func (n *node[T]) group() (tick bt.Tick, children []bt.Node) {
    tick = n.tick

    for node := n.first; node != nil; node = node.next {
        children = append(children, node.bt())
    }

    return
}
```

`Memorize` then copies and wraps child nodes at the start of an execution, while `Async` allocates a channel and launches a goroutine for each asynchronous execution. ([GitHub][4])

The right conclusion is not that linked editing is bad. It is:

> **An editing representation should not be executed directly.**

## 1.5 The current closure form has real strengths

The present BT abstraction is:

```go
type Node func() (Tick, []Node)
type Tick func(children []Node) (Status, error)
```

It offers:

* very low conceptual overhead;
* excellent composition syntax;
* arbitrary encapsulation;
* potentially zero allocation for a static hand-written tree;
* easy wrapping and decoration;
* compatibility with stateful closures.

The more recent metadata interfaces explicitly distinguish conceptual structure from physical node instances, indicating that structural introspection was already becoming difficult to derive from executable closures. ([Go Packages][5])

The closure is therefore worth retaining as an adapter. It is not the optimal common representation for planner-generated, edited, introspected, replicated, verified, and frequently ticked trees.

# 2. The non-negotiable design invariants

An API intended to support the breadth of contemporary planning should adopt these as normative invariants.

| Concern          | Required invariant                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| World state      | One planning or BT tick observes one immutable world revision                                          |
| Model            | Problem and domain views are immutable and revisioned                                                  |
| Search           | Search state is private to a planner session                                                           |
| Artifacts        | Published plans and policies are immutable                                                             |
| BT definition    | Node definitions are immutable and safe for concurrent reading                                         |
| BT execution     | Runtime state belongs to a per-agent `Instance`, never the definition                                  |
| Editing          | Planner mutations happen in a separate graph or arena                                                  |
| Publication      | Program replacement occurs only at a tick boundary                                                     |
| Action model     | Planning actions contain no executable BT closures                                                     |
| Action execution | An executor is bound only after an action has been committed                                           |
| Success          | Action success requires a fresh observation verifying the modeled outcome                              |
| Preemption       | Every running node has defined halt semantics                                                          |
| Guarantees       | Every guarantee names its assumptions and exact problem/artifact revision                              |
| Extensibility    | New planning semantics use capabilities and typed views, not fields added to a universal action struct |
| Performance      | Built-in execution has no interface dispatch and no steady-state allocation                            |
| Interoperability | Custom nodes always have a correct, albeit slower, fallback path                                       |

The most important of these is the separation of **semantic artifact** from **execution artifact**.

A temporal plan is not intrinsically a tree. A FOND solution is often a cyclic policy graph. A POMDP solver may expose only a next-action policy. An STNU produces a dispatchable strategy. A hierarchical planner produces a decomposition. A TAMP planner produces discrete actions plus continuous certificates.

All can be *executed through* a BT runtime, but they should not all be *stored as* ordinary trees.

# 3. The representation pipeline

The optimal pipeline is:

```text
┌──────────────────────────────────────────────────────────────┐
│ Typed authoring model                                        │
│ Go values, predicates, fluents, schemas, costs, resources   │
└──────────────────────────────┬───────────────────────────────┘
                               │ freeze / normalize / compile
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Immutable algorithm-specific model views                     │
│ STRIPS, SAS+, temporal, belief, streams, HTN, hybrid, etc.  │
└──────────────────────────────┬───────────────────────────────┘
                               │ PLAN_Open
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Planner Session                                              │
│ mutable frontier, caches, no-goods, search graph, beliefs   │
└──────────────────────────────┬───────────────────────────────┘
                               │ PLAN_Advance
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Immutable Artifact                                           │
│ sequence, partial order, policy graph, temporal network, BT │
└──────────────────────────────┬───────────────────────────────┘
                               │ artifact-specific lowering
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Immutable BT Program                                         │
│ dense opcodes, child edges, state layout, action references │
└──────────────────────────────┬───────────────────────────────┘
                               │ NewInstance
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Mutable BT Instance                                          │
│ cursors, active set, timers, opaque custom behaviors        │
└──────────────────────────────┬───────────────────────────────┘
                               │ dispatch / poll / verify
                               ▼
┌──────────────────────────────────────────────────────────────┐
│ Action executors and observations                            │
└──────────────────────────────────────────────────────────────┘
```

This is not unnecessary layering. Each layer has fundamentally different optimal data structures.

| Layer                      | Optimal representation                      |
| -------------------------- | ------------------------------------------- |
| User authoring             | strongly typed, ergonomic, generic builders |
| Classical search           | dense integer IDs, bitsets, arrays          |
| Continuous grounding       | lazy streams and certificates               |
| Search state               | arenas, priority queues, hash-consed graphs |
| Editable PA-BT policy      | dense intrusive ID graph                    |
| Published plan             | immutable semantic artifact                 |
| BT execution               | compact immutable instruction/edge arrays   |
| Runtime state              | tightly packed per-instance arrays          |
| Custom behavior            | interface object at extension boundary      |
| Interprocess compatibility | versioned message schema/RPC                |

Trying to use one Go interface or one recursive tree representation for all these roles necessarily sacrifices either planner behavior or performance.

The dependency direction is more important than whether these reside in separate repositories, but separate modules make the contracts clearer:

```text
    Model and artifact views

    Artifact-to-BT lowering and acting controller

github.com/joeycumines/go-pabt/v2
    PA-BT planner engine implementing go-planning

Other engines:
github.com/joeycumines/go-btexp
```

The dependency graph should be:

```text
go-behaviortree/v2  ◄────────── go-planning/bt ─────────► go-planning
                                              ▲
                                              │
                   planner engine modules ────┘
```

Specifically:

* `go-planning` must not import `go-behaviortree`;
* `go-behaviortree` must not import planning packages;
* a planner may return a native semantic artifact without knowing anything about BTs;
* `go-planning/bt` performs the integration;
* `go-pabt/v2` may optionally ship a native artifact lowerer, but its core planner should still be independently usable.

This prevents BT execution concerns from contaminating planner models and prevents planner-specific concepts from bloating the general BT runtime.

# 5. `go-behaviortree/v2`: the recursive interface should be a definition protocol

## 5.1 Normative core

A suitable core is:

```go
package behaviortree

type Status uint8

const (
    Invalid Status = iota
    Running
    Success
    Failure
)

// Node is an immutable behavior-tree definition.
//
// Implementations must be safe for concurrent structural inspection.
// Runtime state must not be stored in the Node.
type Node interface {
    // BT_ChildCount returns the fixed number of direct structural children.
    BT_ChildCount() int

    // BT_Child returns one direct structural child.
    // The caller will only request 0 <= index < BT_ChildCount().
    BT_Child(index int) Node

    // BT_NewBehavior creates runtime behavior for one structural occurrence
    // in one Instance.
    //
    // A compiler-native node may inherit the default implementation because
    // its registered lowerer eliminates the need for an opaque Behavior.
    BT_NewBehavior(*BindContext) (Behavior, error)

    // The sole non-BT_-prefixed interface method is private so that external
    // implementations must embed UnimplementedNode or UnsafeNode.
    mustEmbedUnimplementedNode()
}

type UnimplementedNode struct{}

func (UnimplementedNode) BT_ChildCount() int { return 0 }

func (UnimplementedNode) BT_Child(index int) Node {
    panic(ErrChildIndex)
}

func (UnimplementedNode) BT_NewBehavior(*BindContext) (Behavior, error) {
    return nil, ErrUnimplementedNode
}

func (UnimplementedNode) mustEmbedUnimplementedNode() {}
func (UnimplementedNode) testEmbeddedByValue()       {}

// UnsafeNode may be embedded to opt out of forward-compatible defaults.
// Adding a mandatory method to Node may then break the implementation.
type UnsafeNode interface {
    mustEmbedUnimplementedNode()
}
```

The `BT_` namespace should be reserved for **exported interface-contract methods**. The private embedding marker must remain unexported and is the one necessary exception.

This interface is recursive, but it is not executable. It describes:

* stable conceptual children;
* a way to create one runtime behavior per structural occurrence;
* no mutable status;
* no hidden dynamic child generation;
* no per-tick slice construction.

## 5.2 Why these three exported methods

`BT_ChildCount` and `BT_Child` are preferable to a hot `iter.Seq` or callback because a compiler can:

* preallocate exactly;
* calculate depth and edge count;
* validate the complete structure;
* assign stable occurrence IDs;
* build a compact CSR-style edge array;
* avoid iterator closure escape behavior;
* visit children without allocating.

`iter.Seq` remains excellent for cold inspection APIs:

```go
func Walk(root Node) iter.Seq[NodeInfo]
func (p *Program) Nodes() iter.Seq[NodeInfo]
```

It should not be the execution child interface.

`BT_NewBehavior` is deliberately cold. It is called:

```text
once per custom-node occurrence
per Instance
```

—not once per tick and not during planner search.

## 5.3 Definition immutability is a hard contract

After a `Node` is submitted for compilation:

* `BT_ChildCount` must remain constant;
* every `BT_Child(i)` must continue to identify the same definition;
* calls must be side-effect free;
* the definition must be safe for concurrent inspection;
* structural cycles are invalid unless represented through a specific graph/call operator;
* nil children are invalid.

If the same `Node` value appears at two positions:

```go
Sequence(shared, shared)
```

the two positions are separate **occurrences** with independent runtime state.

Explicit state sharing requires an explicit construct:

```go
SharedState(...)
Call(subtreeID)
PolicyDispatch(policyID)
```

Pointer identity must never implicitly determine runtime-state sharing.

# 6. Runtime behavior must be separate from the definition

## 6.1 Custom behavior contract

```go
type Behavior interface {
    // BT_Tick performs one nonblocking execution step.
    BT_Tick(*Context, Children) (Status, error)

    // BT_Halt makes an active Running occurrence quiescent because it is
    // no longer selected, has been replaced, or the instance is stopping.
    BT_Halt(*HaltContext) error

    mustEmbedUnimplementedBehavior()
}

type UnimplementedBehavior struct{}

func (UnimplementedBehavior) BT_Tick(
    *Context,
    Children,
) (Status, error) {
    return Invalid, ErrUnimplementedBehavior
}

func (UnimplementedBehavior) BT_Halt(*HaltContext) error {
    return nil
}

func (UnimplementedBehavior) mustEmbedUnimplementedBehavior() {}
```

The runtime invokes this interface only for opaque custom behavior. Native composites, decorators, condition nodes, action adapters, dispatchers, and monitors are compiled to native operations.

## 6.2 Why `BT_Halt` is mandatory

Reactive BT execution means a running node can cease to be selected without returning a terminal status.

Examples include:

* a higher-priority fallback condition becoming true;
* an earlier sequence guard becoming false;
* a planner replacing the active policy;
* an external actor satisfying the postcondition;
* a timeout or safety monitor preempting an action;
* shutdown;
* a multi-agent coordinator reassigning the task.

The current `go-pabt` documentation warns that a running action’s eventual result may never be consumed. The correct solution is not merely to warn about it: it is to make preemption an explicit lifecycle event. ([Go Packages][1])

BehaviorTree.CPP similarly treats asynchronous actions as stateful start/poll operations and provides an explicit halt hook when an action is aborted. It also emphasizes that normal BT ticking remains single-threaded and nonblocking. ([BehaviorTree.CPP][6])

The v2 runtime should guarantee:

```text
If an occurrence returned Running on tick N
and is not visited on tick N+1,
BT_Halt is invoked exactly once, deepest child first.
```

Other halt causes include:

```go
type HaltReason uint8

const (
    HaltPreempted HaltReason = iota + 1
    HaltReplaced
    HaltCancelled
    HaltParentCompleted
    HaltShutdown
    HaltProgramError
)
```

`BT_Halt` should:

* be idempotent;
* return promptly;
* initiate external cancellation if relevant;
* invalidate stale completion callbacks;
* not wait indefinitely for remote or physical work;
* leave instance-local behavior ready for another activation.

Long cleanup belongs in optional `BT_Close(context.Context)` support.

## 6.3 Activation semantics

A `Behavior` object is created once per instance occurrence and may be activated repeatedly.

`Context` should expose:

```go
func (c *Context) Starting() bool
func (c *Context) Activation() ActivationID
func (c *Context) Tick() TickID
func (c *Context) Node() NodeID
func (c *Context) ProgramRevision() ProgramRevision
func (c *Context) Frame() Frame
func (c *Context) Waker() Waker
```

The rules should be:

* first tick after inactivity has `Starting() == true`;
* after `Running`, subsequent selected ticks have `Starting() == false`;
* after `Success` or `Failure`, the occurrence returns to inactive;
* the next activation has a new `ActivationID`;
* preemption calls `BT_Halt`, then returns it to inactive;
* an invalid status is an operational error, not silently coerced to failure.

The existing v1 `Status.Status()` coercion of out-of-range values to failure is unsuitable for a planner-grade runtime because it can hide implementation faults. The zero value should remain `Invalid` and should fail visibly.

# 7. Children should be a tick-scoped runtime view, not `[]Node`

```go
type Children struct {
    // Unexported:
    // instance *Instance
    // edgeBase uint32
    // edgeCount uint32
    // tickEpoch uint64
}

func (c Children) Len() int

func (c Children) ID(index int) NodeID

func (c Children) Tick(index int) (Status, error)

func (c Children) Halt(
    index int,
    reason HaltReason,
) error
```

Properties:

* constructing `Children` does not allocate;
* `Tick(i)` dispatches through the owning `Instance`;
* the runtime records visitation and active status;
* tracing, deadlines, and preemption remain under engine control;
* the view cannot be retained beyond the current `BT_Tick`;
* debug builds can use an epoch to detect stale use;
* concurrent use is prohibited;
* child IDs are compiled occurrence IDs, not definition pointer identities.

This resolves several current problems:

* no fresh `[]Node`;
* custom composites do not directly invoke raw node closures;
* the runtime can detect abandoned running branches;
* instrumentation is centralized;
* custom nodes remain general;
* built-in nodes avoid the interface entirely.

# 8. `Program` and `Instance` are the performance boundary

## 8.1 Public surface

```go
type Compiler struct {
    // Registered native lowerers and compile configuration.
}

func NewCompiler(options ...CompilerOption) *Compiler

func (c *Compiler) Compile(
    root Node,
    config CompileConfig,
) (*Program, CompileReport, error)

// Go 1.27 generic concrete method.
func (c *Compiler) RegisterLowerer[T Node](
    lower func(*Lowering, T) error,
) error

type Program struct {
    // Immutable compiled representation.
}

func (p *Program) Revision() ProgramRevision
func (p *Program) Info() ProgramInfo
func (p *Program) Nodes() iter.Seq[NodeInfo]

func (p *Program) NewInstance(
    ctx context.Context,
    config InstanceConfig,
) (*Instance, error)

type Instance struct {
    // Mutable state for one execution of one Program.
}

func (i *Instance) Tick(
    ctx context.Context,
    input TickInput,
) (TickResult, error)

func (i *Instance) Halt(
    ctx context.Context,
    reason HaltReason,
) error

func (i *Instance) Rebase(
    ctx context.Context,
    next *Program,
    transfer StateTransfer,
) (RebaseReport, error)

func (i *Instance) Close(context.Context) error
```

Convenience users should still receive a small façade:

```go
type Tree struct {
    program  *Program
    instance *Instance
}

func Bind(
    ctx context.Context,
    root Node,
    config TreeConfig,
) (*Tree, error)

func (t *Tree) Tick(
    ctx context.Context,
    input TickInput,
) (TickResult, error)
```

The convenience façade preserves the ease of:

```go
tree, err := bt.Bind(ctx, root, bt.TreeConfig{})
result, err := tree.Tick(ctx, input)
```

without contaminating the core definition with runtime state.

## 8.2 Internal layout

A plausible compact representation is:

```go
type nodeRecord struct {
    opcode    uint16
    flags     uint16

    edgeStart uint32
    edgeCount uint32

    payload   uint32
    stateSlot uint32
}

type Program struct {
    nodes []nodeRecord
    edges []NodeID

    customFactories []customFactory
    stateLayout     []stateLayout

    stableIDs []StableID
    debug     *DebugTable

    revision ProgramRevision
}
```

The exact packing should be benchmark-driven, but the principles are:

* integer IDs rather than object pointers;
* child edges in contiguous arrays;
* no Go interface values in built-in hot records;
* custom factories in a separate, rarely accessed table;
* debug metadata in a separable table;
* immutable program memory shared across instances;
* mutable state in separate instance arrays.

An `Instance` can hold:

```go
type Instance struct {
    program *Program

    cursors      []uint32
    statuses     []Status
    activations  []ActivationID
    timers       []timerState

    activePrev bitset
    activeNow  bitset
    visited    bitset

    custom []Behavior

    stack   []frame
    scratch []uint32
}
```

For many built-in nodes, a full status byte per node is unnecessary. The compiler can allocate state only for operations that need it.

## 8.3 Execution backends

There should not be one hard-coded universal interpreter.

A compiler should be able to select among:

1. **Dense direct-recursive execution**

   Best for shallow, bounded trees. It often produces the least dispatch overhead.

2. **Dense explicit-stack execution**

   Best for untrusted depth, policy dispatch, and avoiding Go stack growth.

3. **Interface-bound interpretation**

   The universal fallback for opaque custom nodes.

4. **Specialized fused operations**

   Useful for repeatedly generated patterns such as:

   ```text
   Fallback(
       postcondition,
       Sequence(preconditions..., action)
   )
   ```

A generic bytecode machine is not automatically faster than direct recursion. The public API should permit several backends while preserving exactly the same semantics.

## 8.4 Native lowerers

Compilation should proceed as follows:

```text
For each structural occurrence:

1. Check for a registered exact-type lowerer.
2. If found, emit native opcode/payload/state layout.
3. Otherwise, compile structural children normally.
4. Retain BT_NewBehavior as the opaque runtime factory.
```

A third-party node can therefore be supported immediately:

```go
type MyNode struct {
    bt.UnimplementedNode

    Children []bt.Node
    Config   MyConfig
}

func (n *MyNode) BT_ChildCount() int {
    return len(n.Children)
}

func (n *MyNode) BT_Child(i int) bt.Node {
    return n.Children[i]
}

func (n *MyNode) BT_NewBehavior(
    ctx *bt.BindContext,
) (bt.Behavior, error) {
    return newMyBehavior(n.Config, ctx), nil
}
```

Later, its package can add a native compiler extension without changing `Node`:

```go
compiler.RegisterLowerer(
    func(l *bt.Lowering, n *MyNode) error {
        return l.EmitCustomOptimized(
            myOpcode,
            myPayload(n.Config),
        )
    },
)
```

That is the optimal modularity/performance compromise:

* custom behavior always works;
* native built-ins are fast;
* compiler specialization is opt-in;
* the core interface does not grow for each extension;
* implementors retain all their own concrete methods and interfaces.

# 9. Go 1.27 generic methods: where they are valuable and where they are impossible

As of July 12, 2026, Go 1.27’s release notes are still draft and the release is expected in August 2026. The draft adds type parameters to **concrete methods**, but interface methods may not declare type parameters, and generic concrete methods cannot satisfy interface methods. ([Go][7])

The accepted proposal explains the reason: structural interface satisfaction means the implementation cannot know all potentially required generic instantiations, whereas a call on a concrete receiver is statically resolvable. It also notes that generic methods are not discoverable through reflection in uninstantiated form. ([GitHub][8])

Therefore:

> **The stable plugin boundary must be non-generic. Generics belong on concrete builders, registries, typed keys, codecs, and views.**

Excellent uses include:

```go
func (c *Compiler) RegisterLowerer[T Node](
    fn func(*Lowering, T) error,
) error
```

```go
func (v Views) Get[T any](
    key ViewKey[T],
) (T, bool)
```

```go
func (b *ViewBuilder) Put[T any](
    key ViewKey[T],
    value T,
) error
```

```go
func (m Meta) Get[T any](
    key Key[T],
) (T, bool)
```

```go
func (m Meta) With[T any](
    key Key[T],
    value T,
) Meta
```

```go
func (b *symbolic.Builder) Fluent[A, V any](
    name string,
    args Codec[A],
    values Domain[V],
) Fluent[A, V]
```

```go
func (b *symbolic.Builder) Action[B any](
    name string,
    bindings Codec[B],
) *ActionBuilder[B]
```

These methods improve:

* namespace organization;
* type inference;
* discoverability;
* fluent authoring;
* compile-time type safety;
* registration ergonomics.

They do **not** themselves improve planner runtime. Their outputs should be compiled into:

```text
FormulaID
AtomID
VariableID
ActionID
BindingID
ResourceID
ObjectID
```

and dense arrays.

Given the novelty of generic methods and the accepted proposal’s warning about tooling adaptation, it would be prudent to provide equivalent package-level generic functions during the first release:

```go
func GetView[T any](
    views Views,
    key ViewKey[T],
) (T, bool)
```

alongside:

```go
views.Get(key)
```

This is a tooling migration measure, not a permanent duplication requirement.

# 10. Forward-compatible embedding and the `BT_` namespace

The gRPC Go generator’s forward-compatibility pattern requires implementations to embed an `Unimplemented<Service>Server`, while offering an unsafe opt-out. It also uses a runtime registration check to catch pointer rather than value embedding. ([GitHub][9])

That pattern is suitable here, with some qualifications.

## 10.1 Why the prefix is justified

Normally, Go interface methods should have ordinary names. This is an exceptional case because node implementations may simultaneously participate in:

* a domain-specific node interface;
* a planner artifact interface;
* a UI/introspection interface;
* a serialization interface;
* a BT compiler capability;
* the user’s concrete application API.

Reserving:

```text
BT_
```

for all exported `go-behaviortree` contract methods avoids accidental structural collisions such as:

```go
Children()
Name()
Value()
Tick()
State()
Model()
```

An implementor remains free to expose:

```go
func (n *MoveNode) Name() string
func (n *MoveNode) Cost() Cost
func (n *MoveNode) Action() ActionRef
func (n *MoveNode) DomainMetadata() Metadata
```

without risking future conflict.

Concrete package-owned APIs should remain idiomatic:

```go
program.NewInstance(...)
instance.Tick(...)
compiler.Compile(...)
meta.Get(...)
```

Only the plugin interfaces need the namespace prefix.

## 10.2 Embedding by value

Compilation should verify value embedding:

```go
if v, ok := node.(interface {
    testEmbeddedByValue()
}); ok {
    v.testEmbeddedByValue()
}
```

Embedding:

```go
type MyNode struct {
    bt.UnimplementedNode
}
```

is valid.

Embedding:

```go
type MyNode struct {
    *bt.UnimplementedNode
}
```

should fail early because a nil embedded pointer can panic when a future default method is called.

## 10.3 Do not abuse forward-compatible defaults

Embedding permits adding an interface method without forcing every source implementation to change. It does not make every semantic change safe.

Rules:

* add methods to the core interface very rarely;
* use optional one-method capability interfaces for most growth;
* defaults must either be semantically safe or fail explicitly;
* never add a default that silently changes control behavior;
* inherited `BT_NewBehavior` must return `ErrUnimplementedNode`;
* registration or compilation must detect unsupported defaults before execution;
* an unsafe embedding option must explicitly accept future source breakage.

Optional capabilities can be:

```go
type MetaProvider interface {
    BT_Meta() Meta
}

type StableIDProvider interface {
    BT_StableID() StableID
}

type FingerprintProvider interface {
    BT_Fingerprint() Fingerprint
}

type ModelProvider interface {
    BT_Model() FormalModel
}

type Closer interface {
    BT_Close(context.Context) error
}
```

Adding a new capability then does not alter the meaning of existing `Node` implementations.

This provides source-level forward compatibility. It is not a stable binary ABI. Cross-process and independently versioned plugins should use a versioned RPC or message protocol.

# 11. Metadata, runtime values, planner state, and behavior state must be distinct

The current library’s context-like value mechanism uses package-level synchronization and runtime call-stack discovery. Its own documentation warns that it is intended for information transiting API boundaries and should preferably be used outside normal execution. ([GitHub][10])

The redesign should distinguish four unrelated concepts.

## 11.1 Immutable definition metadata

Examples:

```text
name
source frame
documentation
artifact element ID
planner action ID
visualization category
```

```go
type Meta struct {
    // Immutable typed entries.
}

type Key[T any] struct {
    // Package-unique key identity.
}

func (m Meta) Get[T any](key Key[T]) (T, bool)
func (m Meta) With[T any](key Key[T], value T) Meta
```

The compiler transfers metadata to a `DebugTable`, indexed by `NodeID`.

No runtime stack inspection is necessary.

## 11.2 Runtime frame or ports

Examples:

```text
subtree-local input/output bindings
service references
current immutable observation
execution registry
```

```go
type Frame struct {
    // Immutable or explicitly scoped runtime values.
}

func (f Frame) Get[T any](key Key[T]) (T, bool)
func (f Frame) With[T any](key Key[T], value T) Frame
```

A frame is explicitly supplied to `Instance.Tick`.

It is not a mutable world-state blackboard.

## 11.3 Planner/world snapshot

This is a model-specific immutable object:

```go
type Snapshot struct {
    ModelRevision Revision
    WorldRevision Revision
    ObservedAt    time.Time

    // Dense state representation and observation metadata.
}
```

Every condition evaluated during one planner or BT root tick must use the same revision.

## 11.4 Per-instance behavior state

This consists of:

* sequence/fallback cursors;
* active action handles;
* timeout state;
* retry counts;
* custom `Behavior` objects;
* policy-dispatch state.

It resides only in `Instance`.

Combining any two of these concepts into a universal `map[any]any` sacrifices either correctness, speed, or both.

# 12. Built-in nodes should have explicit memory and reactivity semantics

The v1 pattern:

```go
bt.Memorize(bt.Sequence)
```

is flexible, but it requires runtime wrapping and makes the semantic distinction indirect. The v2 public surface should provide explicit definitions:

```go
func ReactiveSequence(children ...Node) Node
func MemorySequence(children ...Node) Node

func ReactiveFallback(children ...Node) Node
func MemoryFallback(children ...Node) Node

func Parallel(policy ParallelPolicy, children ...Node) Node

func Inverter(child Node) Node
func Retry(policy RetryPolicy, child Node) Node
func Timeout(policy TimeoutPolicy, child Node) Node
func RateLimit(policy RatePolicy, child Node) Node
```

The compiler lowers these to opcodes and allocates only the required cursor or timer state.

For planners, explicit semantics matter:

* `ReactiveSequence` reevaluates earlier guards and preempts a later running action when one reverses;
* `MemorySequence` resumes its cursor without reevaluating prior children;
* `ReactiveFallback` may abandon a running lower-priority method;
* `MemoryFallback` stays with the selected alternative until it terminates.

These choices influence:

* recovery behavior;
* action cancellation;
* optimality;
* safety;
* fairness;
* whether postconditions are continuously monitored.

They should not be hidden behind a generic decorator.

## 12.1 Parallel is cooperative by default

A `Parallel` BT node should tick children sequentially in a deterministic order. External actions may overlap in time, but the BT engine should not create a goroutine per child.

BehaviorTree.CPP makes the same useful distinction: BT ticking is single-threaded, while nonblocking actions create concurrency through repeated `Running` responses. ([BehaviorTree.CPP][6])

Actual action parallelism belongs to:

* executor handles;
* resource claims;
* causal constraints;
* temporal dispatch;
* scheduler policies.

This avoids data races and nondeterministic tree semantics.

# 13. Stable identities and state transfer across replanning

A planner-integrated BT runtime needs several identities:

```go
type NodeID uint32           // occurrence within one Program
type StableID [16]byte       // semantic identity across revisions
type ProgramRevision uint64
type ActivationID uint64
type ActionInstanceID [16]byte
type StateSchemaID uint64
```

`NodeID` is compact and revision-local.

`StableID` is used for:

* mapping planner artifact elements to compiled nodes;
* transferring memory-sequence cursors;
* retaining custom behaviors;
* preserving a running action during an artifact update;
* deterministic tracing.

State transfer must use:

```text
(StableID, StateSchemaID)
```

—not pointer identity or child index alone.

A running action may be preserved only when all relevant identity fields agree:

```text
same action schema
same grounded binding
same responsible agent
same action instance
same executor semantics
compatible state schema
still valid under the new artifact
```

Otherwise the old occurrence must be halted or cancelled.

## 13.1 Rebase semantics

```go
type StateTransfer struct {
    // Generated by the artifact lowerer/compiler.
}

type RebaseReport struct {
    Preserved []StableID
    Reset     []StableID
    Halted    []StableID
    Added     []StableID
    Removed   []StableID
}
```

Rebase occurs only between root ticks:

```text
finish tick on Program revision N
        ↓
halt incompatible active occurrences
        ↓
transfer compatible state
        ↓
atomically adopt Program revision N+1
        ↓
begin next tick
```

A program must never be edited while its instance is traversing it.

# 14. Planner-neutral API: small interfaces, rich concrete values

A planner ecosystem should learn from Unified Planning’s distinction between problem features and operation modes. Unified Planning uses `ProblemKind` to describe model features, lets engines report suitability, and distinguishes one-shot, anytime, validation, compilation, simulation, and other modes. Its result statuses distinguish satisfying solutions, optimal solutions, proven unsolvability, timeouts, memory exhaustion, errors, and intermediate solutions. ([Unified Planning][11])

The Go design should preserve that capability negotiation while avoiding a Python-style mixin hierarchy or one giant mode enum.

## 14.1 Core engine interfaces

```go
package planning

type Engine interface {
    PLAN_Info() EngineInfo
    mustEmbedUnimplementedEngine()
}

type Planner interface {
    Engine

    PLAN_Support(
        problem Problem,
        request Request,
    ) SupportReport

    PLAN_Open(
        context.Context,
        Problem,
        Request,
    ) (Session, error)

    mustEmbedUnimplementedPlanner()
}

type Session interface {
    // PLAN_Advance performs bounded synchronous work.
    //
    // The session does no hidden background planning unless explicitly
    // wrapped by a Runner.
    PLAN_Advance(
        context.Context,
        Input,
    ) (Update, error)

    // PLAN_Current returns the latest immutable solution frontier.
    PLAN_Current() Frontier

    PLAN_Close(context.Context) error

    mustEmbedUnimplementedSession()
}
```

Separate operations should have separate optional interfaces:

```go
type Validator interface {
    Engine

    PLAN_Validate(
        context.Context,
        Problem,
        Artifact,
        ValidationRequest,
    ) (ValidationResult, error)
}

type ProblemCompiler interface {
    Engine

    PLAN_Compile(
        context.Context,
        Problem,
        CompileRequest,
    ) (CompileResult, error)
}

type Simulator interface {
    Engine

    PLAN_OpenSimulator(
        context.Context,
        Problem,
        SimulationRequest,
    ) (Simulation, error)
}
```

Do not make `UnimplementedEngine` implement optional operation interfaces. Otherwise embedding it would falsely advertise support.

## 14.2 Why a pull-driven `Session` is better than channels or one-shot methods

A session can model:

* one-shot planning;
* anytime improvement;
* online planning;
* PA-BT continual refinement;
* action selection;
* plan repair;
* replanning after observations;
* model updates;
* receding-horizon control;
* portfolio planning.

`PLAN_Advance` is preferable as the primitive because it:

* accepts new observations and execution events;
* permits deterministic operation-count budgets;
* avoids mandatory goroutines;
* avoids callback reentrancy;
* supports single-threaded embedding in a simulation or game loop;
* maps cleanly to bidirectional RPC streaming;
* permits caller-controlled scheduling;
* supports reproducible testing.

Convenience functions can be layered on top:

```go
func Solve(
    ctx context.Context,
    planner Planner,
    problem Problem,
    request Request,
) (Result, error)

func Anytime(
    ctx context.Context,
    planner Planner,
    problem Problem,
    request Request,
) iter.Seq2[Update, error]
```

# 15. Requests, inputs, updates, and planner outcomes

## 15.1 Request

A request should separate:

```go
type Request struct {
    Interaction InteractionRequest

    AcceptedArtifacts ArtifactRequirements
    RequiredClaims    ClaimRequirements

    Objective Objective
    Budget    Budget

    Seed        uint64
    Determinism DeterminismRequest

    Extensions Extensions
}
```

`InteractionRequest` describes operational behavior such as:

```text
batch
anytime
continual
receding horizon
repair from prior artifact
online action selection
```

It does not describe the planning model. Model capabilities come from the problem views.

## 15.2 Input

```go
type Input struct {
    // Monotonic external input revision.
    Revision InputRevision

    // Optional fresh world or belief snapshot.
    Snapshot Snapshot

    // Execution outcomes, observations, cancellations, resource changes.
    Events []ExecutionEvent

    // Optional domain/problem change.
    Delta ProblemDelta

    // Work permitted for this Advance call.
    Budget Budget

    Extensions Extensions
}
```

Several calls may use the same input revision to continue search.

## 15.3 Update

```go
type Update struct {
    Revision UpdateRevision

    Phase       Phase
    Disposition Disposition

    Solutions []Solution
    Delta     ArtifactDelta

    Bounds ObjectiveBounds
    Claims []Claim

    Needs []Need
    Stats Stats
}
```

Suggested phases:

```go
const (
    PhaseSearching Phase = iota + 1
    PhaseReady
    PhaseActing
    PhaseSucceeded

    PhaseUnsatisfiableProven
    PhaseIncomplete
    PhaseBudgetExhausted

    PhaseInvalidModel
    PhaseObservationError
    PhaseCancelled
)
```

Suggested dispositions:

```go
const (
    ContinuePlanning Disposition = iota + 1
    ReadyToExecute
    AwaitObservation
    AwaitExternal
    Terminal
)
```

This replaces the narrow, global `Plan.Running()` bit with an actual planner protocol.

## 15.4 Go errors versus modeled outcomes

The contract should be:

| Situation                                      | Representation                                        |
| ---------------------------------------------- | ----------------------------------------------------- |
| Valid plan found                               | `Update` / `Solution`                                 |
| Proven unsatisfiable                           | `PhaseUnsatisfiableProven`                            |
| Search budget ended                            | `PhaseBudgetExhausted`                                |
| No plan yet                                    | `PhaseSearching` or `PhaseIncomplete`                 |
| Modeled action failure                         | `ExecutionEvent` and BT `Failure`                     |
| Unsupported problem                            | `SupportReport`, then typed `Open` error if attempted |
| Invalid model                                  | update phase or typed validation result               |
| API misuse, corrupted state, transport failure | Go `error`                                            |
| Context cancellation                           | Go context error plus terminal update where possible  |

Search failure is not automatically a Go error.

# 16. Typed views are the correct generic interoperability mechanism

A universal planner action or state interface would become a lowest-common-denominator API full of optional fields and `any`.

Instead:

```go
type Problem interface {
    PLAN_Info() ProblemInfo
    PLAN_Views() Views

    mustEmbedUnimplementedProblem()
}

type Artifact interface {
    PLAN_Info() ArtifactInfo
    PLAN_Views() Views

    mustEmbedUnimplementedArtifact()
}
```

`Views` is a concrete immutable registry:

```go
type ViewID struct {
    Namespace string
    Name      string
    Major     uint16
}

type ViewKey[T any] struct {
    // Unexported stable identity and runtime type token.
}

func NewViewKey[T any](id ViewID) ViewKey[T]

type Views struct {
    // Immutable, indexed entries.
}

// Go 1.27.
func (v Views) Get[T any](
    key ViewKey[T],
) (T, bool)

type ViewBuilder struct {
    // Mutable only while constructing a Problem or Artifact.
}

func (b *ViewBuilder) Put[T any](
    key ViewKey[T],
    value T,
) error
```

A symbolic planner can do one typed lookup when opening a session:

```go
task, ok := problem.PLAN_Views().Get(symbolic.DenseTaskView)
if !ok {
    return nil, planning.ErrMissingView
}
```

Its hot search loop then holds:

```go
*symbolic.DenseTask
```

and performs no further view lookup, type assertion, reflection, or general interface dispatch.

This design gives:

* a stable non-generic plugin boundary;
* typed Go authoring;
* extensibility without changing core interfaces;
* exact, algorithm-specific dense types;
* view versioning;
* cross-package discoverability;
* no lowest-common-denominator model;
* no `any` in planner hot loops.

# 17. Capability negotiation must be richer than `Supports() bool`

```go
type SupportLevel uint8

const (
    Unsupported SupportLevel = iota
    SupportedNative
    SupportedViaCompilation
    SupportedApproximately
    SupportedConditionally
)

type SupportReport struct {
    Level SupportLevel

    RequiredViews []ViewID
    Missing       []Feature
    Compilers     []EngineID

    PossibleClaims []ClaimTemplate
    SemanticLosses []SemanticLoss
    Diagnostics    []Diagnostic
}
```

Examples:

```text
Native:
    finite deterministic STRIPS with nonnegative costs

ViaCompilation:
    conditional effects can be compiled away

Approximate:
    numeric values can be discretized, but completeness is lost

Conditional:
    continuous stream support requires a supplied sampler

Unsupported:
    strong-cyclic policy requested, engine produces only sequences
```

A request can prohibit approximation:

```go
RequiredClaims:
    validity checked
    completeness under finite deterministic model

AllowedSemanticLoss:
    none
```

This matters because “supports temporal planning” or “supports uncertainty” is too coarse to be technically meaningful.

# 18. Artifacts must not be synonymous with behavior trees

Standard artifact views should include:

```text
SequentialPlan
PartialOrderPlan
TemporalPlan
Schedule
STN
STNUDispatchStrategy
PolicyGraph
ContingentPolicy
BeliefPolicy
HierarchicalPlan
MultiAgentPlan
BehaviorTreeArtifact
RecedingHorizonPolicy
Trajectory
Controller
```

An artifact header should include:

```go
type ArtifactInfo struct {
    ID       ArtifactID
    Revision ArtifactRevision

    ProblemID       ProblemID
    ProblemRevision Revision
    ModelRevision   Revision
    SnapshotRevision Revision

    Kinds ArtifactKinds

    ObjectiveValues ObjectiveValues
    Bounds          ObjectiveBounds

    Claims     []Claim
    Provenance Provenance

    Engine EngineID
    Seed   uint64
}
```

Artifacts must be immutable and safe for concurrent reading.

A session can publish successive artifacts sharing internal structure.

## 18.1 Why a policy graph must remain a graph

A strong-cyclic FOND policy may intentionally revisit a state. Expanding it into an ordinary recursive tree can:

* create an infinite structure;
* duplicate large subpolicies;
* obscure fairness assumptions;
* lose a stable state-to-action mapping.

The BT compiler should lower it to a native:

```text
PolicyDispatch
```

operation containing a compact policy-state table.

Similarly, a POMDP search tree is usually planner-internal state. The BT should call an online action-selection behavior, not copy the entire MCTS tree into BT nodes.

# 19. Guarantees must be first-class, scoped claims

Boolean fields such as:

```go
Complete bool
Optimal  bool
```

are insufficient.

```go
type ClaimKind uint16

const (
    ClaimValidity ClaimKind = iota + 1
    ClaimSoundness
    ClaimCompleteness
    ClaimOptimality
    ClaimBoundedSuboptimality

    ClaimGroundingComplete
    ClaimModelExecutorConsistent

    ClaimStrongPolicy
    ClaimStrongCyclicPolicy
    ClaimDynamicControllability

    ClaimSafety
    ClaimTemporalLogic
    ClaimProbabilityBound
)

type ClaimStrength uint8

const (
    ClaimAsserted ClaimStrength = iota + 1
    ClaimChecked
    ClaimProved
)

type Claim struct {
    Kind     ClaimKind
    Strength ClaimStrength

    Scope       ClaimScope
    Assumptions AssumptionSet

    Bound    Bound
    Evidence EvidenceRef
}
```

Examples:

```text
Completeness:
    finite deterministic grounded task
    complete action enumeration
    exact transition model
    no opaque conditions

Optimality:
    declared scalar cost
    initial snapshot revision 109
    nonnegative action costs
    search completed without timeout

Strong-cyclic:
    nondeterministic outcomes
    fairness assumption F1

Dynamic controllability:
    STNU revision 8
    contingent duration intervals as modeled

Safety:
    LTL invariant checked over Program revision 42
    opaque custom leaves excluded
```

A world change does not necessarily invalidate plan validity, but it ordinarily invalidates an optimality claim scoped to the old snapshot.

## 19.1 End-to-end guarantees are a chain

A planner theorem alone is not an execution guarantee.

The effective mission guarantee is approximately:

[
\Gamma_{\text{mission}}
=======================

\Gamma_{\text{model}}
\land
\Gamma_{\text{grounding}}
\land
\Gamma_{\text{planner}}
\land
\Gamma_{\text{lowering}}
\land
\Gamma_{\text{executor}}
\land
\Gamma_{\text{observation}}
]

For example:

```text
Planner:
    produced an optimal valid plan under model M

Lowerer:
    preserved the plan's causal and temporal semantics

Executor:
    implemented every grounded action consistently with M

Observer:
    provided fresh and sufficiently complete state evidence

Runtime:
    maintained the relevant safety invariants
```

CABTO’s complete-and-consistent grounding formulation is directly relevant to the model-to-controller part of this chain, while formal BT tools such as BehaVerify apply to the execution-structure portion. ([AAAI Publications][12])

# 20. Typed symbolic authoring, dense symbolic execution

## 20.1 Generic authoring layer

Go 1.27 generic methods are particularly useful here:

```go
package symbolic

type Predicate[A any] struct {
    id PredicateID
}

type Fluent[A, V any] struct {
    id VariableID
}

type Builder struct {
    // Mutable authoring state.
}

func (b *Builder) Predicate[A any](
    name string,
    arguments Codec[A],
) Predicate[A]

func (b *Builder) Fluent[A, V any](
    name string,
    arguments Codec[A],
    values Domain[V],
) Fluent[A, V]

func (b *Builder) Action[B any](
    name string,
    bindings Codec[B],
) *ActionBuilder[B]
```

Because Go lacks variadic type parameters, predicate arguments should normally be structs:

```go
type AtArgs struct {
    Actor  ActorID
    Object ObjectID
}

at := builder.Predicate[AtArgs]("at", atCodec)
```

This is preferable to:

```text
"atEntity_107"
"pathBlocker_goal_1"
```

## 20.2 Freeze into dense IDs

The typed authoring layer should freeze into something like:

```go
type DenseTask struct {
    Objects    []objectRecord
    Variables  []variableRecord
    Formulas   []formulaRecord
    Actions    []actionRecord
    Outcomes   []outcomeRecord

    FormulaEdges []FormulaID

    Preconditions []FormulaID

    AddOffsets []uint32
    AddAtoms   []AtomID

    DelOffsets []uint32
    DelAtoms   []AtomID

    EffectIndex effectIndex
}
```

Different model views can expose different dense organizations:

```text
ClassicalView       STRIPS-style facts and actions
FiniteDomainView    SAS+-style variables and transitions
FormulaView         interned expression DAG
NumericView         numeric expressions and effects
TemporalView        durative actions and constraints
BeliefView          observation and transition models
HierarchyView       tasks and methods
StreamView          continuous generators and certificates
HybridView          processes and events
```

A planner requests only the view it is optimized to consume.

## 20.3 No universal DNF requirement

The present `go-pabt` representation uses an OR of conjunctions, which is useful for PA-BT.

The planner-neutral model should hold a formula DAG:

```go
type FormulaID uint32
```

Normalization into:

* DNF;
* CNF;
* BDDs;
* grounded literals;
* numeric constraints;
* temporal automata;

belongs to the engine or a problem compiler.

A DNF-only neutral API would unnecessarily constrain:

* first-order goals;
* quantified goals;
* temporal goals;
* numeric constraints;
* belief conditions;
* large formulas whose DNF is exponential.

# 21. Observation evaluation, entailment, conflict, and regression must be separate

A symbolic reasoner should expose distinct operations:

```go
type Truth uint8

const (
    TruthFalse Truth = iota
    TruthTrue
    TruthUnknown
)

type Relation uint8

const (
    RelationNo Relation = iota
    RelationYes
    RelationUnknown
)
```

Operational failure remains a Go error.

A compatibility reasoner could be:

```go
type Reasoner interface {
    PLAN_Evaluate(
        snapshot SnapshotID,
        formula FormulaID,
    ) (Truth, error)

    PLAN_Entails(
        transition TransitionID,
        formula FormulaID,
    ) (Relation, error)

    PLAN_Conflicts(
        transition TransitionID,
        formula FormulaID,
    ) (Relation, error)

    PLAN_Regress(
        formula FormulaID,
        action ActionID,
        outcome OutcomeID,
    ) (FormulaID, Relation, error)
}
```

Native engines should consume a concrete dense reasoner rather than pay this interface call in every expansion.

This design directly fixes the current `Match` conflation.

## 21.1 Unknown is not false

Belief Behavior Trees explicitly extend BT planning to conditions and actions affected by uncertainty, including unknown conditions and sensing behavior. ([Miccol][13])

A planner-grade condition result therefore needs:

```text
True
False
Unknown
Error
```

where `Error` remains separate from the semantic truth domain.

Unknown can mean:

```text
missing
stale
occluded
insufficient confidence
not yet sampled
```

A policy may respond by:

* sensing;
* waiting;
* selecting a conservative alternative;
* replanning in belief space;
* failing safely.

It must not silently execute the corrective action for an observed false fact.

# 22. Action model and action execution must be independent

## 22.1 Planning identity


# 23. Grounding must be streaming, budgeted, and explicit about completeness

A suitable general grounding protocol is:

```go
type Grounder interface {
    GROUND_Open(
        context.Context,
        GroundRequest,
    ) (GroundCursor, error)

    mustEmbedUnimplementedGrounder()
}

type GroundCursor interface {
    // The caller owns dst, avoiding a result allocation.
    GROUND_Next(
        context.Context,
        dst []Candidate,
    ) (
        n int,
        state GroundState,
        err error,
    )

    GROUND_Close(context.Context) error

    mustEmbedUnimplementedGroundCursor()
}
```

```go
type GroundState uint8

const (
    GroundMore GroundState = iota + 1

    // Exhaustive enumeration completed.
    GroundComplete

    // Exact enumeration can continue when granted another budget.
    GroundSuspended

    // The source intentionally provides only suggestions.
    GroundIncomplete
)
```

A request can include:

```go
type GroundRequest struct {
    Target FormulaID

    Relation RequiredRelation
    Bindings BindingEnvironment

    ModelRevision    Revision
    SnapshotRevision Revision

    Budget Budget
}
```

A candidate contains no executable node:

```go
type Candidate struct {
    Action ActionRef

    Support     SupportRelation
    LowerBounds ObjectiveBounds

    Certificates []CertificateRef
    Provenance   Provenance
}
```

## 23.1 Native finite grounding should normally bypass the cursor

For a finite symbolic task, use direct indexes:

```text
added literal → grounded actions
variable assignment → grounded actions
predicate → candidate schemas
resource → applicable actions
```

The cursor is the interoperability and infinite-domain abstraction, not a requirement that fast classical planners call an interface for every action.

## 23.2 Continuous streams

A TAMP stream may expose:

```go
type StreamResult struct {
    Outputs      BindingTuple
    Certified    []Literal
    ExternalCost ObjectiveValues

    Dependencies []RevisionDependency
    Evidence     CertificateRef
}
```

A trajectory certificate tied to occupancy revision 42 must not remain usable after occupancy revision 43 unless its dependency rules explicitly permit it.

## 23.3 Learned and LLM guidance

The API should distinguish:

```text
Ranker:
    reorders existing candidates

Heuristic:
    estimates remaining cost

ProposalSource:
    suggests bindings or actions; usually incomplete

Pruner:
    removes candidates and must justify claim preservation
```

A learned proposal source should ordinarily report:

```text
GroundIncomplete
```

It may accelerate PA-BT, BT Expansion, OBTEA, or TAMP, but must not silently inherit their completeness or optimality claims.

CABTO is directly instructive here: it treats learned components as heuristic search over grounding candidates and uses planner/environment feedback to seek complete and consistent grounded behavior. ([AAAI Publications][14])

# 24. Planner families and the APIs they actually require

No single `PlannerMode` enum captures these semantics. They require different views, artifacts, and runtime operators.

| Planner family             | Required model/view                                            | Native artifact                                     | BT integration requirement                                        |
| -------------------------- | -------------------------------------------------------------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| PA-BT continual refinement | symbolic conditions, exact effects, grounder, current snapshot | incrementally revised reactive policy               | compile PPA structures; preserve running actions across revisions |
| Classical A*/GBFS/BFS      | dense finite state/action view, heuristic                      | sequential plan                                     | verified sequence, optional replanning guard                      |
| SAT/SMT/CP/MILP planning   | formula/encoding view                                          | sequence, schedule, partial order                   | execute decoded artifact; retain solver certificate/provenance    |
| BT Expansion               | finite deterministic STRIPS/state-space model                  | behavior tree or condition-set policy               | preserve soundness/completeness assumptions                       |
| OBTEA                      | costs, preconditions, add/delete effects, goals                | minimum-cost BT                                     | preserve action order and objective scope                         |
| Anytime planning           | objective and lower/upper bounds                               | successive artifacts                                | revision-safe `Instance.Rebase`                                   |
| Plan repair                | prior artifact, model/world delta                              | artifact delta                                      | state transfer and safe preemption                                |
| HTN/HDDL                   | tasks, methods, decomposition constraints                      | hierarchical plan plus primitive network            | preserve hierarchy as metadata/subprogram calls                   |
| Partial-order planning     | causal links, threats, resource constraints                    | partial-order plan                                  | scheduler/resource gates or causal parallel BT                    |
| PDDL 2.1 temporal planning | durations, invariants, numeric fluents, concurrency            | temporal plan/STN                                   | temporal dispatcher, invariant monitors, injected clock           |
| STNU/CSTNU                 | contingent timepoints and constraints                          | dynamic execution strategy                          | native temporal dispatcher, not sleeps in a sequence              |
| FOND                       | nondeterministic outcomes                                      | strong or strong-cyclic policy graph                | policy dispatcher with explicit outcome edges                     |
| Contingent/belief planning | observation model and belief state                             | contingent or belief policy                         | sensing and observation-dispatch nodes                            |
| POMDP/MCTS/POMCPOW         | generative model, rewards, belief updater, samplers            | online action selector/value policy                 | planner-session node selecting one action per decision epoch      |
| TAMP/PDDLStream            | symbolic task plus black-box streams                           | grounded discrete plan plus continuous certificates | certificate validation and revision-sensitive execution           |
| LTL/LTLf synthesis         | temporal formula/automaton                                     | strategy or monitor                                 | automaton monitor/shield around planner-generated actions         |
| PDDL+ / hybrid planning    | continuous processes, events, differential dynamics            | hybrid plan/controller                              | native hybrid monitor/controller integration                      |
| Multi-agent planning       | agent-specific actions, communication, shared resources        | coordinated policy set                              | one Program/Instance per agent plus coordinator                   |

| Portfolio planning         | several engine sessions and common objective                   | best or Pareto artifact frontier                    | artifact replacement with claim comparison                        |

## 24.1 BT-native complete and optimal planning

BT Expansion provides soundness and completeness under its finite STRIPS/state-space assumptions. OBTEA introduces cost-sensitive backward expansion for an optimal BT under its model assumptions. BTPG uses typed predicate domains and STRIPS-style action models to benchmark BT planners. These require canonical symbolic conditions and exact transitions—not arbitrary callback matching. ([AAAI Publications][15])

## 24.2 Temporal and hierarchical planning

PDDL 2.1 adds numeric expressions, durative actions, and concurrency; HDDL 2.1 work extends hierarchical planning toward temporal and numeric constraints. These artifacts cannot be faithfully reduced to ordinary sequential BT nodes without retaining a temporal network and resource semantics. ([Foundations of Artificial Intelligence][16])

STNU dynamic controllability is specifically about a real-time execution strategy that reacts to contingent durations while guaranteeing temporal constraints. The BT integration must therefore be a dispatcher backed by the temporal network, not a set of fixed delays. ([DROPS][17])

## 24.3 Nondeterministic and partially observable planning

Strong FOND policies and strong-cyclic policies have different guarantees; strong-cyclic solutions carry fairness assumptions. Those assumptions must appear in artifact claims. ([JAIR][18])

POMCPOW and related online POMDP methods require weighted particle beliefs and progressive widening for continuous spaces. Their internal search structures should remain inside the planner session; BT execution should invoke the selected action and feed observations back. ([arXiv][19])

## 24.4 Temporal logic and formal verification

LTLf-based work shows that BT structures can be synthesized so that successful traces satisfy specified temporal missions. BehaVerify converts supported BT semantics into nuXmv models and requires additional models for custom leaves. These results justify explicit formal-model capabilities and temporal claim evidence in the API. ([arXiv][20])

## 24.5 Parallel and multi-agent execution

Research on converting PDDL execution graphs into BTs uses causal relationships to permit safe action parallelism. MRBTP extends BT planning to coordinated multi-robot policies through cross-tree expansion and intention sharing. The API therefore needs partial-order artifacts, resource claims, per-agent action identities, and multi-artifact coordination—not merely a generic `Parallel` composite. ([IFAAMAS][21])

# 26. How different artifacts should lower

## 26.1 Sequential plan

```text
Sequence(
    VerifiedAction(a1),
    VerifiedAction(a2),
    ...
)
```

Each `VerifiedAction` performs:

```text
check or establish dispatch preconditions
start executor
poll controller
await snapshot newer than start
verify modeled outcome
publish execution event
```

A separate replanning shell may surround the sequence.

## 26.2 Partial-order plan

Do not arbitrarily linearize unless requested.

Lower to:

```text
CausalScheduler(
    action nodes,
    predecessor counts,
    causal links,
    resource constraints
)
```

Ready actions can execute concurrently through independent executor handles.

## 26.3 Temporal plan or STNU strategy

Lower to:

```text
TemporalDispatcher(
    timepoint network,
    contingent links,
    action interval table,
    invariants,
    resource calendar
)
```

The dispatcher uses:

* an injected clock;
* event-driven wakeups;
* temporal observations;
* deadline and invariant monitors;
* the underlying dispatch strategy.

## 26.4 FOND policy graph

Lower to:

```text
PolicyDispatch(
    policy state,
    observed outcome → next policy state,
    action table
)
```

Do not duplicate cycles into a structural tree.

## 26.5 Belief policy

Lower to:

```text
BeliefDispatch(
    belief updater,
    sensing action,
    observation partition,
    selected action
)
```

The belief may remain in the planner session or an immutable belief-policy artifact.

## 26.6 Online POMDP or MCTS planner

Lower to an orchestration behavior:

```text
observe
    ↓
PLAN_Advance
    ↓
select next action
    ↓
execute and verify
    ↓
feed observation/reward back
```

The BT is a safety and lifecycle shell around the online planner.

## 26.7 HTN plan

Preserve decomposition in metadata and optional subprogram calls:

```text
task
  method
    subtask
      primitive action
```

Execution can use the primitive partial-order network while introspection retains the hierarchy.

## 26.8 LTLf mission

Lower the temporal formula to an automaton or monitor:

```text
MissionMonitor(
    planner/controller subtree
)
```

The monitor tracks progress and rejects or shields actions that would make the mission unrealizable, depending on the synthesis method.

## 26.9 Multi-agent policy

Produce:

```text
Program A + Instance A
Program B + Instance B
...
Coordinator/session
```

Intention, reservation, and outcome exchange should be versioned messages or immutable snapshots, not one shared mutable blackboard.

# 27. PA-BT v2 should become a planner engine, not a BT constructor

A revised PA-BT API should not start with:

```go
New(state, goal) -> Plan.Node()
```

It should implement:

```go
type Engine struct {
    planning.UnimplementedPlanner
}

func (e *Engine) PLAN_Open(
    ctx context.Context,
    problem planning.Problem,
    request planning.Request,
) (planning.Session, error)
```

Its session owns:

```text
failed-condition frontier
condition-set interning
action-support indexes
grounding cursors
conflict information
no-goods
mutable PA-BT PlanGraph
current artifact revision
```

It publishes an immutable artifact or artifact delta.

## 27.1 PA-BT-specific mutable representation

A compact editing node can be:

```go
type editNode struct {
    parent NodeID
    first  NodeID
    last   NodeID
    prev   NodeID
    next   NodeID

    kind    uint16
    flags   uint16
    payload uint32

    stable StableID
}
```

A mutable ID can pack index and generation:

```go
type NodeID uint64
```

This retains:

* O(1) insertion;
* O(1) deletion;
* O(1) leftward conflict relocation;
* stale-ID detection;
* fewer heap objects;
* less GC scanning;
* better locality than pointer-linked nodes.

The execution compiler consumes an immutable snapshot of this graph.

## 27.2 Search graph and execution graph should also be separate

Even PA-BT benefits from distinguishing:

```text
Search graph:
    canonical failed condition sets
    action alternatives
    costs and dominance
    cycle detection
    expanded/unexpanded state

Execution PlanGraph:
    selected or retained reactive policy structure
```

Equivalent symbolic subproblems can be hash-consed in the search graph without forcing shared runtime state in the execution tree.

## 27.3 Replace `Running()`

The session update should communicate:

```text
ContinuePlanning
ReadyToExecute
AwaitObservation
AwaitActionCompletion
Terminal
```

The acting controller can decide whether to:

* immediately spend another planning budget;
* tick the current Program;
* wait for an executor wake event;
* publish a new observation;
* switch to a better artifact.

A single Boolean cannot support this.

## 27.4 Planner variants should be separate engines

Avoid:

```go
pabt.New(
    WithCompleteMode(),
    WithOptimalMode(),
    WithBeliefMode(),
    WithTemporalMode(),
)
```

Prefer:

```go
pabt.NewEngine()
btexp.NewEngine()
obtea.NewEngine()
fond.NewEngine()
```

with shared internal libraries where useful.

A portfolio can select or run several:

```go
portfolio.New(
    pabt.NewEngine(),
    obtea.NewEngine(),
    btexp.NewEngine(),
)
```

This keeps each algorithm’s assumptions and guarantees explicit.

# 28. Performance analysis

## 28.1 What the current hot path does

An editable `go-pabt` group broadly performs:

```text
invoke Node closure
    ↓
walk linked children
    ↓
append child closures to []Node
    ↓
invoke Tick closure
    ↓
invoke child Node closure
    ↓
invoke child Tick closure
```

Condition evaluation then adds:

```text
Condition interface
    ↓
any key
    ↓
map lookup / State.Variable(any)
    ↓
any value
    ↓
Match callback
```

The proposed native built-in path is:

```text
load opcode
    ↓
load contiguous child IDs
    ↓
load per-instance state slot
    ↓
evaluate dense formula/state IDs
```

Custom behavior pays an interface call only at the extension boundary.

## 28.2 A controlled synthetic comparison

I ran a deliberately limited microbenchmark comparing:

1. a best-case static v1 closure tree;
2. a current-like editable closure tree that materializes child slices from linked nodes;
3. a direct recursive interface implementation;
4. a compact explicit-stack program;
5. a dense arena recursive evaluator.

Environment:

```text
Go 1.23.2
linux/amd64
AMD EPYC 9V74
500 ms benchmark duration
64-child wide and 64-node deep all-success trees
```

Results:

| Benchmark                      | ns/op |  B/op | allocs/op |
| ------------------------------ | ----: | ----: | --------: |
| Wide-64 static closure         | 251.6 |     0 |         0 |
| Wide-64 editable closure       | 730.3 | 1,016 |         7 |
| Wide-64 recursive interface    | 93.09 |     0 |         0 |
| Wide-64 explicit-stack Program | 149.8 |     0 |         0 |
| Wide-64 dense recursive arena  | 145.9 |     0 |         0 |
| Deep-64 static closure         | 613.0 |     0 |         0 |
| Deep-64 editable closure       | 2,041 |   512 |        64 |
| Deep-64 recursive interface    | 260.9 |     0 |         0 |
| Deep-64 explicit-stack Program | 325.0 |     0 |         0 |
| Deep-64 dense recursive arena  | 273.2 |     0 |         0 |

These are directional, not package-level performance claims:

* the benchmark used Go 1.23.2, not Go 1.27;
* it did not include errors, tracing, running nodes, rebasing, executors, or world access;
* the test trees had fixed topology and all children succeeded;
* implementation details can change inlining and branch prediction;
* a production compiler needs more metadata and lifecycle machinery.

The important findings are:

1. A static closure tree is not inherently allocation-heavy.
2. The editable projection is allocation-heavy.
3. A recursive interface can outperform the two-stage `Node`-then-`Tick` closure shape.
4. A generic explicit-stack VM is not automatically the fastest backend.
5. The architecture should permit specialized direct and iterative backends.

The correct conclusion is not “interfaces beat closures” or “bytecode beats interfaces.”

It is:

> **Use the interoperable recursive interface on the cold definition boundary, then compile built-ins into the most appropriate dense backend.**

## 28.3 Performance objectives

Release gates should include:

```text
0 steady-state allocations per built-in root tick
0 B/op for stable built-in execution
O(number of visited nodes) tick complexity
O(1) direct child lookup
no global locks in the tick path
no runtime stack inspection
no goroutine per node or action
one Program shared by many Instances
no interface dispatch for built-in composites
at most one behavior dispatch at each opaque custom-node visit
```

Planner-side objectives:

```text
no Action.Node construction during search
no map[any] in native planner loops
effect-indexed action support
caller-supplied candidate buffers
canonical formula/condition identities
arena allocation for search nodes
reusable priority queues and scratch buffers
revision-aware caches
```

## 28.4 Dense symbolic techniques

Depending on the planner:

* propositional states: bitsets;
* finite-domain state: dense `ValueID` arrays;
* sparse preconditions/effects: CSR arrays;
* action applicability: precomputed indexes;
* formula identity: hash-consed DAG nodes;
* condition sets: sorted IDs or interned bitsets;
* closed lists: hash to arena IDs;
* costs: tightly packed numeric arrays;
* plan edges: `uint32`;
* mutable graph IDs: index plus generation;
* custom values: isolated out of the hot arrays.

Do not require every planner to use the same representation. Require it to consume a typed immutable view.

# 29. Event-driven asynchronous execution

The current `Async` wrapper allocates a channel and launches a goroutine for each execution and does not provide a corresponding cancellation mechanism. ([GitHub][22])

The v2 runtime should support a shared wake mechanism:

```go
type Waker interface {
    Wake()
}

type Scheduler interface {
    WakeAt(NodeID, time.Time)
    CancelWake(NodeID)
}
```

An executor can register the instance’s waker when starting an action. When IO completes:

```text
executor receives completion
        ↓
updates handle state
        ↓
calls shared Waker
        ↓
event loop ticks the Instance
```

No per-action polling ticker and no BT-owned goroutine are required.

A periodic ticker remains available for games or simulations, but it is no longer the only model.

# 30. Clock and determinism

Time-dependent nodes must use an injected clock:

```go
type Clock interface {
    Now() time.Time
}
```

No built-in timeout, rate limiter, or temporal dispatcher should call `time.Now()` directly.

Planner and runtime requests should carry:

```text
seed
deterministic tie-break policy
operation-count budget
clock
model revision
snapshot revision
```

This enables:

* deterministic replay;
* reproducible benchmarks;
* binary-searching regressions;
* exact incident reconstruction;
* reliable formal traces.

Wall-clock timeout alone is not a reproducible search budget. Include:

```go
type Budget struct {
    MaxExpansions  uint64
    MaxEvaluations uint64
    MaxGroundings  uint64
    MaxSamples     uint64
    MaxMemoryBytes uint64

    // Optional nondeterministic real-time limit.
    MaxDuration time.Duration
}
```

A formal model can describe:


# 33. Compatibility with `go-behaviortree` v1

Changing `Node` from a function type to an interface is a major-version break. It should be a real v2 module.

## 33.1 Import a v1 tree as one opaque node

```go
package legacy

func Opaque(node v1.Node) v2.Node
```

Semantics:

* one v2 custom behavior calls `v1.Node.Tick()`;
* the entire v1 subtree is one opaque runtime occurrence;
* v2 cannot reliably halt an internal v1 asynchronous operation;
* v2 cannot optimize internal composites;
* formal verification stops at the opaque boundary;
* v1 metadata may be copied during cold binding.

This gives maximum behavioral compatibility.

## 33.2 Export a v2 instance as a v1 node

```go
func Export(instance *v2.Instance) v1.Node
```

The returned v1 node ticks the entire v2 instance as one leaf.

Its conceptual structure can be exposed through v1’s `WithStructure` metadata facility where useful.

This allows existing:

```text
Ticker
Manager
one-shot-man bridge
JavaScript integration
```

code to adopt the new runtime incrementally.

## 33.3 Structural v1 import must be explicit

Calling a v1 node closure to inspect its children may:

* execute user code;
* mutate closure state;
* return different children each time;
* register value providers;
* allocate;
* expose only physical rather than conceptual structure.

Therefore a structural importer should be named conspicuously:

```go
legacy.SnapshotStructure(...)
```

and should document that it executes node-expansion code.

Opaque import should be the safe default.

# 34. Compatibility with `go-pabt` v1

A legacy adapter can expose current models to a v2 PA-BT engine:

```go
type LegacyStateAdapter[T pabtv1.Condition] struct {
    State pabtv1.State[T]

    GroundingCoverage GroundingCoverage
```

Mappings:

| v1 concept            | v2 mapping                                                |
| --------------------- | --------------------------------------------------------- |
| `Condition.Match`     | opaque runtime evaluator plus unknown entailment/conflict |
| `State.Variable(any)` | compatibility snapshot adapter                            |
| `State.Actions`       | eager ground cursor                                       |
| returned action slice | one cursor batch                                          |

| `Action.Effects`      | declared expected assignments                             |
| `Action.Node`         | deferred execution binder                                 |

The adapter must not claim formal completeness or optimality when effect entailment remains an opaque callback.

Crucially:

> `Action.Node()` must be invoked only when the action is bound for committed execution, not when it is encountered during search.

# 35. What not to do

## 35.1 Do not merely pool child slices

Pooling may reduce allocations in the current representation, but it does not solve:

* definition/runtime state coupling;
* action construction during planning;
* preemption;
* stable identity;
* multi-instance sharing;
* policy graphs;
* semantic artifacts;
* formal claims.

## 35.2 Do not make `Node` a directly ticked stateful interface

That replaces closure opacity with interface opacity and leaves the architectural coupling intact.

## 35.3 Do not make a bytecode VM the public node API

A public opcode ABI is difficult to evolve and hostile to user-defined nodes.

Use the recursive interface publicly and bytecode or dense records internally.

## 35.4 Do not make BT the universal planner artifact

It will distort:

* STN/STNU strategies;
* cyclic policies;
* belief policies;
* hierarchical decompositions;
* continuous trajectories;
* multi-agent coordination.

BT is the execution target, not the sole semantic IR.

## 35.5 Do not put every model feature in one action struct

A struct containing every possible field for:

```text
classical
numeric
temporal
stochastic
belief
continuous
hierarchical
hybrid
multi-agent
```

would be mostly optional, difficult to validate, and poor for every native planner.

Use typed views.

## 35.6 Do not put generic methods on plugin interfaces

Go 1.27 does not support that, and the accepted design explicitly excludes it. ([Go][7])

## 35.7 Do not use context values as planner state

`context.Context` is for cancellation, deadlines, and request-scoped metadata.

The world model needs an immutable typed snapshot. Planner search state belongs to the session. BT runtime state belongs to the instance.

## 35.8 Do not mutate a Program in place

Publish a new revision and rebase at a safe boundary.

# 36. Recommended implementation sequence

## Phase 1 — normative semantics and benchmarks

Before implementing v2:

* specify reactive and memory composite semantics;
* specify activation and halt semantics;
* specify status versus error behavior;
* specify repeated-tick behavior;
* specify one-snapshot-per-root-tick;
* construct differential tests for current v1 behavior;
* establish benchmark suites.

Acceptance:

```text
Every built-in has a state-transition specification.
Every Running path has a halt test.
Invalid status never becomes ordinary Failure.
```

# 38. The documentation should be reframed around this architecture

The existing planning-and-acting page should no longer present PA-BT’s current `State`, `Condition`, and `Action.Node()` interfaces as if they formed a general planning abstraction.

A technically mature reference should explain:

## 38.1 PA-BT is one planner engine

```text
Best suited to:
    low-latency online refinement
    reactive policies
    composing action providers

Not inherently:
    complete
    cost optimal
    temporal
    belief-space
    strong-cyclic
    grounding complete
```

## 38.2 Planning and execution are separate

```text
Action model:
    what planning may reason about

Action binding:
    how the committed action is executed

Effect verifier:
    what establishes success

BT Program:
    how the artifact is reactively dispatched
```

## 38.3 Planner modes are negotiated

The documentation should show:

```go
report := engine.PLAN_Support(problem, request)
```

and explain the returned model requirements and possible claims.

## 38.4 Research maps to concrete API capabilities

| OBTEA        | explicit costs, objective bounds, canonical backward states |

| CABTO        | grounding completeness and model-executor consistency       |

“Full plan tick” is otherwise too ambiguous.

# Final recommendation

The target design should not be “a better closure” or “a faster interface.”

It should be:

> **A planner-neutral, capability-negotiated model and artifact protocol, paired with a recursively interoperable BT definition API that compiles into an immutable dense Program and executes through per-agent Instances with rigorous halt and verified-action semantics.**

The specific architectural decisions I would regard as essential are:

1. `Node` becomes an immutable recursive definition interface.
2. `Behavior` becomes per-instance custom runtime state.
3. `Program` becomes the immutable optimized execution form.
4. `Instance` owns every mutable execution field.
5. planner-side editable structures are never executed directly.
6. `Action.Node()` is removed from the planning model.
7. action execution is bound only after commitment.
8. action success requires fresh effect verification.
9. all running behavior has explicit halt semantics.
10. planner engines operate through bounded incremental sessions.
11. problem and artifact extensibility use concrete typed `Views`.
12. Go 1.27 generic methods are used on concrete builders and registries, never plugin interfaces.
13. forward-compatible embedding is used for the minimal recursive contracts.
14. exported interface methods reserve the `BT_`, `PLAN_`, `EXEC_`, or equivalent namespaces.
15. planner guarantees are scoped claims with assumptions and evidence.
16. policy graphs, temporal networks, belief policies, and TAMP certificates remain native artifacts.
17. artifact-specific lowerers compile those semantics into specialized BT runtime operations.
18. built-in tick execution is allocation-free and interface-free.
19. opaque user behavior remains universally supported through a slower fallback.
20. v1 closures remain available as adapters and convenience leaf/composite definitions.

The decisive insight is that the historic modularity-versus-performance trade-off is not resolved by finding one magical node representation. It is resolved by putting interoperability, editing, semantic planning, and execution into **different but explicitly connected representations**.

That architecture would allow PA-BT to remain a valuable reactive planner while making the surrounding ecosystem capable of supporting complete BT Expansion, cost-optimal OBTEA, temporal and hierarchical planning, FOND and belief policies, online POMDP search, task-and-motion streams, temporal-logic synthesis, multi-agent coordination, formal verification, and future planning research without repeatedly breaking or diluting the foundational API.
