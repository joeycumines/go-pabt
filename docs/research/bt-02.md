# Technical autopsy of the `osm:pabt` reference and implementation

## Executive verdict

The page is a useful **conceptual introduction** to PA-BT, but it is not yet a dependable technical reference. Its most important problems are not editorial:

* Several examples are incompatible with the implementation and cannot behave as described.
* The documentation presents a much stronger reliability story than either the original PA-BT paper or the present implementation supports.
* The JavaScript API discards useful expressiveness provided by the underlying Go planner.
* Condition failures, observation uncertainty, bridge failures, and programming errors are collapsed into the same Boolean result.
* Actions are trusted to have achieved their declared effects merely because their BT node returned `Success`.
* The documented static-plus-parametric behavior differs materially from the source.
* The performance table mixes unmeasured or non-comparable quantities.

The best optimization is therefore **not** initially a faster condition evaluator. It is a redesign of the semantic boundary between observations, symbolic planning, and physical execution.

My recommended end state is:

> Retain PA-BT as a reactive execution and incremental-refinement substrate, but place it over a typed, versioned, formally interpretable action model with atomic observations, verified effects, explicit costs and resources, bounded search, and selectable completeness/optimality modes.

I inspected the target page, the current JavaScript bridge, state/action/condition and blackboard implementations, the underlying `go-pabt` planner, the checked-in benchmark source, repository history, the original PA-BT paper, and relevant research through AAAI 2026. The page was added on February 9, 2026, while the bridge implementation was subsequently changed on May 4, 2026, which helps explain some of the documentation drift. I could not rerun the repository test suite in this environment, so runtime conclusions below are source-derived rather than independently benchmarked. ([GitHub][1])

# 1. What the implementation actually does

At the core, expansion approximately follows this rule:

```text
Given failed condition c:

candidate action a is relevant when
    normalize(a.effect.key) == normalize(c.key)
and c.match(a.effect.value) == true

Then construct:
    Fallback(
        c,
        Sequence(
            action-preconditions,
            action-node
        )
    )
```

When several actions are relevant, the underlying planner places their subtrees under a memorizing selector. Failed preconditions can themselves be expanded, and conflict resolution attempts to move a newly introduced subtree leftward until it precedes actions whose effects conflict with its conditions. ([GitHub][2])

The Go core supports:

* goals in disjunctive normal form: an OR of AND groups;
* alternative precondition groups for an action;
* multiple alternative actions;
* incremental tree mutation;
* action-failure-triggered re-refinement;
* conflict relocation.

But the JavaScript bridge exposes goals only as an OR of individual conditions and action preconditions only as one conjunction. Thus, the core can represent:

[
(A \land B)\lor(C\land D)
]

but the JavaScript API cannot express that goal directly. Likewise, an action whose preconditions are `(A ∧ B) OR (C ∧ D)` cannot be represented through `newAction`. ([GitHub][3])

This distinction matters because the page describes a relatively simple action matcher, while the actual behavior depends on:

* DNF grouping;
* action ordering;
* memorizing-selector semantics;
* failed-condition selection;
* conflict relocation;
* action generator precedence;
* the exact meaning of `Running`;
* whether an action's declared effect is actually observed.

Those are the mechanisms that determine correctness and liveness.

# 2. High-confidence defects in the current page

## 2.1 The quick-start example has a broken observation loop

The example synchronizes:

```javascript
actorX
actorY
atCube
handsEmpty
```

but the goal tests the blackboard key `heldItem`. The action changes `actor.heldItem`, yet `heldItem` is never written to the blackboard. The planner therefore never observes its goal becoming true. ([GitHub][4])

This is worse than merely “the goal never succeeds.” Given the PPA structure:

```text
Fallback(
    heldItem == 1,
    Sequence(atCube, Pick)
)
```

the root can return `Success` through the `Pick` branch on the same tick that the goal condition failed. On the next tick, the goal remains false because it was not synchronized, so the action may execute again.

That produces **phantom success**:

[
\text{BT Success} \not\Rightarrow \text{observed goal satisfaction}
]

This violates the most important planner postcondition.

### Immediate correction

At minimum, the example must include:

```javascript
bb.set(
  'heldItem',
  actor.heldItem === null ? null : actor.heldItem.id
);
```

More importantly, an action should not produce final `Success` merely because it dispatched or locally mutated something. It should remain `Running` until a **fresh observation revision** confirms the effect, or fail with a model/execution error.

A robust action protocol is:

```text
dispatch command
    ↓
wait for completion or timeout
    ↓
publish a new world snapshot
    ↓
verify declared effects in that snapshot
    ↓
only then return Success
```

---

## 2.2 The conflict-resolution example cannot select the advertised action

The page says that when the failed condition is `handsEmpty`, an action with effect:

```javascript
{ key: 'heldItem', value: null }
```

will be found and inserted. But action relevance requires the failed condition and effect to have the same normalized key. Consequently:

```text
failed key: handsEmpty
effect key: heldItem
```

cannot match, regardless of the values. ([GitHub][4])

The correct model should use one canonical state variable:

```javascript
const handsEmpty = {
  key: 'heldItem',
  match: value => value === null
};

const placeTemporaryEffect = {
  key: 'heldItem',
  value: null
};
```

Better still, `handsEmpty` should be a **derived condition**, not an independently synchronized Boolean. Maintaining both:

```text
heldItem = 42
handsEmpty = true
```

permits logically inconsistent world states.

---

## 2.3 “Static + parametric actions” is not additive in the implementation

The page says static and generated actions can be combined. The source comments say the same. But the actual logic treats any non-empty successful generator result as authoritative and skips the static registry.

Crucially, this happens even when none of the generated actions has a relevant effect. Therefore:

```text
generator returns [irrelevantAction]
static registry contains relevantAction
```

can yield no candidates at all. ([GitHub][4])

This is an actual completeness defect, not merely a documentation ambiguity.

### Recommended API

```typescript
state.setActionGenerator(generator, {
  mode: "augment",       // default
  errors: "strict",
  maxCandidates: 128
});
```

Semantics should be explicit:

* `augment`: generated and static candidates are combined.
* `override`: generated candidates replace static candidates.
* `fallback`: use generated candidates if at least one is relevant; otherwise scan static actions.
* `strict`: generator exceptions fail planning.
* `lenient`: generator exceptions are recorded and static actions remain available.

The current silent, implicit override behavior should not be the default.

---

## 2.4 The page simultaneously requires exact effects and recommends speculative effects

Early in the page, effects are defined as state guaranteed to be true after an action succeeds. Later, “heuristic effects” that may not occur are encouraged. The page acknowledges that the planner may retry or loop when the guessed effect remains false. ([GitHub][4])

The underlying planner uses effects to:

1. decide whether an action is relevant;
2. construct the PPA postcondition;
3. reason about action conflicts;
4. determine candidate alternatives.

The upstream action-model contract also says that all relevant effects must be mapped and that undeclared side effects are not allowed. ([GitHub][3])

A speculative correlation is therefore not an effect in the planning sense. Treating it as one corrupts the planner's transition model.

### Replace one field with two

```typescript
interface ActionModel {
  guaranteedEffects: Transition;
  predictedConsequences?: PredictedConsequence[];
}
```

* `guaranteedEffects` participate in correctness, regression, conflict detection, completeness, and verification.
* `predictedConsequences` participate only in heuristic ranking or expected-utility calculation.

For the blockade example:

```typescript
guaranteedEffects: {
  heldItem: blockadeCubeId
},

predictedConsequences: [{
  condition: reachable(target),
  probability: 0.65,
  evidenceSource: "learned-clearance-model-v3"
}]
```

If an action has genuinely nondeterministic outcomes, model those outcomes explicitly rather than pretending one hoped-for outcome is an effect.

## 2.5 Several documented API calls do not match the exposed JavaScript API

The current source exposes `plan.running()`, not `plan.Running()`. The `pabt.State` wrapper does not expose `state.actions.All()`, and it exposes `get` and `set` rather than a documented `blackboard` property. The action-sync example may have intended an application-specific aggregate object, but it does not say so. ([GitHub][4])

Other drift includes:

* “three components” followed by four action arguments;
* `newExprCondition(key, expression, [value])` supporting an optional generator-passthrough value that the page does not document;
* `getAction` existing in the bridge but receiving little or no reference treatment;
* action names described as unique while duplicate registrations silently replace previous actions.

The action registry explicitly performs replacement and returns actions sorted lexicographically by registration name. ([GitHub][5])

This should be solved by generating API reference material from the bridge schema or TypeScript declarations and running every code block as a documentation test.

# 3. The deepest semantic problem: `match` is doing three different jobs

The current condition abstraction is approximately:

```typescript
interface Condition {
  key: unknown;
  match(value: unknown): boolean;
}
```

The same `match` function is used for at least two semantically different operations:

1. **Observation evaluation**

   ```text
   Does the currently observed value satisfy this condition?
   ```

2. **Effect entailment**

   ```text
   Would the value declared by an action's effect satisfy this condition?
   ```

Conflict detection introduces a third related requirement:

3. **Compatibility/conflict reasoning**

   ```text
   Does this effect preserve, establish, or contradict another condition?
   ```

In the action-relevance code, the planner invokes `failed.Match(effect.Value())`. For a JavaScript condition, that means running the actual JavaScript callback against a synthetic effect value. ([GitHub][2])

This is only semantically safe when the matcher is:

* pure;
* deterministic;
* total;
* dependent solely on its argument;
* stable over the duration of planning;
* meaningful when applied to an abstract effect value.

The documentation, however, advertises JavaScript closures for complex conditions. A matcher could depend on:

* another world variable;
* current time;
* randomness;
* a mutable closure;
* an external service;
* a side effect of its own.

For example:

```javascript
{
  key: 'distance',
  match: d => d < currentWeapon.range &&
              target.visible &&
              Math.random() > 0.1
}
```

Calling that matcher on an action's synthetic `distance` effect is not a proof that the effect entails the condition.

## Recommended condition abstraction

```typescript
interface SymbolicConstraint {
  readonly id: ConstraintId;
  readonly variable: VariableId;

  evaluate(snapshot: WorldSnapshot): ConditionResult;

  // Planning-time relation:
  isEntailedBy(effect: SymbolicEffect): boolean;

  // Conflict analysis:
  conflictsWith(effect: SymbolicEffect): boolean;

  // Search, caching, and cycle detection:
  canonicalForm(): CanonicalConstraint;
}
```

Built-in constraint forms should include:

* equality and inequality;
* finite-domain membership;
* numeric intervals;
* Boolean composition;
* typed predicate literals;
* temporal freshness constraints.

Arbitrary JavaScript conditions may remain available as **opaque runtime guards**, but they should be excluded from modes claiming soundness, completeness, or optimality unless accompanied by a sound symbolic abstraction.

This single change would make a large portion of modern planning research directly usable.

# 4. Boolean condition results are insufficient

## 4.1 Infrastructure errors are converted into ordinary false conditions

`JSCondition.Match` returns `false` for:

* a nil matcher;
* a nil bridge;
* a stopped bridge;
* a JavaScript callback exception;
* a bridge marshalling error.

The comments say errors are logged, but the shown implementation simply returns `false`. `ExprCondition.Match` does record and log errors, but still returns `false` to the planner. Expressions are also compiled with undefined variables allowed. ([GitHub][6])

This creates a dangerous equivalence:

```text
“The door is observed closed”
            ==
“The observation subsystem is unavailable”
            ==
“The condition contains a typo”
            ==
“The JavaScript runtime is stopping”
```

The planner may respond to all four by selecting an action intended to open the door.

## 4.2 Missing and explicit null are conflated

A missing blackboard key returns `nil`, while `null` is also represented as `nil` after JavaScript-to-Go conversion. Thus:

```text
heldItem is explicitly null
```

and:

```text
heldItem has never been observed
```

can satisfy the same null check. ([GitHub][2])

For safety and partial observability, these states must be distinct.

## Recommended result model

```typescript
type ConditionResult =
  | {
      kind: "satisfied";
      evidence?: Evidence;
    }
  | {
      kind: "unsatisfied";
    }
  | {
      kind: "unknown";
      reason: "missing" | "stale" | "occluded" | "insufficient-confidence";
      sensingActions?: ActionSchemaId[];
    }
  | {
      kind: "error";
      error: Error;
    };
```

The default control policy should be:

* `satisfied`: continue;
* `unsatisfied`: consider planning actions;
* `unknown`: sense, wait, or fail conservatively;
* `error`: stop planning and surface an operational fault.

This is not only safer. It also creates the correct integration point for belief-space behavior trees.

# 5. The blackboard is thread-safe but not transactionally consistent

The blackboard protects each operation with a mutex. That makes individual reads and writes race-safe, but a sequence of writes is not atomic. `Snapshot()` creates a shallow copy, and mutable values remain aliased. ([GitHub][7])

Consequently:

```javascript
bb.set('actorX', actor.x);
bb.set('actorY', actor.y);
bb.set('heldItem', held);
bb.set('reachable', calculateReachability());
```

is not a batch update merely because those calls occur in one function. A ticker running concurrently can observe:

```text
actorX from frame N+1
actorY from frame N
heldItem from frame N
reachable from frame N-1
```

The page's threading description explicitly puts BT ticking on a Go goroutine while JavaScript work is marshalled through an event-loop bridge, so consistent world revisions are operationally important. ([GitHub][4])

## Replace mutable per-key truth with immutable frame snapshots

```typescript
interface WorldSnapshot {
  readonly revision: bigint;
  readonly observedAt: number;

  readonly facts: ReadonlyMap<FactId, FactValue>;
  readonly provenance: ReadonlyMap<FactId, ObservationMetadata>;
}
```

Application-side synchronization should be:

```typescript
const frame = world.beginFrame();

frame.set(actorX(actorId), actor.x);
frame.set(actorY(actorId), actor.y);
frame.set(heldItem(actorId), actor.heldItem?.id ?? null);
frame.set(reachable(actorId, cubeId), computeReachability());

world.commit(frame); // One atomic publication and revision increment
```

One planner tick must hold one immutable snapshot pointer for its entire evaluation.

Benefits include:

* no torn reads;
* deterministic replay;
* cheap revision-keyed memoization;
* reliable postcondition verification;
* straightforward observation age checks;
* lock-free or low-lock hot-path reads;
* meaningful planner trace records.

Derived conditions should be memoized against the snapshot revision rather than maintained as independent writable facts.

# 6. `plan.running()` is being assigned the wrong meaning

The upstream implementation defines `Running()` narrowly: it indicates that the previous root tick returned `Running` specifically as the result of an action-node tick. It is only valid between root ticks. It is not a general “plan is active,” “planning is finished,” or “world observations may safely be skipped” signal. ([GitHub][3])

The page recommends using it to avoid recomputing expensive reachability facts during action execution. This can preserve stale conditions exactly when moving objects, obstacles, or other agents make those conditions most likely to change. It also uses the wrong method casing. ([GitHub][4])

The correct optimization is:

* always publish safety-critical and action-relevant observations;
* memoize expensive derived facts by their actual dependencies;
* invalidate them when those dependencies change;
* allow freshness requirements in conditions;
* compute only facts requested by the current planning frontier, if demand-driven evaluation is needed.

Do not gate world correctness on `plan.running()`.

# 7. Action `Success` is not evidence that an effect occurred

The page says the action node must mutate JavaScript state so that a later sync reflects the effect. Yet the BT can already propagate `Success` before that later sync occurs. ([GitHub][4])

This confuses three events:

1. command accepted;
2. action controller finished;
3. planner-visible effect observed.

For synchronous toy actions these may coincide. For animation, navigation, IO, robotics, networking, or distributed systems they usually do not.

## Recommended execution state machine

```text
Created
  → Dispatched
  → Running
  → ControllerCompleted
  → AwaitingObservation
  → Verified
  → Success
```

Failure states should distinguish:

```text
Rejected
TimedOut
Cancelled
ControllerFailed
VerificationFailed
ModelViolation
ObservationError
```

A generated subtree should behave conceptually like:

```text
Fallback(
    ObservedPostcondition,

    Sequence(
        EnsurePreconditions,
        ExecuteOrPollAction,
        AwaitSnapshotNewerThan(action.startRevision),
        VerifyGuaranteedEffects
    )
)
```

On verification failure:

* do not blindly report ordinary action failure;
* record the observed state delta;
* mark the action model as inconsistent;
* apply a bounded retry policy;
* temporarily no-good the same action/binding under equivalent conditions;
* consider an alternative action;
* escalate repeated model violations.

A useful invariant is:

[
\text{Plan.Success}
\Rightarrow
\text{Goal satisfied in a fresh committed snapshot}
]

That invariant should become an executable property test.

# 8. Asynchronous actions need cancellation and stale-completion semantics

The upstream planner explicitly warns that the eventual result of a running asynchronous action is not guaranteed to be consumed. A reactive tree may stop ticking that action because an external event satisfied its postcondition or because another branch became preferable. ([GitHub][3])

The present reference does not define:

* what happens when a running action is no longer ticked;
* whether it is cancelled;
* whether cleanup occurs;
* whether repeated ticks redispatch the command;
* how a late callback is rejected;
* how action instances are identified;
* whether the operation is idempotent;
* what timeout applies;
* whether compensation is available.

## Required lifecycle contract

Every action execution should carry:

```typescript
interface ActionInstance {
  planId: string;
  treeRevision: bigint;
  actionInstanceId: string;
  bindingId: string;
  startWorldRevision: bigint;
  deadline: number;
  idempotencyKey: string;
  attempt: number;
}
```

The execution API should support:

```typescript
execute(context)
poll(context)
cancel(context)
cleanup(context)
compensate(context)
```

A completion event must be ignored unless its `actionInstanceId` is still active. Cancellation and cleanup must be invoked when the BT branch is halted.

For actions with duration, also introduce:

* exclusive resource claims;
* invariants that must hold while running;
* interruptibility classifications;
* safe interruption points;
* deadlines and watchdogs.

Without these, `Running` is a status code rather than a reliable acting protocol.

# 9. The current planner is neither complete nor cost-optimal

The original PA-BT paper explicitly assumes:

* valid grounded action refinement always exists;
* handling absent valid refinement is out of scope;
* a non-conflicting action order exists;
* optimal action selection is not investigated.

The paper also explicitly describes some environmental changes as requiring replanning and tree extension. The page's broader statement that the structure “inherently handles failure” without a separate replanning trigger should therefore be narrowed. ([ar5iv][8])

The accurate distinction is:

* **Execution-level reactivity:** already-satisfied conditions can be skipped, and a reversed condition can cause an existing subtree to run again.
* **Online refinement:** a newly failed, expandable condition can cause tree expansion.
* **Action failure recovery:** possible only if the model exposes another viable refinement or the tree is rebuilt into a viable one.
* **Completeness:** not currently guaranteed.
* **Optimality:** not currently attempted.
* **Recovery from arbitrary failures:** not guaranteed.

The implementation's own conflict-resolution comments note ambiguity in the original presentation for multiple candidate actions and multiple alternative condition groups. ([GitHub][9])

# 10. Action ordering is currently an accidental policy

Static actions are returned sorted by registration name. Multiple relevant actions are placed under a memorizing selector, so candidate order determines which alternative gets the first opportunity and which running alternative remains selected. ([GitHub][10])

As a result, renaming:

```text
MoveSafely
```

to:

```text
A_MoveSafely
```

can change agent behavior.

That is deterministic, but it is not meaningful planning.

## Add explicit decision criteria

At minimum, every action should expose:

```typescript
cost
estimatedDuration
successProbability
risk
resourceContention
switchingCost
```

A greedy reactive mode could use:

[
J(a)
====

c(a)
+\lambda_t d(a)
-\lambda_p \log p_{\text{success}}(a)
+\lambda_r r(a)
+\lambda_s s(a)
]

This remains a heuristic unless embedded in a search algorithm with an appropriate objective and proof. The action name should be only a final deterministic tie-breaker.

# 11. Cycles, dead ends, and retries need explicit semantics

The page itself acknowledges that speculative effects may lead to retries or loops. The exposed API does not provide a clear contract for:

* cyclic precondition dependencies;
* repeated equivalent expansions;
* unsatisfiable goals;
* maximum tree depth;
* search budgets;
* retry budgets;
* temporal backoff;
* no-good learning;
* generator completeness;
* action-space finiteness.

For example:

```text
Action A:
  requires B
  establishes A

Action B:
  requires A
  establishes B
```

must not trigger unbounded alternating expansion.

## Required planner controls

```typescript
interface PlanningBudget {
  maxExpansions: number;
  maxDepth: number;
  maxWallTimeMs: number;
  maxGeneratedCandidates: number;
  maxRetriesPerActionBinding: number;
}
```

Use canonical condition-set hashes to maintain:

```text
ancestor set       — immediate cycle detection
bestCost map       — dominated-path elimination
expanded set       — repeated-expansion prevention
no-good cache      — known dead ends
```

No-goods should be versioned by:

```text
world revision class
domain/model version
failed condition set
resource constraints
```

Planner termination should be typed:

```typescript
type PlanTermination =
  | "succeeded"
  | "unsatisfiable"
  | "budget-exceeded"
  | "model-error"
  | "observation-error"
  | "cancelled";
```

Ordinary BT `Failure` is not expressive enough for diagnostics or policy decisions.

# 12. The JavaScript binding unnecessarily reduces planning expressiveness

The underlying goal is an OR of conjunctions, and an action may have an OR of conjunctions as its precondition. The JavaScript bridge converts each goal element into a singleton conjunction and all action conditions into one conjunction. ([GitHub][5])

Introduce explicit combinators:

```typescript
const goal = anyOf(
  allOf(
    eq(location(robot), kitchen),
    eq(holding(robot), mug)
  ),
  allOf(
    eq(location(robot), table),
    eq(mugAt, table)
  )
);
```

Action preconditions should use the same language:

```typescript
precondition: anyOf(
  allOf(hasGripper(robot), reachable(robot, mug)),
  allOf(hasTray(robot), mugOnTray(mug))
)
```

Avoid assigning different implicit meanings to nested and flat arrays. Make logical structure explicit in both runtime objects and TypeScript types.

# 13. Replace string-encoded predicates with typed terms

The page encourages keys such as:

```text
atEntity_42
reachable_target
reachable_17
```

This creates several problems:

* string parsing becomes part of action grounding;
* collisions and spelling differences are undetectable;
* parameter domains are implicit;
* unification is impossible;
* effect indexing is coarse;
* renaming schemas is risky;
* static model validation is weak.

Use typed predicates or finite-domain variables:

```typescript
at(actorId, entityId)
reachable(actorId, entityId)
holding(actorId)
location(actorId)
```

or:

```typescript
Fact {
  predicate: "at";
  args: [actorId, entityId];
}
```

The current key/value representation maps naturally to a SAS+-style finite-domain model:

```text
location(actor) ∈ {cube, goal, staging, ...}
heldItem(actor) ∈ {none, cube1, cube2, ...}
```

A finite-domain assignment such as:

```text
heldItem(actor) := cube1
```

implicitly replaces the previous value and is easier to reason about than maintaining many mutually exclusive Boolean keys.

Typed terms also permit true lazy grounding:

```text
MoveTo(?actor, ?target)
```

with constrained bindings, rather than relying on `startsWith` and `parseInt`.

# 14. Action parsing must fail closed

The JavaScript bridge silently skips malformed action conditions and effects, including:

* null entries;
* non-object entries;
* entries without a key;
* conditions without a callable matcher;
* effects without a value.

By contrast, goal parsing is substantially more fail-fast. ([GitHub][5])

Silently dropping a precondition is especially dangerous:

```javascript
pabt.newAction(
  'DangerousOperation',
  [
    { key: 'safetyInterlock' /* match accidentally omitted */ }
  ],
  effects,
  node
);
```

can become an action with no effective guard.

Use schema validation at registration:

```typescript
const result = actionSchema.safeParse(input);

if (!result.success) {
  throw new ActionSchemaError(result.error);
}
```

Other required checks include:

* non-empty stable action ID;
* no duplicate effect variables;
* no duplicate condition variables within a conjunction;
* finite and valid costs;
* known predicate and object types;
* valid expression compilation;
* declared resources;
* executor and verifier availability;
* duplicate registration rejection.

Provide a deliberately named operation for replacement:

```typescript
state.replaceAction(id, expectedVersion, action);
```

Do not make replacement the silent behavior of `registerAction`.

# 15. Performance claims need to be reconstructed

The document gives approximate figures including:

* state lookup around 500 ns;
* JavaScript condition around 5 μs;
* expression condition around 100 ns;
* Go function condition around 50 ns;
* full plan tick around 10 μs.

The checked-in benchmark notes instead report approximately:

* expression conditions around 88–262 ns depending on operation;
* Go function conditions around 1–13 ns;
* first expression compilation around 8.4 μs;
* cached expression lookup around 157 ns;
* simple plan construction around 1.7 μs;
* five-action plan construction around 4.1 μs.

But the checked-in suite does **not** measure the same complete set of operations. In particular, it does not provide the documented full-tick, JavaScript bridge, or `State.Variable` measurements. It measures condition evaluation and plan construction. Thus, neither set should be used as a substitute for the other. ([GitHub][4])

## Better performance model

A planner tick is approximately:

[
T_{\text{tick}}
\approx
N_{\text{JS}}
\left(T_{\text{bridge}}+T_{\text{callback}}\right)
+
N_{\text{expr}}T_{\text{expr}}
+
T_{\text{generator}}
+
T_{\text{candidate search}}
+
T_{\text{tree traversal}}
+
T_{\text{action}}
]

The likely high-leverage targets are not sub-100-nanosecond expression details.

### 15.1 Reduce bridge crossings

Every JavaScript condition evaluation is synchronously marshalled to the event loop. Batch evaluations for one snapshot into one bridge invocation, or compile common symbolic predicates to Go-native constraints. ([GitHub][6])

### 15.2 Index actions by effects

Current relevance scanning is approximately:

[
O(|A|\cdot\bar{|E|})
]

per failed condition.

Maintain:

```text
predicate/variable → candidate actions
```

For equality effects:

```text
variable → effect value → candidate actions
```

For interval constraints, use interval or range indexes.

### 15.3 Cache grounding correctly

Cache grounded action **models and bindings**, not arbitrary closures over mutable world state. Cache keys should include:

```text
failed symbolic condition
world/domain revision
binding domain version
resource context
```

The page's generic recommendation to cache parametric actions needs invalidation semantics.

### 15.4 Compile expressions at registration

Expressions should be compiled and validated when registered, not on the first live planning tick. Undefined variables should be rejected by default rather than allowed. ([GitHub][6])

### 15.5 Use immutable snapshots

A single immutable snapshot avoids repeated per-key locking and gives every condition in the tick the same state revision.

### 15.6 Separate the planning graph from the execution tree

Maintain a hash-consed AND/OR planning DAG internally. Equivalent condition sets should share nodes during search. Compile or materialize the required structure into an execution BT afterward. This avoids duplicated planning subproblems even if the BT engine ultimately requires a tree.

### 15.7 Publish reproducible benchmarks

Every published benchmark should include:

* commit SHA;
* Go version;
* CPU and OS;
* bridge/event-loop configuration;
* action and effect counts;
* tree depth and branching;
* generator cardinality;
* allocations;
* p50, p95, and p99;
* benchmark command;
* cold versus warm-cache status.

Generate the documentation table from CI output rather than maintaining approximate numbers manually.

# 16. Research that can be applied directly

There is unusually applicable research here. The primary prerequisite is replacing opaque matcher/effect semantics with a formal symbolic layer.

## 16.1 BT Expansion: add a complete planner mode

The 2021 BT Expansion algorithm provides a state-space formulation and proves soundness and completeness under its formal assumptions. It was designed precisely because earlier BT synthesis methods could fail on solvable tasks. ([AAAI Publications][11])

### Direct application

Implement:

```typescript
plannerMode: "complete"
```

using BT Expansion over:

* a finite symbolic state space;
* exact deterministic action transitions;
* explicit preconditions;
* complete action grounding;
* well-formed goals.

The current PA-BT mode can remain the low-latency option, but its guarantees should be labelled differently:

```text
reactive-lazy:
  low planning latency
  best-effort
  not complete
  not optimal

complete:
  finite-model completeness
  potentially higher planning cost
```

The completeness theorem cannot be inherited while action relevance is decided by arbitrary JavaScript callbacks or while effects are permitted to be heuristic.

---

## 16.2 OBTEA: add a cost-optimal backward search mode

The 2024 Optimal Behavior Tree Expansion Algorithm represents actions using STRIPS-style preconditions, add effects, and delete effects, normalizes goals into DNF, and searches backward through condition sets by accumulated action cost. ([IJCAI][12])

For a needed condition set (C), OBTEA explores an action (a) and constructs the predecessor:

[
C_a = pre(a)\cup\left(C\setminus add(a)\right)
]

while excluding actions that delete required literals. It expands the currently lowest-cost unexplored condition set and retains only cost-improving paths. ([IJCAI][12])

### Direct transplant

```text
priority queue:
    condition set ordered by accumulated cost

bestCost:
    canonical condition set → lowest known cost

parent:
    condition set → action and successor condition set

stop:
    current snapshot satisfies an explored condition set
```

Each goal DNF clause can be initialized as an alternative search root.

This provides:

```typescript
plannerMode: "optimal"
```

provided that:

* action costs are nonnegative;
* effects are exact;
* the grounding set is complete;
* condition sets have canonical identities;
* the state model matches execution.

The present implementation already has the broad backward-expansion shape, but it lacks the cost search, delete-effect formalism, canonical condition sets, and completeness assumptions needed for the result.

---

## 16.3 BTPG and UHBTP: adopt their benchmark methodology and heuristics

The 2025 Behavior Tree Planning Gym formalizes everyday-service domains using predicate logic and STRIPS-style action models. It evaluates BT planners across RoboWaiter, VirtualHome, OmniGibson, and RobotHow and introduces metrics for:

* planning progress;
* region distance;
* execution robustness;
* planning time and timeout rate;
* action cost and count;
* tree size;
* execution tick count. ([IJCAI][13])

The same paper's UHBTP approach uses domain-independent heuristic information to prioritize promising condition sets. The results also show a practical trade-off: faster heuristic planning can increase action cost or tree size, and robustness of generated trees remains an open challenge rather than an automatic property. ([IJCAI][13])

### Direct application

Use delete-relaxation planning layers to estimate literal and condition-set distance:

```text
h(literal) = first relaxed layer containing literal
h(condition set) = aggregate of literal estimates
```

Use this for an **anytime** mode:

```typescript
plannerMode: "anytime"
```

A sensible policy is:

1. run heuristic search within a small budget;
2. execute an available safe prefix if permitted;
3. retain a complete fallback frontier;
4. continue improvement between action ticks;
5. never permanently discard candidates solely because a heuristic ranked them poorly.

---

## 16.4 Belief Behavior Trees: model unknown conditions and sensing

Belief Behavior Trees extend BT planning to partially observable environments. They explicitly model uncertainty in conditions and actions, include actions whose purpose is to reduce uncertainty, and support nondeterministic outcomes. ([miccol.github.io][14])

This maps directly onto the current `nil`/missing and observation-error problems.

### Minimal applicable version

Introduce:

```text
Satisfied
Unsatisfied
Unknown
Error
```

and permit a condition to nominate sensing actions:

```typescript
{
  condition: objectAt(cube, goal),
  result: "unknown",
  sensingActions: [
    inspectRegion(goal),
    queryObjectTracker(cube)
  ]
}
```

Add observation metadata:

```typescript
interface ObservationMetadata {
  source: string;
  observedAt: number;
  confidence: number;
  revision: bigint;
}
```

A condition can then require:

```text
confidence ≥ 0.9
age ≤ 250 ms
```

Unknown should not be treated as false unless the domain explicitly uses a closed-world assumption.

---

## 16.5 CABTO: formalize grounding completeness and model consistency

CABTO, published at AAAI 2026, defines BT grounding as construction of a **complete and consistent** BT system whose high-level action models align with low-level control policies. It directly targets the assumption that usable grounded actions already exist. ([AAAI Publications][15])

This is highly relevant even without adopting its large-model components.

### Apply its concepts in CI

**Completeness checks**

* Can every required predicate be established initially or by at least one grounded action?
* Does the action generator cover all declared object and parameter domains?
* Does every goal clause have a possible backward-support path?
* Does a generator declare when its candidate enumeration is incomplete?

**Consistency checks**

* When an executor reports success, do fresh observations satisfy every guaranteed effect?
* Are undeclared writes observed?
* Can the action violate its own persistent invariants?
* Does the low-level policy require conditions absent from the high-level model?
* Are declared resources actually acquired?

A learned model or LLM may propose candidate schemas or bindings, but the symbolic planner and execution verifier should decide whether they are admissible.

---

## 16.6 BehaVerify, Fiacre, and LTLf: add formal safety and temporal goals

BehaVerify translates behavior trees into nuXmv models and checks nontrivial LTL properties, including trees with selectors, sequences, parallel nodes, and custom leaves given appropriate models. ([arXiv][16])

The Fiacre-based work provides formal BT semantics, offline model checking, and runtime verification. ([arXiv][17])

Goal-oriented LTLf synthesis shows how successful BT traces can be made to satisfy temporal mission formulas, extending beyond final-state DNF goals. ([arXiv][18])

### Direct application

Export each stable BT revision plus the symbolic action model into a verification representation. Check invariants such as:

```text
G ¬(holding(robot, cube1) ∧ holding(robot, cube2))

G (inForbiddenZone(robot) → emergencyStopActive)

G (actionDispatched → F(actionCompleted ∨ actionTimedOut))

G ¬(resourceHeldBy(A) ∧ resourceHeldBy(B))
```

Because the planner mutates its tree online, verifying the full unbounded mutation process on every tick may be impractical. A more deployable design is:

1. formally verify the static safety shell;
2. verify a finite family of permitted graft templates;
3. statically validate each generated action model;
4. run lightweight temporal monitors at runtime;
5. optionally model-check exported tree revisions offline.

Use LTLf mission goals for requirements such as:

```text
inspect A before entering B
never carry hazardous items through zone C
eventually deliver X, then return home
```

These cannot be represented faithfully as a simple final-state OR.

---

## 16.7 HBTP and active inference: useful, but not foundational

HBTP uses an LLM-generated heuristic path to guide BT expansion while retaining a symbolic planner around it. The paper is explicit that LLM correctness and safety are uncertain; the LLM is used for heuristic guidance rather than as the sole executor. ([arXiv][19])

The active-inference/BT work uses an offline BT structure while selecting local actions online to handle partial observability and contingencies. ([arXiv][20])

Both are reasonable later additions:

* use LLMs to rank candidate schemas, suggest bindings, or construct reversible search hints;
* use active inference or another probabilistic controller inside bounded local subgoals.

Neither should precede atomic observations, exact effects, action verification, and explicit safety constraints.

---

## 16.8 Temporal and parallel execution

Research on converting PDDL execution graphs into BTs demonstrates that causal relationships can be used to parallelize independent actions. ([arXiv][21])

This becomes relevant once actions declare:

```typescript
readSet
writeSet
resources
invariants
duration
interruptibility
```

Parallel execution should be allowed only when:

* write sets do not conflict;
* neither action deletes the other's invariant;
* exclusive resources are disjoint;
* failure and cancellation semantics are defined.

A parallel BT node alone is not a concurrency model.

# 18. Planner modes should expose their guarantees

| Mode            | Algorithmic intent                                    | Honest guarantee                                                       |
| --------------- | ----------------------------------------------------- | ---------------------------------------------------------------------- |
| `reactive-lazy` | Present PA-BT-style incremental expansion             | Fast best-effort refinement; neither complete nor optimal              |
| `complete`      | BT Expansion or equivalent exhaustive symbolic search | Complete under documented finite deterministic model assumptions       |
| `optimal`       | OBTEA-style uniform-cost backward search              | Minimum declared action cost under documented assumptions              |
| `anytime`       | Heuristic expansion with complete fallback            | Rapid initial solution when available; improving solution over budget  |
| `belief`        | Belief-state conditions and sensing actions           | Explicit uncertainty handling under declared observation/outcome model |

A plan object should expose its assumptions:

```typescript
plan.guarantees()
```

returning something like:

```json
{
  "complete": false,
  "optimal": false,
  "requiresDeterministicEffects": true,
  "requiresFreshObservations": true,
  "groundingComplete": false,
  "plannerMode": "reactive-lazy"
}
```

This is much more useful than a generic assertion that the tree “handles failure.”

# 20. Required test and evaluation programme

## 20.1 Semantic properties

The following properties should hold across generated domains:

```text
Plan Success implies the goal is true in a fresh snapshot.

An Error condition never triggers an ordinary corrective action.

An Unknown safety condition never permits an unsafe action.

A guaranteed effect that is not observed produces ModelViolation.

The same world snapshot, model version, and seed produce the same
candidate ordering and tree revision.

Augment-mode generators never suppress relevant static actions.

An irrelevant generated action never makes a reachable plan unreachable.
```

## 20.2 Differential planning tests

For randomly generated finite action domains:

* compare `complete` mode with a reference STRIPS solver;
* when the reference says solvable, complete mode must solve;
* when both terminate, solvability classifications must agree;
* compare `optimal` mode's total cost with a reference uniform-cost solution;
* validate every returned action sequence by forward simulation.

This is much stronger than testing a few hand-written pick-and-place examples.

## 20.3 Property-based and fuzz testing

Fuzz:

* malformed JavaScript condition objects;
* effects with missing or duplicate keys;
* cyclic action models;
* generator exceptions;
* enormous generator outputs;
* bridge shutdown during matching;
* expression parser failures;
* stale and reordered observations;
* asynchronous late completion;
* duplicate action registration;
* cancellation at every action lifecycle state.

## 20.4 Disturbance scenarios

Test at least:

* external goal achievement;
* reversal of an achieved effect;
* action controller failure;
* effect not observed after reported success;
* unexpected side effect;
* a new obstacle;
* deleted or moved target;
* missing observation;
* stale observation;
* low-confidence observation;
* generator failure;
* incomplete grounding;
* bridge shutdown;
* resource contention;
* cancellation;
* delayed completion from an obsolete action instance.

These distinguish true execution robustness from ordinary BT reevaluation.

## 20.5 Metrics

Record:

* solve rate;
* soundness violations;
* completeness failures;
* optimality gap;
* planning p50/p95/p99;
* full-tick p50/p95/p99;
* bridge calls per tick;
* generator time and candidate count;
* expansions and revisitations;
* action cost and count;
* tree and planning-DAG size;
* execution ticks;
* recovery latency;
* retry and no-good counts;
* model-violation rate;
* snapshot age;
* memory and allocations;
* execution robustness under controlled noise.

BTPG's planning-progress, region-distance, and execution-robustness metrics are especially suitable for comparing the current PA-BT mode with complete, optimal, and heuristic alternatives. ([IJCAI][13])

# 22. Suggested replacement for the opening claim

> `osm:pabt` is an online reactive behavior-tree expansion engine based on PA-BT. Under a deterministic and fully observable state model, accurate declared action effects, fresh state synchronization, and viable grounded actions, it incrementally expands failed conditions into Postcondition–Precondition–Action subtrees. The resulting tree can skip conditions that have already been achieved and can re-execute existing subtrees when observed facts are reversed.
>
> The default algorithm is not a complete or cost-optimal planner. It does not guarantee recovery from arbitrary action failures, invalid or incomplete action grounding, stale or unknown observations, unmodelled side effects, cyclic dependencies, unsatisfiable goals, or domains in which no conflict-free action ordering exists. Applications requiring those guarantees should use the corresponding complete, optimal, belief-state, or verified planning modes.

That wording preserves the genuine strengths of PA-BT without overpromising.

# Bottom line

Yes—there is directly applicable research, not merely tangential literature.

The most immediately useful sequence is:

1. **Formalize the model boundary.**
2. **Make observations atomic and typed.**
3. **Verify effects rather than trusting action status.**
4. **Expose full logical structure and explicit grounding.**
5. **Add bounded search, cycle detection, costs, and diagnostics.**
6. **Implement BT Expansion for completeness.**
7. **Implement OBTEA-style search for cost optimality.**
8. **Use BTPG/UHBTP for heuristics and evaluation.**
9. **Use BBT for uncertainty and sensing.**
10. **Use CABTO-style consistency checks and formal BT verification for deployment assurance.**

The central technical principle is:

> **The theorem boundary follows the symbolic-model boundary.**

As long as planner semantics are based on arbitrary JavaScript matchers, speculative effects, non-atomic state, and unverified action success, the system can be reactive and useful, but it cannot honestly inherit soundness, completeness, optimality, or robustness guarantees from the planning literature. Once those boundaries are made explicit and machine-checkable, the existing PA-BT execution machinery becomes a strong foundation rather than a limiting factor.
